What a container actually is

Before writing a Containerfile, you need an accurate picture of what happens when you run one. Most confusing container behaviour follows from a few facts about processes, filesystems and kernels, and this lesson covers those facts.

By the end you should be able to explain

  • why a container starts in milliseconds and a VM doesn't

01The problem containers solve

An application is more than its source code. A typical AI web service needs a specific Python version, pinned packages like torch and transformers, system libraries such as libgomp or ffmpeg, environment variables, and a start command. Each of these can differ between your laptop, a colleague's laptop, CI and production. When one of them does, you get the classic “works on my machine” bug.

A container packages the application together with everything it needs from the operating system's user space: the runtime, the libraries, the files and the default command. The result runs the same way anywhere a container engine is available. That is why teams ship containers rather than instructions for setting up a server.

02Containers are processes, not small VMs

This is the most important idea in the lesson. A virtual machine emulates a whole computer: it boots its own operating system with its own kernel on top of a hypervisor. A container is an ordinary Linux process running on the host's kernel. The kernel restricts what that process can see and use, so from the inside it looks like a separate machine.

The kernel provides two features that make this isolation work:

  • Namespaces control what a process can see. A process in its own PID namespace sees itself as PID 1 and can't see other processes on the host. Other namespaces give it its own network interfaces and ports, its own hostname, its own mount table (and therefore its own root filesystem) and its own view of user IDs.
  • Control groups (cgroups) control what a process can use. They cap CPU, memory and the number of processes. When you pass --memory 2g, a cgroup enforces it. If a model loads more than that, the kernel's OOM killer ends the process.

Add a separate root filesystem, which comes from the image, and you have a container. There is no other machinery. This explains most container behaviour:

  • Fast start. Starting a container means starting a process, not booting a kernel. It takes milliseconds.
  • Low overhead. There is no guest OS using memory, so one host can run many containers.
  • Linux containers need a Linux kernel. The container brings its own libraries but never its own kernel.
  • Weaker isolation than a VM. All containers share one kernel, so a kernel bug can affect all of them. This is why running containers as a non-root user matters, and why cloud providers often run containers inside lightweight VMs.

03Why your Mac runs a VM anyway

macOS uses its own kernel (Darwin), not Linux, so it can't run Linux containers directly. Podman solves this with podman machine: a small Linux VM (Fedora CoreOS) that runs in the background. The podman command on your Mac sends each request over a socket to the Podman service inside that VM, and the containers run there. Docker Desktop, OrbStack and Colima work the same way.

Three consequences are worth knowing from day one:

  • The VM has its own resource limits. If a container runs out of memory while loading a model, the VM's limit may be the cause. You can change it with podman machine set --memory and --cpus, then restart the machine.
  • Mounting files from your Mac crosses the VM boundary. Sharing your source folder with a container works, but file I/O is slower than on Linux.
  • CPU architecture matters. On an Apple-silicon Mac, the VM is arm64, so images you build are linux/arm64 by default. Most servers are linux/amd64. An arm64 image on an amd64 server fails with exec format error. You'll learn to build for the right platform with --platform linux/amd64 in a later lesson.

04Images: the template

An image is a read-only template for a container. It has two parts:

  1. A stack of filesystem layers. Each layer is a diff: the files one build step added, changed or deleted, stored as an archive and identified by the SHA-256 hash of its contents.
  2. A config. This holds the default command, environment variables, working directory, the user to run as, exposed ports and the target platform (such as linux/amd64).

You build images from a Containerfile. Docker calls it a Dockerfile, and the syntax is identical. Each instruction that changes files, mainly RUN, COPY and ADD, produces a new layer on top of the previous ones. When the engine assembles the container's root filesystem, it stacks the layers with a union filesystem (usually overlayfs), so the process sees one merged directory tree.

Because layers are identified by their content, they are stored and downloaded once. If ten of your images use python:3.12-slim as their base, its layers exist on disk once, and a registry push sends only the layers the registry doesn't already have.

Gotcha

Deleting a file in a later layer doesn't shrink the image. A later layer can only record “this file is deleted”, which hides the file; the bytes stay in the earlier layer. If one RUN step downloads a 4 GB model and the next step deletes it, your image still contains 4 GB. Clean up in the same step that created the files, or use a multi-stage build, which you'll learn later.

Layers also make builds fast. The builder caches each layer, and when you rebuild, it reuses every layer up to the first instruction whose inputs changed. The order of instructions therefore decides how much of the build is reused. This is the main topic of Lesson 2.

05Containers: a running instance

A container is what you get when you start an image. It consists of:

  • the image's read-only layers,
  • a thin writable layer on top, unique to this container,
  • runtime settings you choose at start: published ports, environment variables, mounted volumes, memory and CPU limits,
  • and a running main process.

If you think in code, an image is like a class and a container is like an object: you can create many independent instances from one image, and each has its own state.

When a container modifies a file that came from the image, the file is first copied into its writable layer and the change is made there. This is copy-on-write. The image itself never changes, which is why a hundred containers can share one image safely.

Key rule

Treat containers as disposable. When a container is removed, its writable layer goes with it. A new deployment replaces your containers with new ones from a new image. Anything worth keeping, such as user uploads, database files or downloaded model weights you don't want to download again, must live in a volume (storage managed outside the container, covered in a later lesson) or in an external service like a database or object storage.

06The container lifecycle

A container isn't a machine that stays switched on. It's one program with walls around it, and when that program finishes, the container is done. The rest of this section explains why, because it's behind several confusing first experiences.

The main process

Every image names a command to run when a container starts:

ImageDefault command
python:3.12-slimpython3, an interactive Python prompt
nginxnginx, a web server
your FastAPI imagesomething like uvicorn main:app

If you add a command after the image name in podman run, it replaces the default:

podman run docker.io/library/python:3.12-slim python -c "print('hi')"

Whichever command runs is the container's main process. Inside the container it gets process ID 1, PID 1, because it's the first process there. Any other processes in the container were started by it.

A virtual machine keeps running after your app ends, because a whole operating system is running underneath. A container has nothing underneath, so:

  • Container running = main process running.
  • Main process ends = container stops. Any other processes still inside are killed at the same moment.

It works like running python script.py in your terminal: the process runs until the script finishes, then it's gone. A container behaves the same way, with isolation added.

Why podman run python:3.12-slim exits instantly

podman run docker.io/library/python:3.12-slim
  1. The container starts python3, the image's default command.
  2. Normally python3 shows a >>> prompt and waits for you to type.
  3. Without -it, your keyboard isn't connected to the container. Python sees there's no terminal, so it doesn't show a prompt. It reads its input as a script instead, and that input is empty.
  4. An empty script has nothing to do, so Python exits successfully.
  5. The main process ended, so the container stops. Your shell prompt comes back instantly, with no output. podman ps -a shows Exited (0), and 0 means success.

Nothing is broken; Python simply had no work to do. Compare:

podman run -it docker.io/library/python:3.12-slim

-i connects your keyboard and -t gives it a terminal, so now you get a >>> prompt. The container runs for as long as you stay in Python. Type exit() and the container stops, for the same reason as above.

Why a web server must stay in the foreground

On a normal server, many programs send themselves to the background: you run nginx, it starts a hidden copy of itself, and your command returns straight away while the server keeps running. That works there because the operating system keeps everything alive. In a container, it breaks:

  1. The command you started is PID 1.
  2. It starts a background copy of itself, then the original exits.
  3. PID 1 exited, so the container stops, and the background copy is killed with it.
  4. The container starts and exits immediately, and the server never answers a request.

So in a container the server must run in the foreground: the main process is the server, and it keeps running until it's told to stop. The official nginx image runs nginx -g 'daemon off;' for this reason. uvicorn and gunicorn run in the foreground by default, so your AI apps are usually fine. In a Containerfile, avoid &, nohup, --daemon flags and service … start.

Don't confuse

podman run -d is not the same as a program going to the background. -d only means your terminal doesn't wait for the container. Inside the container, the main process still runs in the foreground as normal.

Stopping is a two-step signal. podman stop sends SIGTERM, waits a grace period (10 seconds by default), then sends SIGKILL. Your app should handle SIGTERM by finishing in-flight requests and exiting. For an AI service that is mid-way through a long generation, this is the difference between a clean shutdown and a dropped response. The exit code tells you what happened: 0 is success, and 137 (128 + signal 9) means the process was killed, either by SIGKILL after the grace period or by the OOM killer.

07Registries and image names

A registry is a server that stores images: Docker Hub, GitHub's ghcr.io, Red Hat's quay.io, AWS ECR, Google Artifact Registry. You pull images from registries and push your own. A full image reference has four parts:

docker.ioRegistry/ libraryNamespace/ pythonRepository: 3.12-slimTag

library is the namespace Docker Hub uses for its official images. Your company's images might look like 123456789.dkr.ecr.eu-west-1.amazonaws.com/team/rag-api:1.4.2.

  • A tag is a movable label. python:3.12-slim is rebuilt regularly with security patches, so the same tag points to different images over time. latest has no special meaning; it's only the tag used when you don't write one, and it's a poor choice for anything you deploy.
  • A digest is an exact identity. python@sha256:… identifies the image by a hash of its contents and can never change. Use digests or specific version tags when you need reproducible deployments.
  • One tag can cover several platforms. Most official images publish a manifest list with one variant per platform, such as linux/amd64 and linux/arm64. The engine pulls the variant that matches the machine, which is why the same pull works on your Mac and on a server.
Podman

Docker assumes that a short name like python means Docker Hub. Podman doesn't assume a registry: depending on its configuration, it may ask you to pick one, or search a list of registries. Get used to writing fully qualified names, such as docker.io/library/python:3.12-slim. It avoids the prompt, and it's a good habit for security, because you always know which registry you're pulling from.

08Podman vs Docker

Both tools follow the OCI (Open Container Initiative) standards for images and runtimes. An image built with Podman runs on Docker and Kubernetes, and the reverse is also true. The commands match closely enough that many people run alias docker=podman. The differences are in the architecture:

DockerPodman
ArchitectureThe CLI sends every command to a long-running background service, dockerd.No central service. Each container is started directly and watched by a small monitor process, conmon.
PrivilegesThe service traditionally runs as root. Rootless mode exists but isn't the default.Rootless by default. Root inside a container maps to your unprivileged user outside it.
Build fileDockerfileContainerfile or Dockerfile, same syntax
Multi-container appsdocker composepodman compose, which reads the same compose files, or podman kube play for Kubernetes YAML
PodsNot availableGroups of containers that share a network namespace, the same idea as Kubernetes pods
On macOSA Linux VM managed by Docker DesktopA Linux VM managed by podman machine

For this course, the practical effect is small. Examples you find online written for docker will almost always work if you replace the word with podman. When your team's scripts or CI use Docker, your images still work there.

09Vocabulary

imageRead-only template: a stack of layers plus a config.
layerOne filesystem diff, identified by the hash of its contents.
containerA running (or stopped) instance of an image: image layers, a writable layer, runtime settings and a main process.
ContainerfileThe recipe for building an image. Called Dockerfile by Docker.
registryA server that stores and serves images.
tagA movable, human-readable label for an image version.
digestAn exact, unchangeable image identity: sha256:….
namespaceKernel feature that limits what a process can see.
cgroupKernel feature that limits what a process can use.
volumeStorage that lives outside a container and survives its removal.
OCIThe open standards for image format and container runtimes that Docker, Podman and Kubernetes share.
podman machineThe Linux VM that runs your containers on macOS.

10Check yourself

Try answering each question out loud before opening it.

Q1Why does a container start in under a second while a VM takes much longer?Show

Starting a container means starting a process on a kernel that's already running, with namespaces and cgroups applied. A VM has to boot a whole operating system and its kernel first.

Q2Your service saves user uploads to /app/uploads inside the container. You deploy a new version. What happens to the uploads?Show

They are lost. The new version runs in a new container from a new image, and the old container's writable layer is deleted when it's removed. Uploads belong in a volume or in object storage.

Q3A Containerfile downloads a 4 GB model in one RUN step and deletes it in the next. How much does the model add to the image?Show

The full 4 GB. The first layer still contains the file; the second layer only records that it's deleted. Download and delete in the same step, or use a multi-stage build.

Q4An image built on your Apple-silicon Mac fails on the production server with exec format error. Why?Show

It was built for linux/arm64 because the Podman VM on your Mac is arm64. The server is linux/amd64 and can't run arm64 binaries. Build with --platform linux/amd64, or build in CI on an amd64 machine.

Q5You run podman run docker.io/library/python:3.12-slim and it exits immediately with no output. Is something wrong?Show

No. The main process is the Python interpreter. Without -it it gets no terminal, so it treats its empty input as a script, has nothing to run and exits with code 0. The container stops with it.

Q6Will python:3.12-slim pulled next month be byte-for-byte the same as today's? How do you guarantee an exact image?Show

Probably not, because tags move when the image is rebuilt. Reference the image by digest (python@sha256:…) to get exactly the same image every time.

Q7You start 10 containers from the same 1 GB image. Roughly how much disk do they use?Show

About 1 GB plus whatever each container writes. The read-only layers are shared; only the writable layers are per container.

Q8A container stopped with exit code 137 while loading a model, and nobody ran podman stop. What's the most likely cause?Show

The OOM killer. 137 means the process received SIGKILL. Without a stop command, the usual source is exceeding a memory limit: the container's own --memory limit, or on a Mac, the memory of the Podman VM.

11See it for real

You don't need to understand every command yet. The goal is to see the ideas above with your own eyes. Run these in your Mac's terminal.

Make sure the Linux VM is running

podman machine list

If the list is empty, create a machine first with podman machine init. If it shows one that isn't running, start it:

podman machine start

Containers run on a Linux kernel, not macOS

uname -s   # on your Mac: Darwin
podman run --rm docker.io/library/python:3.12-slim uname -srm

The second command prints Linux with a kernel version and your VM's architecture (aarch64 on Apple silicon). That kernel belongs to the VM; the image didn't bring one. --rm removes the container when it exits.

An image is a stack of layers

podman history docker.io/library/python:3.12-slim
podman image inspect docker.io/library/python:3.12-slim --format '{{.Os}}/{{.Architecture}}, {{len .RootFS.Layers}} layers'

history lists the build steps that created each layer, newest first, with their sizes. inspect shows the platform that was pulled for your machine.

Namespaces, and the disposable writable layer

podman run -it --rm docker.io/library/python:3.12-slim bash

You now have a shell inside a container. Run:

echo $$            # 1: bash is PID 1 in its own PID namespace
cat /etc/hostname  # the container ID, not your Mac's name
touch /i-was-here && ls /i-was-here
exit

Then start a fresh container from the same image and look for the file:

podman run --rm docker.io/library/python:3.12-slim ls /i-was-here

It isn't there. The file lived in the first container's writable layer, which was deleted with it.

A container lives as long as its main process

This container runs a 5-second job and stops by itself:

podman run --rm docker.io/library/python:3.12-slim python -c "import time; print('working...'); time.sleep(5); print('done')"

This one starts sleep 60 in the background, and the main shell exits straight away:

podman run --name bg docker.io/library/python:3.12-slim sh -c 'sleep 60 & echo "started sleep in the background"'
podman ps -a --filter name=bg
podman rm bg

podman ps -a shows Exited (0) almost immediately, not after 60 seconds. The background sleep was killed when the main process ended, which is exactly what happens to a web server that sends itself to the background.

The lifecycle and the stop signal

podman run -d --name sleeper docker.io/library/python:3.12-slim sleep 600
podman ps
podman stop sleeper
podman ps -a
podman rm sleeper

-d runs the container in the background. Notice that podman stop takes about 10 seconds and the status afterwards is Exited (137). sleep doesn't handle SIGTERM, and the kernel ignores unhandled signals sent to PID 1, so Podman waits out the grace period and sends SIGKILL. You've just watched the two-step stop from section 6. Your own services should handle SIGTERM so they stop cleanly.
