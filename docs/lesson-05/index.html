Docker Fundamentals · Lesson 5 · Serving a real model

Putting a real model in a container

hello-ai's "model" was a keyword counter. This lesson swaps in a real transformer model and shows, with measurements from the test Mac, what changes: image size, start-up time, memory, CPU use and response streaming. It ends with what's different when a model needs a GPU.

Reading about 40 minLab about 45 minPractice app ~/practice/hello-modelOutputs from the test Mac, autumn 2026

By the end you should be able to

  • install PyTorch without gigabytes of GPU libraries you don't use
  • bake a pinned model into an image, and know when to download it instead
  • separate "the process is alive" from "the model is ready" so no request arrives too early
  • set a memory limit from measurements, and recognise when a container was killed for exceeding it
  • stop PyTorch from fighting a CPU limit
  • stream a response through a container
  • explain what a GPU container needs, and where GPUs are available on AWS and Cloudflare

01The practice app: hello-model

The second practice app is in ~/practice/hello-model, where the setup step put it. It runs DistilBERT SST-2, a widely used sentiment model (Apache-2.0 licence, 268 MB), on the CPU:

EndpointWhat it does
POST /predictReturns positive or negative, a confidence score, and how long the model took
GET /health/liveAnswers as soon as the server is running
GET /health/readyReturns HTTP 503 until the model is loaded, then 200
GET /streamSends a reply word by word, the way LLM APIs stream tokens

Three files matter: main.py (the API), download_model.py (fetches one pinned revision of the model files) and requirements.txt. A .containerignore is included. The Containerfile is yours to write in the lab.

02Installing PyTorch the right way

Step 1: see what a plain install brings

PyTorch is published in several builds. The one you get from a plain pip install torch on a Linux x86-64 server is built for NVIDIA GPUs. These are PyPI's numbers for version 2.14.0, checked in September 2026:

What pip downloads for Linux x86-64Size
Default build: the torch package555 MB
Default build: 16 NVIDIA CUDA packages it depends on1.4 GB
Default build, totalabout 2.0 GB
CPU-only build (arm64: 159 MB)196 MB

If your service runs on CPUs, those 1.8 GB are pure cost: slower builds, bigger images, slower deploys.

Step 2: ask for the CPU build

The CPU build lives on PyTorch's own package server. requirements.txt in hello-model points pip there:

hello-model/requirements.txtpinned
--extra-index-url https://download.pytorch.org/whl/cpu

Also look for packages on PyTorch's CPU package server, as well as the normal one (PyPI).

torch==2.14.0+cpu

The +cpu version only exists on that server, so pip takes it from there. Everything else comes from PyPI.

transformers==5.17.0 huggingface_hub==1.33.0 fastapi==0.141.1 uvicorn==0.54.0

Hugging Face's model library, its download client, and the web server, all pinned (Lesson 2).

Installed, all of this still takes 1.02 GB: PyTorch unpacks to several hundred MB, plus transformers and numpy. Images with PyTorch are big; the goal is to avoid the unnecessary part, not to reach 200 MB.

Step 3: download only the files you need

Model repositories often hold the same weights in several formats. This one has five copies (PyTorch, safetensors, TensorFlow, ONNX, Rust), about 1.3 GB together. download_model.py asks for exactly four files, 268 MB, and pins the revision so a rebuild next month gets identical weights:

MODEL_REVISION = os.getenv("MODEL_REVISION", "714eb0fa89d2f80546fda750413ed43d93601a13")
FILES = ["config.json", "model.safetensors", "tokenizer_config.json", "vocab.txt"]
snapshot_download(MODEL_ID, revision=MODEL_REVISION, local_dir=target, allow_patterns=FILES)

It takes only the .safetensors weights, which can't run code when loaded (Lesson 3, section 8).

03The Containerfile

It is the Lesson 3 Containerfile with two additions: a setting that tells the app where the model is, and a step that downloads the model during the build.

hello-model/Containerfile1.44 GB
FROM docker.io/library/python:3.12-slim@sha256:f77ac9…e51f ENV PYTHONUNBUFFERED=1 ENV MODEL_DIR=/models/sst2 RUN useradd --create-home --uid 1000 app

Pinned base, unbuffered output and the app user, as in Lesson 3. MODEL_DIR tells the app where the model is. Write the full digest.

WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir -r requirements.txt

The packages. This step reruns only when requirements.txt changes.

COPY download_model.py . RUN python download_model.py /models/sst2

Copy the download script alone, then run it. The download reruns only if download_model.py or a line above it changes, never because you edited main.py.

COPY . . USER app

Packages, then model, then code: from least to most often changed, so editing code rebuilds a 5 kB layer, not 1.3 GB.

EXPOSE 8000 HEALTHCHECK --interval=15s --timeout=3s --start-period=60s --retries=3 \ CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health/ready', timeout=2)"] CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

The health check calls /health/ready, with a longer start period because models take time to load.

Built on the test Mac in 43 seconds. podman history shows where the size comes from:

Output (largest layers)

1.02GB   RUN pip install …                   ← Python packages, mostly PyTorch
269MB    RUN python download_model.py …      ← the model weights
5.12kB   COPY . .                            ← your code
         + 149 MB python:3.12-slim           = 1.44 GB

After a changed comment in main.py and a rebuild, every step up to and including the download printed Using cache, and the build took 1.6 seconds.

04Alive vs ready

A model has to be loaded into memory before it can answer. That took 1.9 seconds here; a large language model can take minutes. If requests arrive during that time, they fail. The app answers two different questions:

  • /health/live: is the process running and responsive? If not, the platform should restart it.
  • /health/ready: can it serve requests right now? If not, the platform should send traffic elsewhere and wait. It shouldn't restart anything.

To make that possible, main.py loads the model in a background thread, so the server can answer health checks during loading:

@asynccontextmanager
async def lifespan(app):
    threading.Thread(target=load_model, daemon=True).start()   # don't block start-up
    yield

@app.get("/health/ready")
def ready():
    ...
    if state["status"] != "ready":
        return JSONResponse(body | {"error": state["error"]}, status_code=503)
    return body

The container was started, and /health/ready was asked every quarter second:

Measured on the test Mac

  0.0s  HTTP 000                                    ← nothing listening yet
  0.6s  HTTP 503 {"status":"loading","load_seconds":null,…}
  2.5s  HTTP 200 {"status":"ready","load_seconds":1.9,"torch_threads":5}
  • Liveness must not depend on the model. If /health/live waited for the model and loading took longer than the platform's patience, the platform would restart the container mid-load, again and again: a restart loop.
  • Readiness is what load balancers should check. On AWS ECS Express Mode, that's the health-check path you set (Lesson 6). Kubernetes uses both separately (Lesson 7).
  • The container's HEALTHCHECK uses /health/ready with --start-period=60s, so slow loading isn't counted as failure. podman ps showed (healthy) after the first check.

05Memory

Step 1: measure

podman stats --no-stream

Output, model loaded

NAME   MEM USAGE / LIMIT
api    382.1MB / 3.784GB      ← the limit is the whole Podman VM

Most of that is the model's weights in memory: 66 million numbers at 4 bytes each is about 265 MB, plus Python and PyTorch.

Step 2: find what happens below it

--memory sets a hard limit, enforced by a cgroup (Lesson 1). Several were tried:

Measured on the test Mac

--memory 600m   ready, 314 MB used
--memory 300m   ready
--memory 250m   Exited (137)   OOMKilled=true      ← killed while loading

Exit code 137 is SIGKILL (Lesson 1), and podman inspect CONTAINER --format '{{.State.OOMKilled}}' confirms who sent it: the kernel's out-of-memory killer. The logs show nothing useful, because the process never got a chance to write anything. On AWS the same event appears as a stopped task with the reason OutOfMemoryError.

Rule: measure peak memory, then set the limit with headroom, often 1.5 to 2 times. For this model that's around 768 MB. Memory use also rises with longer inputs and bigger batches, so measure with realistic requests.

Step 3: every worker is a full copy

uvicorn can run several worker processes for more throughput. Each one loads its own model:

uvicorn … --workers 2

model ready in 2.2 s          ← printed twice: two copies
MEM USAGE  638.5MB            ← vs 382 MB with one worker

For small models that's fine. For large models the usual pattern is one worker per container and more containers, or a dedicated model server (like vLLM or Triton) that shares one copy across many requests.

06CPU and threads

PyTorch splits each prediction across several threads, one per CPU it can see. Inside a container with a CPU limit, it still sees all of them:

podman run -d --name api --cpus 1 -p 8000:8000 hello-model:1.0
podman exec api nproc
curl localhost:8000/health/ready

Output

5                                                  ← all of the VM's CPUs
{"status":"ready","load_seconds":1.6,"torch_threads":5}
  1. --cpus 1 doesn't hide CPUs. It limits how much CPU time the container gets: one CPU's worth.
  2. PyTorch sees 5 CPUs and starts 5 threads.
  3. The 5 threads compete for one CPU's worth of time. The kernel pauses and resumes them constantly, and they wait on each other.

Setting OMP_NUM_THREADS tells PyTorch how many threads to use. Thirty requests each way, same limit:

With --cpus 1ThreadsMedian time90th percentile
Default564.6 ms85.7 ms
-e OMP_NUM_THREADS=1130.8 ms35.0 ms

Twice as fast with one setting. Rule: set OMP_NUM_THREADS to the number of CPUs the container is allowed. On AWS you choose CPU per task (for example 1 vCPU), so pass OMP_NUM_THREADS=1 as an environment variable in the same place. Without a limit, all 5 threads were useful: the median was 12 ms.

07Streaming responses

LLM APIs don't wait until the whole answer is written; they send it piece by piece, so users see text appear. hello-model's /stream endpoint imitates that with Server-Sent Events: one HTTP response that stays open and sends data: … lines as they're ready.

curl -N "localhost:8000/stream?text=hello"

Output, with the time each line arrived

58.59  data: {"token": "You"}
58.90  data: {"token": "wrote:"}
59.21  data: {"token": "hello."}
59.51  data: {"token": "Streaming"}
59.82  data: {"token": "sends"}
…      data: [DONE]

Each piece arrived 0.3 seconds after the previous one, straight through the container and the published port. -N stops curl from saving output up before printing it: the same buffering problem as Lesson 3's PYTHONUNBUFFERED. Streaming breaks when something in between buffers or times out:

  • Reverse proxies such as nginx buffer responses by default. The header X-Accel-Buffering: no turns that off for nginx.
  • Load balancers close connections that are quiet for too long. An AWS Application Load Balancer's default is 60 seconds of no data. Long generations should keep sending something.
  • Test streaming through the real path (load balancer, Worker, proxy), not only against the container directly.

08Baked in or downloaded at start

Lesson 3 listed three places for model weights. hello-model supports two with the same image: if MODEL_DIR has no model, the app downloads it there first. Point MODEL_DIR at a volume and the download happens once:

podman run -d --name api -p 8000:8000 -e MODEL_DIR=/cache/sst2 -v models:/cache hello-model:1.0

Measured on the test Mac

first start:   0.6s downloading
first start:   4.5s loading
first start:   6.4s ready          ← 268 MB downloaded into the volume
second start:  0.6s loading
second start:  1.9s ready          ← found in the volume, no download
Baked into the imageDownloaded at start
Image size1.44 GB1.17 GB, and it doesn't grow with bigger models
Ready afterabout 2 s, every time6.4 s first time here, much longer for big models or slow networks
Needs at startNothingNetwork access to Hugging Face (or your S3 bucket) and somewhere writable
Updating the modelNew imageChange MODEL_REVISION, restart

On Cloudflare, container disks are wiped when a container sleeps, so a downloading container downloads again on every wake-up. That's a strong reason to bake models in there. When a model is baked in, set HF_HUB_OFFLINE=1 so Hugging Face libraries never try to contact the internet.

09GPUs

This model answers in 12 ms on CPU, so it doesn't need a GPU. Large language models and image models usually do. You can't try this part on your Mac: CUDA needs an NVIDIA GPU, and Macs don't have one. The idea is short, though.

What a GPU container needs, and where each part lives

PartWhere it lives
NVIDIA kernel driverThe host. It's part of the kernel, and containers share the host's kernel (Lesson 1).
NVIDIA Container ToolkitThe host. It lets the container engine hand GPU devices to a container.
CUDA and cuDNN librariesThe image: the 1.4 GB of NVIDIA packages from section 2, or an nvidia/cuda base image
Your code and modelThe image
  • Starting one: with Podman, podman run --device nvidia.com/gpu=all …, after the toolkit has described the GPUs with nvidia-ctk cdi generate. With Docker, docker run --gpus all ….
  • The compatibility rule: the host's driver must be new enough for the CUDA version in your image. Newer drivers run older CUDA; the reverse fails even though the image is fine.
  • On AWS: Fargate, which ECS Express Mode uses, has no GPUs. GPU containers run on EC2 GPU instances (the g5 or g6 families, for example), managed by ECS or by EKS (Kubernetes), or behind a SageMaker endpoint.
  • On Cloudflare: Containers offer CPU and memory sizes only. For GPU inference, Cloudflare's product is Workers AI, which runs hosted models for you, without containers.
  • Cost: GPU instances cost many times more than CPU ones. Measure first: small models like this one are often fast enough on CPU.

10Lab: containerize hello-model

Work in ~/practice/hello-model. The first build downloads about 450 MB (PyTorch and the model).

1

Read the app

cd ~/practice/hello-model
cat requirements.txt download_model.py
less main.py

Find where the model loads in a background thread, and what /health/ready returns before it's done.

2

Write the Containerfile

Start from your Lesson 3 Containerfile and change it so that it:

  • sets MODEL_DIR=/models/sst2
  • copies download_model.py alone and runs python download_model.py /models/sst2, after pip install and before the rest of the code is copied
  • has its health check on /health/ready, with a 15-second interval and a 60-second start period
Show solution
FROM docker.io/library/python:3.12-slim@sha256:f77ac9e44ae96ef2c90b8053ea08c31f8be030f824196b0ae4db6d462c84e51f
ENV PYTHONUNBUFFERED=1
ENV MODEL_DIR=/models/sst2
RUN useradd --create-home --uid 1000 app
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY download_model.py .
RUN python download_model.py /models/sst2
COPY . .
USER app
EXPOSE 8000
HEALTHCHECK --interval=15s --timeout=3s --start-period=60s --retries=3 \
  CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health/ready', timeout=2)"]
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
3

Build and inspect

podman build --format docker -t hello-model:1.0 .
podman images hello-model
podman history hello-model:1.0 | head -12

Expect about 1.4 GB. The two big layers are the packages and the model. Then change a comment in main.py and rebuild: every step up to the download says Using cache, and the build takes a second or two.

4

Watch it become ready

podman run -d --name api -p 8000:8000 hello-model:1.0
for i in $(seq 1 12); do curl -s -w "   HTTP %{http_code}\n" localhost:8000/health/ready; sleep 0.5; done

You'll see empty lines with HTTP 000, then 503 with "loading", then 200 with "ready".

5

Ask the model

curl -X POST localhost:8000/predict -H 'Content-Type: application/json' -d '{"text": "I love how fast this container starts"}'
curl -X POST localhost:8000/predict -H 'Content-Type: application/json' -d '{"text": "The build broke again and I am annoyed"}'
curl -X POST localhost:8000/predict -H 'Content-Type: application/json' -d '{"text": "It is a container"}'

On the test Mac: positive 0.999, negative 0.999, and positive 0.893 for the neutral sentence. SST-2 was trained with only two labels, so it can't say "neutral"; it picks one, confidently. Knowing what a model was trained for matters as much as serving it well.

6

Memory: measure, then break it

podman stats --no-stream
podman rm -f api
podman run -d --name small --memory 250m hello-model:1.0
sleep 10
podman ps -a --filter name=small
podman inspect small --format 'OOMKilled={{.State.OOMKilled}} exit={{.State.ExitCode}}'
podman rm small

Then try --memory 768m and confirm it's ready.

7

Threads under a CPU limit

podman run -d --name api --cpus 1 -p 8000:8000 hello-model:1.0
sleep 5
for i in $(seq 1 15); do curl -s -X POST localhost:8000/predict -H 'Content-Type: application/json' -d '{"text": "the deployment went smoothly and everyone is happy"}'; echo; done
podman rm -f api

Note the "ms" values. Repeat with -e OMP_NUM_THREADS=1 added to podman run, and compare.

8

Streaming

podman run -d --name api -p 8000:8000 hello-model:1.0
sleep 3
curl -N "localhost:8000/stream?text=streaming works"

Words should appear one by one. Try it once without -N too.

9

Download at start instead

podman rm -f api
podman run -d --name api -p 8000:8000 -e MODEL_DIR=/cache/sst2 -v models:/cache hello-model:1.0
for i in $(seq 1 30); do curl -s localhost:8000/health/ready; echo; sleep 0.5; done

Watch "downloading", then "loading", then "ready". Remove the container, start it again with the same command, and it skips straight to loading.

Clean up

podman rm -f api

11Check yourself

Try answering each question out loud before opening it.

Q1A teammate's CPU-only model service has a 7 GB image. Where would you look first?Show

At which PyTorch build was installed. A plain pip install torch on Linux x86-64 brings about 2 GB of downloads, mostly NVIDIA libraries (several GB installed). The CPU build from download.pytorch.org/whl/cpu is about 200 MB. Then check whether the model repository was downloaded in every format.

Q2Why is download_model.py copied and run before COPY . ., and not after it?Show

Caching. After COPY . ., every code change would invalidate the download step and fetch 268 MB again. Placed before it, with only download_model.py copied first, the download reruns only when that file or a line above it changes.

Q3A model takes 3 minutes to load. The platform's liveness check calls /health/ready and gives up after 60 seconds. What happens?Show

A restart loop: the platform restarts the container before the model finishes loading, every time. Liveness should check /health/live, which answers as soon as the server runs. Readiness should check /health/ready, which only controls whether traffic is sent.

Q4A container exits with code 137 a few seconds after starting, and its logs end in the middle of loading. What do you check, and what's the fix?Show

podman inspect … --format '{{.State.OOMKilled}}'. If it's true, the memory limit is below what the model needs. Measure real usage with podman stats and set the limit with headroom (1.5 to 2 times).

Q5You run the model with 4 uvicorn workers to handle more traffic, and memory jumps from 400 MB to 1.6 GB. Why?Show

Each worker is a separate process that loads its own copy of the model. For large models, prefer one worker per container and more containers, or a model server that shares one copy.

Q6Your model runs twice as slow on a 1-vCPU AWS task as on your laptop, even for single requests. What setting would you try first?Show

OMP_NUM_THREADS=1 (matching the CPU allowance). PyTorch sees all the host's CPUs and starts one thread per CPU, and those threads fight over one CPU's worth of time. On the test Mac this halved the response time.

Q7Streaming works with curl against the container, but through the company's nginx proxy the whole answer arrives at once at the end. Why?Show

nginx buffers responses by default. Disable buffering for that route, for example by sending the X-Accel-Buffering: no header from the app. Always test streaming through the real path.

Q8Your team wants to move a 7B-parameter LLM from a GPU server into ECS Express Mode. What's the problem?Show

ECS Express Mode runs on Fargate, which has no GPUs. It needs ECS or EKS on EC2 GPU instances (or SageMaker), with a host driver new enough for the image's CUDA version.
