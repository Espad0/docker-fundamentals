Part I

Foundations

What a cluster does that one machine cannot, the parts of a container that Kubernetes relies on, and the idea at the centre of everything: desired state, kept true by control loops.

1From one machine to a cluster

Why you need thisEvery object and setting in the rest of the chapter exists to solve one of the four problems in this section. When you know which problem a setting solves, you can work out what it should be for your app.

1.1What one machine gives you

In Lessons 1 to 6 everything ran on one machine. podman run started one container; Compose started a few that could find each other by name. That is enough to develop an app, and for some small services it is enough to run them. But one machine has limits that no command on it can remove:

  • When the machine fails, everything on it stops. A container can be restarted automatically on the same machine, but nothing moves it to another one.
  • Its capacity is fixed. If your app needs more copies than one machine has room for, there is nowhere to put them.
  • Updates are manual. To deploy a new version you stop the old container and start a new one, and for that moment the app is down.
  • Addresses belong to that machine. Other services reach your app at that machine's address. Move the app, and every caller has to change.

1.2Four jobs a cluster does

ClusterA group of machines managed as one, plus the software that decides what runs where.NodeOne machine in a cluster that runs containers.

A cluster is a group of machines, called nodes, managed as one. The software that manages it has four jobs, and they map onto the four limits above:

  1. Placement. Choose a node with enough free memory and CPU for each container (§8.1).
  2. Recovery. Notice when a container or a whole node fails, and start replacements elsewhere (§3.3, §3.6).
  3. Updates. Replace running copies with a new version gradually, without downtime, and stop if the new version is broken (§10).
  4. Discovery. Give each app a fixed name and address that keeps working while its copies move between nodes (§5).

1.3What Kubernetes is, and what it isn't

Kubernetes (k8s)Open-source software that runs a cluster: it places containers on nodes, keeps them running, updates them and connects them. "k8s" is short for it: k, eight letters, s.

Kubernetes is the open-source software most companies use to do those four jobs. It started at Google in 2014 and is now maintained by a large community under the Cloud Native Computing Foundation. A Kubernetes cluster has two halves: the control plane, a few programs that store what should be running and make decisions, and the nodes, where your containers actually run. Section 3 introduces each program.

Running the control plane yourself is hard work, so cloud providers sell it as a service. On AWS that service is Amazon EKS (Elastic Kubernetes Service): AWS runs the control plane, and your company's nodes are EC2 machines. Everything in this chapter works the same on EKS and on the small cluster you'll run on your Mac in the lab, because both run the same Kubernetes.

Three things Kubernetes does not do, so you know where your work stays:

  • It doesn't build images. It runs images that CI built and pushed to a registry (Lesson 6).
  • It doesn't make your app safe to run several copies of, or to stop at any moment. Those are properties of your code, and Part III shows how to check them.
  • It doesn't store your app's data. Containers come and go, and anything worth keeping lives in a database or a storage service such as S3 (§2.2).

1.4Who does what

In most companies a devops or platform team runs the cluster, and developers bring their apps to it. The work splits like this:

You, the app developerThe team that runs the cluster
The app, its Containerfile, and the image CI builds from themThe cluster, its nodes, and a namespace for your app (§4.4)

2Containers: the parts Kubernetes depends on

Why you need thisKubernetes doesn't replace containers; it runs them. Its strangest-looking settings (a user number, a read-only filesystem, a grace period, exit code 137) are about five basic facts of containers. This section explains those five, so the later sections can rely on them.

2.1A container is a process

ProcessA running program. The operating system gives each one a number, its process ID (PID).ContainerA process that the Linux kernel isolates (namespaces) and limits (cgroups).

A container is an ordinary process, a running program, that the Linux kernel treats specially in two ways (Lesson 1):

  • Namespaces isolate it. The process gets its own view of the system: its own list of processes, its own network address, its own files. It can't see other containers.
  • Control groups (cgroups) limit it. The kernel counts how much memory and CPU the process uses, and enforces a ceiling. When a container goes over its memory ceiling, the kernel kills it. This is the mechanism behind Kubernetes' memory limits (§8.2).

On your Mac, these processes run inside Podman's Linux virtual machine. On a cluster, they run on the nodes, which are Linux machines too. A node runs a container runtime (on EKS and in the lab, containerd), which does what podman run does on your Mac.

2.2The image and the filesystem

ImageA read-only stack of filesystem layers plus settings (the command to run, the user, environment variables).Writable layerA thin layer on top of the image where a running container's file changes go. It is deleted with the container.

An image is a stack of read-only filesystem layers, plus settings such as the command to run and the user to run it as (Lesson 2). When a container starts, the runtime puts one thin writable layer on top. Every file the app creates or changes goes into that layer, and the layer is deleted when the container is.

Two consequences shape this whole chapter:

  1. A container's files don't last. Kubernetes replaces containers all the time (new versions, failed nodes, maintenance), so anything the app must keep belongs in a service built for it. sheet-tool keeps its one settings file in S3 for exactly this reason.
  2. The writable layer can be switched off. A read-only root filesystem means the container can't write anywhere except folders mounted for it. That stops an attacker who gets into the container from changing the app or adding tools. Many clusters require it, and §13.5 shows what it breaks if the app doesn't expect it.

2.3Users are numbers

UIDUser ID: the number the Linux kernel uses for a user. Names such as app are only labels in the file /etc/passwd.rootThe user with UID 0, which may do almost anything.

The Linux kernel doesn't know user names. It knows numbers, called user IDs (UIDs). A name such as app is a line in the file /etc/passwd inside the image that maps the name to a number. The user with UID 0 is root, and root may do almost anything.

Lesson 3 made images run as a normal user. For Kubernetes the detail that matters is that the image's USER line is a number, such as USER 10001. A cluster that refuses root containers has to check the user before starting the container, and it can't read /etc/passwd inside your image to translate a name. Section 13.4 shows the exact error.

2.4Signals, process 1 and exit codes

SignalA short message the kernel delivers to a process. SIGTERM (15) asks it to stop; SIGKILL (9) stops it at once and can't be caught.PID 1The first process in a container. Signals it hasn't asked to handle are ignored.

Something outside a process can tell it to stop by sending a signal. Two signals matter here:

  • SIGTERM (signal 15) is a polite request: "please stop". A well-written server catches it, stops accepting new work, finishes what it's doing and exits.
  • SIGKILL (signal 9) can't be caught or ignored. The kernel ends the process immediately, in the middle of whatever it was doing.

Kubernetes stops a container by sending SIGTERM, waiting a grace period (30 seconds unless set otherwise), then sending SIGKILL. Section 9.3 follows that sequence in detail.

The first process in a container has process ID 1, and the kernel treats PID 1 specially: it ignores any signal that the process hasn't installed a handler for. That's why the exec form of CMD matters (Lesson 2). With CMD ["uvicorn", …], uvicorn itself is PID 1 and handles SIGTERM. With the shell form, CMD uvicorn …, PID 1 is /bin/sh, which doesn't pass the signal on, so the app never hears it and is killed when the grace period runs out.

When a process ends, it leaves an exit code, a number from 0 to 255. By convention 0 means success and anything else means failure. When a signal kills a process, the exit code is 128 plus the signal number: 137 is 128 + 9 (SIGKILL), and 143 is 128 + 15 (SIGTERM). You'll see 137 often, because both the out-of-memory killer and the end of a grace period use SIGKILL.

2.5Ports and addresses inside a container

PortA number from 1 to 65535 that picks one program on a machine; an address plus a port picks one program on one machine.0.0.0.0"Listen on every network interface", as opposed to 127.0.0.1, which is only reachable from inside.

A server listens on a port, a number that identifies one program among the many on a machine. Two details from Lesson 2 carry straight into Kubernetes:

  • Listen on 0.0.0.0. Inside a container, 127.0.0.1 (localhost) means the container itself, so a server listening only there can't be reached from anywhere else. Listening on 0.0.0.0 means "on every network interface", which lets traffic from the rest of the cluster in.
  • Use a port above 1024. On Linux, opening a port below 1024 traditionally needs root rights. sheet-tool listens on 8000, so it needs none, which matters when the cluster removes those rights (§13.2).

3Desired state and control loops

Why you need thisThis is the one idea that explains how Kubernetes behaves: why a deleted pod comes back, why a broken release doesn't take the app down, and why "undo" in the cluster isn't the same as undo in Git. Every later section is an application of it.

3.1Two ways to give instructions

ImperativeGiving steps: "start two containers".DeclarativeDescribing the result: "there should be two containers".

There are two ways to tell a system what to do. You can give it steps: "start two containers of sheet-tool". That style is called imperative, and it's how podman run works. Or you can describe the result: "there should always be two containers of sheet-tool, using this image". That style is called declarative.

The difference shows up the moment something changes. After the imperative command has run, nobody remembers what you wanted. If a container dies, the system has no reason to start another. With the declarative description, the wish is stored, so the system can keep comparing it with what's running and act whenever they differ. Kubernetes works this way: you describe the result, and it keeps making it true.

3.2The API server: a database of what should exist

API serverThe front door of the control plane. Every change to the cluster, from you or from Kubernetes' own programs, goes through it.etcdThe database where the API server stores every object.

The description you write is stored as an object: a record with a type (such as Deployment), a name, and its settings. Objects are kept by the API server, a program in the control plane that every other program talks to, in a database called etcd. kubectl, the command you use to work with a cluster, is just a client for the API server: kubectl apply -f file.yaml sends the file's objects to it.

spec, statusThe two halves of an object: what you want, and what Kubernetes last observed.

Most objects have two halves:

  • spec: what you want, written by you. For sheet-tool's Deployment: "2 copies, this image, these settings".
  • status: what is actually true, written by Kubernetes. "2 copies exist, 2 are ready".

3.3Controllers: observe, compare, act

ControllerA program in the control plane that watches one kind of object and keeps acting until reality matches its spec.ReconcileOne pass of a controller: observe, compare, act.

A controller is a program that watches one kind of object and runs the same loop forever:

  1. Observe what exists now.
  2. Compare it with the object's spec.
  3. Act to reduce the difference: create something, delete something, or change something.

One pass of that loop is called reconciling. The important property is that a controller reacts to the current difference, not to individual events. It doesn't matter whether a pod disappeared because it crashed, because its node failed or because you deleted it: the controller sees "2 wanted, 1 exists" and creates one. That's why you can delete a pod to restart it, and why deleting it doesn't make it go away for good.

3.4The scheduler and the kubelet

SchedulerThe control-plane program that picks a node for each new pod.kubeletThe agent on every node that starts the containers of the pods assigned to it, runs their health checks and reports back.

Controllers decide what should exist. Two more programs decide where and make it happen:

  • The scheduler watches for pods that have no node yet, and assigns each one to a node with enough room for what the pod asks for (§8.1).
  • The kubelet is an agent on every node. It watches for pods assigned to its node, tells the container runtime to start their containers, runs their health checks (§6), and writes their status back to the API server.

None of these programs talk to each other directly. Each one reads and writes objects through the API server. This is what makes the design robust: any of them can restart, read the current objects, and carry on.

3.5One kubectl apply, from start to finish

Here is everything that happens when you deploy sheet-tool in the lab (§19), in order:

  1. kubectl sends the objects to the API server, which checks them and stores them in etcd.
  2. The Deployment controller sees a new Deployment and creates a ReplicaSet for it (§4.3 explains why there are two levels).
  3. The ReplicaSet controller sees "2 wanted, 0 exist" and creates two pod objects. They have no node yet.
  4. The scheduler assigns each pod to a node with room for its requests.
  5. The kubelet on that node asks the runtime to start the container, then starts calling its health checks.
  6. When a pod's readiness check passes, it's added to the Service's list of addresses, and requests start reaching it (§5.3).

3.6When a whole node fails

Each kubelet reports to the API server every few seconds. If a node stops reporting, the control plane marks it NotReady. Its pods aren't replaced at once, because a network blip shouldn't move every app: by default they wait 300 seconds, after which the controllers create replacements on healthy nodes.

Recorded · the 300 seconds, in a pod's spec (excerpt)

"key": "node.kubernetes.io/not-ready",
"tolerationSeconds": 300
"key": "node.kubernetes.io/unreachable",
"tolerationSeconds": 300

Kubernetes added these two settings to every sheet-tool pod by itself. They're called tolerations: "this pod tolerates its node being not ready for 300 seconds".

This is the practical reason to run at least two copies of an app, on different nodes. With one copy, a node failure means minutes of downtime; with two, the other copy keeps serving while the replacement is made.

4Objects, labels and namespaces

Why you need thisYour team will send you YAML files, and you'll need to read them line by line. This section explains the shape every object shares, how objects find each other (labels), and how they're grouped (namespaces).

4.1The shape of every object, and enough YAML to read it

YAMLA text format for structured data. Indentation shows nesting; key: value is a field; - starts a list item.

Objects are usually written in YAML, a text format with three rules you need: key: value is a field; indenting lines under a key puts them inside it; and a line starting with - is one item of a list. One file can hold several objects, separated by a line with ---.

Every object starts with the same four fields. Here's sheet-tool's Service, the shortest object it has:

apiVersion: v1             # which version of the API defines this type
kind: Service              # the type of object
metadata:
  name: sheet-tool         # its name, unique for its type in its namespace
  namespace: sheet-tool    # its folder (§4.4)
spec:                      # what you want: the rest depends on the kind
  selector:
    app: sheet-tool
  ports:
    - name: http
      port: 80
      targetPort: http

Two YAML details trip people up. Numbers and text look alike: port: 80 is a number, but an environment variable's value must be text, so a ConfigMap writes MAX_UPLOAD_MB: "10" with quotes. And indentation is meaning: moving a line two spaces left moves it into a different part of the object, often without any error.

4.2Labels and selectors: how objects find each other

LabelA key and a value attached to an object, such as app: sheet-tool.SelectorA condition on labels that picks a set of objects.

Objects don't point at each other by name. Instead, an object carries labels, small key-value pairs such as app: sheet-tool, and another object uses a selector, a condition on labels, to find all objects that match. The Service above selects "all pods with app: sheet-tool", whatever their names are and however many there are. Pods come and go with new names all the time; the label is what stays the same.

4.3Who owns what: Deployment, ReplicaSet, pod

PodOne or more containers that Kubernetes starts together on one node, sharing one network address. sheet-tool's pods have one container each.ReplicaSetKeeps a number of identical pods running.DeploymentManages ReplicaSets, one per version, to roll out changes.

Kubernetes doesn't run containers directly; it runs pods. A pod is one or more containers that are always started together on the same node and share one network address. Most pods, including sheet-tool's, have one container. When this chapter says "a copy of the app", it means one pod.

You don't usually create pods yourself either. Two layers of objects manage them:

  • A ReplicaSet keeps a number of identical pods running. Its controller is the one in Figure 3.1.
  • A Deployment manages ReplicaSets. Each version of your app (each image tag, each change of settings) gets its own ReplicaSet, and the Deployment moves pods from the old ReplicaSet to the new one gradually. That's how updates work without downtime (§10).

Every pod records its owner, and every ReplicaSet records its own:

Recorded · a pod's owner, and its owner's owner

kubectl get -n sheet-tool pod/sheet-tool-58f88959bf-296s8 -o jsonpath='{.metadata.ownerReferences[0].kind}/{.metadata.ownerReferences[0].name}'
ReplicaSet/sheet-tool-58f88959bf      # the pod's owner
Deployment/sheet-tool                 # the ReplicaSet's owner, asked the same way

The pod's name is its ReplicaSet's name plus five random characters, and the ReplicaSet's name is the Deployment's name plus a fingerprint of the pod template. Deleting the Deployment deletes everything it owns; this cleanup is called garbage collection.

4.4Namespaces

NamespaceA named group of objects in a cluster. Not related to the Linux namespaces of §2.1.

A namespace is a named folder of objects inside one cluster. Names only have to be unique within a namespace, so two teams can both have a Service called api. Namespaces are also where rules are attached: who may change what (§12.1), how much CPU and memory the folder may use in total, and how strict the security rules are (§13.3). Teams often get one namespace per app and environment, such as sheet-tool-staging.

Despite the shared name, Kubernetes namespaces have nothing to do with the Linux namespaces that isolate a container (§2.1). One is a folder in a database; the other is a kernel feature.

5How a request reaches your pod

Why you need thisWhen users see an error, it may come from your app or from one of four things in front of it. Knowing the path lets you tell which, and it explains three settings your team will ask you about: the port, the upload size limit and the timeout.

5.1Addresses, ports and names in one page

This section needs four networking terms. Each one is defined here once.

IP addressA number that identifies one network interface, such as 10.244.0.9.DNSThe system that turns names into addresses.
  • An IP address identifies one machine, or one pod, on a network, written as four numbers such as 10.244.0.9. Addresses starting with 10. are private: they only work inside one network, such as the inside of a cluster.
  • A port picks one program at that address (§2.5). 10.244.0.9:8000 means "the program listening on port 8000 at that address".
  • DNS (the Domain Name System) turns a name such as openrouter.ai into an IP address. Your browser asks DNS before every new connection.
  • NAT (network address translation) rewrites addresses as traffic crosses a boundary. It's how a pod with a private address can call the internet: the node, or a gateway, replaces the private address with a public one on the way out (§7.1).

5.2Every pod has its own address, and it changes

Each pod gets its own private IP address inside the cluster. Every pod can reach every other pod's address directly, on any node, unless a network rule forbids it (§7.1). That's simpler than Compose on one machine, where containers shared the machine's ports.

But a pod's address belongs to that pod only. When the pod is replaced, the new one gets a new address:

So nothing should call a pod by its address. Callers need something that stays the same while pods come and go.

5.3Services: a fixed address in front of changing pods

ServiceA fixed name and virtual address that spreads requests over the ready pods its selector picks.EndpointSliceThe list of pod addresses behind a Service, each marked ready or not.kube-proxyA program on each node that turns Service addresses into rules in the node's kernel.

A Service gives a set of pods one fixed address and one name. Three pieces work together:

  1. The Service gets a cluster IP, a virtual address that never changes while the Service exists. sheet-tool's is 10.96.132.195. No machine or pod actually has this address.
  2. A controller keeps an EndpointSlice for the Service: the list of addresses of the pods its selector picks (§4.2), each marked ready or not ready.
  3. On every node, kube-proxy writes rules into the Linux kernel that say: "a connection to 10.96.132.195:80 goes to one of these ready pod addresses, on port 8000". The kernel applies the rule to each new connection, so connections are spread over the pods.

5.4Names inside the cluster

CoreDNSThe DNS server inside the cluster. It answers for Service names.Search domainsSuffixes the system tries to add to a short name before looking it up.

A cluster runs its own DNS server, CoreDNS, which knows every Service. A Service's full name is NAME.NAMESPACE.svc.cluster.local, but inside a pod much shorter names work, because each pod's DNS settings include search domains: suffixes that are tried in turn when a name is short.

So inside the namespace sheet-tool, the name sheet-tool works on its own, because the first search domain turns it into sheet-tool.sheet-tool.svc.cluster.local. To reach a Service in another namespace, add the namespace: the lab's app reaches its S3 stand-in as minio.stand-ins, which the second search domain completes. Every name resolves to the Service's fixed address, never to a pod's.

In depth What ndots:5 does to calls to the internet

ndots:5 means: a name with fewer than five dots is first tried with each search domain added. So openrouter.ai, with one dot, is first looked up as openrouter.ai.sheet-tool.svc.cluster.local, then with the other suffixes, and only then as itself. Each failed try is a quick question to CoreDNS, so it costs a few milliseconds per new connection. Writing the name with a final dot, openrouter.ai., skips the search, but for an app that reuses its connections (as sheet-tool's HTTP client does) the difference doesn't matter.

5.5From the outside in

Load balancerA service with a public or company-network address that forwards connections to several targets.Ingress, GatewayKubernetes objects describing how outside HTTP requests reach Services: by hostname and path.TLS terminationDecrypting HTTPS at the entry point, so the rest of the path is plain HTTP.

A Service's cluster IP only works inside the cluster. Requests from people need a way in, and that way has three parts:

  1. A load balancer with an address people's browsers can reach. On AWS it's usually an Application Load Balancer (ALB), reachable from the internet or only from the company network. DNS maps the app's hostname, such as sheet-tool.internal.example.com, to it.
  2. An Ingress (or its newer replacement, a Gateway with an HTTPRoute): an object that says "requests for this hostname and path go to this Service". A program called an ingress controller (or gateway controller) reads these objects and configures the load balancer or itself.
  3. TLS termination: HTTPS is decrypted at the load balancer or ingress controller, using the certificate for the hostname. From there to your pod the request is plain HTTP, which is why sheet-tool listens on HTTP port 8000.

A detail worth knowing when you read logs: most ingress controllers, and the AWS Load Balancer Controller in its usual setting (target-type: ip), send requests straight to the ready pod addresses they read from the Service's EndpointSlice. They skip the cluster IP, but they follow the same ready list, so §5.3's rule still holds. Calls from inside the cluster go through the cluster IP.

Which ingress controller?

For years the most common one was ingress-nginx. Its maintenance ended in March 2026 and its repository is archived. Teams on EKS usually use the AWS Load Balancer Controller, or a Gateway API implementation. Ask your team which one they use; each has its own settings for upload size and timeouts.

One tool skips this path entirely: kubectl port-forward, which you'll use in the lab, connects your Mac straight to one pod through the API server. It ignores readiness and doesn't spread requests. It's for you to test with, not a model of what users get.

5.6When something fails on the way

502, 503, 504Errors made by a proxy, not by your app: bad answer from upstream, no upstream available, upstream too slow.

Each hop on the path can refuse or fail a request, and the status code tells you which hop it was, if you know the conventions. The load balancer and the ingress controller are proxies: they forward requests to an upstream, the next hop toward your app. A proxy that can't get a good answer from upstream makes up its own error:

6Probes: traffic and restarts

Why you need thisKubernetes can't see inside your app. It decides whether to send requests to a pod, and whether to restart it, from your app's answers to a few HTTP calls. Get those answers wrong and the cluster either sends users to a broken pod or restarts healthy ones in a loop.

6.1Three questions Kubernetes asks your app

ProbeA check the kubelet runs against a container on a schedule: an HTTP request, a TCP connection or a command.

A probe is a check that the kubelet (§3.4) runs against a container on a schedule. For a web app it's usually an HTTP request to a path you choose; any status from 200 to 399 is a pass. There are three kinds, and the difference between them is what happens on failure:

ProbeThe questionWhen it failssheet-tool
StartupHas the app finished starting?Keep waiting, up to a limit; until it passes, the other two aren't askedNot needed: it starts in about a second
ReadinessCan it do its job right now?No traffic: marked not ready in the Service's list. Not restarted./health/ready: can it read its settings from S3?
LivenessIs the process stuck?Restart the container/health/live: does it answer at all?

A startup probe matters for apps that load something big before they can work, such as a model (Lesson 5): without it, a liveness probe would restart the container before it finished loading.

6.2Readiness decides who gets traffic

This is where Part II joins up. A pod whose readiness probe fails is marked ready=false in the Service's EndpointSlice (§5.3); kube-proxy and the ingress controller stop sending it new requests; and when it passes again, it's put back. Nobody has to do anything.

6.3What each probe should check

sheet-tool's two endpoints are short, and each line is a decision:

@app.get("/health/live")
def live():
    return {"status": "ok"}                # checks nothing else

@app.get("/health/ready")
def ready():
    try:
        load_settings(client=s3_check)     # can it read settings.yaml from S3?
    except Exception as error:
        raise HTTPException(503, "Settings storage is unreachable")
    return {"status": "ready"}
  • Liveness checks nothing outside the process. A restart only helps when the process itself is broken. If liveness checked S3, an S3 outage would restart every pod, over and over, and fix nothing.
  • Readiness checks what the app can't work without. sheet-tool can't process a file without its settings, so S3 belongs here. It uses a separate S3 client with a 1-second connect and 2-second read timeout, so the check finishes well within the probe's own timeout.
  • Neither calls OpenRouter. Probes run every 5 to 10 seconds on every pod. Each call to a paid AI API would cost money and use up rate limits, and an OpenRouter outage would make the whole app unready, upload page included, when only the AI step is affected.
Trade-off Should readiness check a dependency at all?

When S3 is down, every pod becomes unready at the same moment, so the Service has no pods and users get errors even on pages that don't need S3. For sheet-tool that's honest: nothing works without its settings. An app that can still do useful work without a dependency should keep reporting ready, and return an error only from the parts that need it. Ask of each dependency: "if this is down, is this pod useless?" Only a yes belongs in readiness.

6.4The timing settings

Each probe has the same five settings. sheet-tool's readiness probe:

readinessProbe:
  httpGet:
    path: /health/ready
    port: http
  periodSeconds: 5        # ask every 5 seconds
  timeoutSeconds: 3       # no answer in 3 seconds counts as a failure
  failureThreshold: 3     # 3 failures in a row before acting
  # successThreshold: 1     one pass to count as ready again (the default)
  # initialDelaySeconds: 0  wait before the first check (the default)

The arithmetic is what matters. With readiness every 5 seconds and 3 failures needed, a pod is marked unready about 15 seconds after S3 disappears. With liveness every 10 seconds and 3 failures, a stuck process is restarted after about 30 seconds. The thresholds are there so that one slow answer doesn't take a pod out of service. The readiness failures in the first second of a new pod (the connection refused lines in §3.5) are harmless: a pod starts unready and becomes ready on its first pass.

6.5Probes come from the node

The kubelet runs httpGet probes itself, from the node, to the pod's address. Your image doesn't need curl or anything else for them. Two consequences:

  • The HEALTHCHECK line from Lesson 3 is ignored by Kubernetes, which uses its own probes. For your Mac, put a healthcheck: in compose.yaml instead (§15.3).
  • The app must listen on 0.0.0.0 (§2.5). A server on 127.0.0.1 fails every probe, because the kubelet's request comes from outside the container.

7Calls going out

Why you need thissheet-tool calls two services outside the cluster on every upload: S3 and OpenRouter. Whether those calls are allowed is your team's decision, and how long they may take decides whether "upload and download in one request" is a workable design at all.

7.1The way out

NetworkPolicyA Kubernetes object that limits which connections a pod may make or accept.EgressTraffic leaving the cluster.HTTPS_PROXYAn environment variable that sends a program's outbound HTTPS through a proxy server.

When sheet-tool calls openrouter.ai, four things happen: CoreDNS looks the name up (§5.4); the connection leaves the pod with its private address; NAT on the node or on a gateway gives it a public address (§5.1); and any rule on the way may allow or block it. Outbound traffic is called egress, and companies often restrict it, in three ways:

  • NetworkPolicy: an object that lists which connections the pods in a namespace may make. Once one applies to a pod, everything not listed is blocked. NetworkPolicies match addresses and labels, not hostnames, so allowing openrouter.ai by name needs an extra product (some network plugins add it).
  • An outbound proxy: all traffic to the internet goes through one server that checks it. Programs find it through the HTTPS_PROXY and NO_PROXY environment variables. sheet-tool's HTTP client, httpx, reads them by itself, so this is a setting, not a code change.
  • Cloud firewall rules outside Kubernetes, which you can't see from the cluster at all.

The lab cluster allows everything, so none of this shows up on your Mac. Ask your team before the first deploy: "can pods in my namespace reach openrouter.ai on port 443, and S3?" The symptom of a blocked call is a timeout, not a clear error.

7.2Every call needs a timeout

TimeoutThe longest a program waits for something before giving up. Connect timeout: for the connection to open. Read timeout: for the next bytes of the answer.

A timeout is the longest a program waits before giving up. Without one, a call to a service that never answers (blocked by a firewall, or stuck) waits forever, and so does the user's request, holding its memory the whole time. sheet-tool sets two kinds on every outside call: a connect timeout, for the connection to open, and a read timeout, for the answer to arrive.

CallConnectReadWhy
S3, normal2 s5 sS3 answers in milliseconds; waiting longer only hides an outage
S3, readiness check1 s2 sMust finish inside the probe's 3-second timeout (§6.4)

7.3The timeout chain, and the design it decides

Idle timeoutHow long a proxy keeps a connection open with no data flowing. The AWS ALB default is 60 seconds.

A request passes through several layers, and each has its own timeout: the browser, the load balancer, the ingress, and your app's own limits. The request survives only if it finishes before the shortest of them. An AWS Application Load Balancer, for example, closes a connection on which no data has moved for 60 seconds, its idle timeout. sheet-tool sends nothing back until the whole file is processed, so for the load balancer the entire processing time is silence.

sheet-tool asks the model about one row at a time, so its processing time is roughly rows × seconds per answer. With 500 rows and 2 seconds per answer, that's over 16 minutes: no load balancer setting makes that a good single request. Figure 7.1 lets you try your own numbers.

If realistic files take more than a minute or two, the design has to change: the browser starts a job and gets an ID back, checks on it, and downloads the result later. That needs the result stored somewhere every pod can read, such as S3, because the download request may reach a different pod than the upload did (§5.3). It's a change in the app, so find out early by measuring with real data (§17).

Resources and lifecycle

8CPU and memory

Why you need this"How much memory and CPU does it need?" is the first question your team will ask, and the two numbers you give become the most consequential lines in the Deployment. Too low, and the pod is killed in the middle of a user's upload. Too high, and the pod costs more than it should, or doesn't fit on any node.

8.1Requests: what the scheduler counts

RequestThe CPU and memory a container is guaranteed, and what the scheduler reserves on a node for it.m, Mi, GiCPU in thousandths of a core (250m = a quarter core); memory in binary units (1 Mi = 1,048,576 bytes).AllocatableWhat a node offers to pods, after what the system itself needs.

Each container can state a request: the CPU and memory it needs to work. CPU is counted in cores and thousandths of a core, so 250m is a quarter of a core. Memory is counted in binary units: 512Mi is 512 mebibytes, and a mebibyte is 1,048,576 bytes.

The scheduler (§3.4) uses requests, and only requests, to place pods. Each node has an allocatable amount of CPU and memory. The scheduler adds up the requests of the pods already on a node, and a new pod only goes there if its request fits in what's left. It doesn't look at how much the pods actually use.

8.2Limits: CPU is slowed, memory is killed

LimitThe most CPU or memory a container may use. Enforced by the kernel's cgroups (§2.1).OOMKilled"Out of memory, killed": the container went over its memory limit and the kernel ended it with SIGKILL.

A limit is the ceiling: the most a container may use. Limits are enforced by the Linux kernel's control groups (§2.1), and the two resources behave completely differently at the ceiling:

  • CPU is slowed down. A container at its CPU limit simply gets less processor time. Requests take longer, but nothing breaks.
  • Memory is fatal. Memory can't be taken back from a running program, so a container that goes over its memory limit is killed by the kernel's out-of-memory killer with SIGKILL: exit code 137 (§2.4), reason OOMKilled. Kubernetes restarts it, but whatever it was doing is lost.

Requests and limits needn't be equal. A request below the limit means "this is what I normally need, but let me burst above it". The scheduler only guarantees the request, so a node can have more limits than memory; the recorded node above has 2388 Mi of limits on 3.5 GiB, which is fine as long as the pods don't all burst at once.

8.3Quality of service, and who is evicted first

QoS classGuaranteed, Burstable or BestEffort, decided from a pod's requests and limits. It sets the order in which pods are evicted when a node runs short.EvictionThe kubelet stopping a pod to save its node.

When a whole node runs low on memory, the kubelet doesn't wait for the kernel; it starts evicting pods, stopping them so the controllers recreate them elsewhere. Which pods go first depends on a quality-of-service class that Kubernetes derives from requests and limits:

ClassWhenEvicted
BestEffortNo requests or limits at allFirst
BurstableSome requests or limits, not all equalNext, starting with pods using most above their request
GuaranteedEvery container has CPU and memory limits equal to its requestsLast

sheet-tool requests 512 Mi and is limited to 1 Gi, so it's Burstable, which kubectl get pod -o jsonpath='{.status.qosClass}' confirms in the lab. It normally uses about 66 Mi, far below its request, so it's among the last Burstable pods to go. A pod with no requests is first, which is one more reason never to leave them out.

8.4Measure instead of guessing

The kernel keeps a running maximum for every container: the file /sys/fs/cgroup/memory.peak holds the most memory the container has used since it started. Restart the container, send it the worst case, and read the file. For sheet-tool the worst case is the largest file it accepts (10 MB) filled with text that barely compresses, because openpyxl holds the whole workbook in memory. Two rules follow. Memory is set by the largest input you accept, not by the typical one. And it adds up with concurrency: two large uploads at once need twice the working memory. sheet-tool therefore requests 512 Mi (one large upload with room to spare) and is limited to 1 Gi (two at once).

CPU is simpler. One limit-size upload took 4.1 seconds, and two at once took 8 seconds each: Python runs one thread of Python code at a time, so the app never uses more than one core. A CPU limit of 1 costs it nothing, and a request of 250m is enough because most of its time is spent waiting for the model.

Why you need thisEvery deploy stops your pods, and every crash restarts one. Whether a user notices depends on a few seconds at the start and at the end of a pod's life. This section follows both, and explains every status word you'll see in kubectl get pods.

9.2Crashes and restarts

When an app's process exits, the kubelet restarts the container on the same node; that's the pod's restart policy, and for Deployments it is always "restart". If the app keeps crashing, the kubelet waits longer between attempts: about 10 seconds, then 20, then 40, doubling up to five minutes. This growing wait is the back-off, and a pod in it is said to be in a crash loop.

And make your app fail fast at start on missing settings, as sheet-tool does, so a configuration mistake shows up during the deploy rather than on the first user's upload.

9.3How a pod is stopped

Grace periodterminationGracePeriodSeconds: how long Kubernetes waits after asking a pod to stop before killing it. Default 30.preStop hookAn action the kubelet runs in the container before sending SIGTERM.

Pods are stopped all the time: by every new version (§10), by scaling down, by maintenance on a node (§10.5), and when you delete one. Each time the same sequence runs:

  1. The pod is marked Terminating, and the grace period starts: terminationGracePeriodSeconds, 30 unless set, 90 for sheet-tool.
  2. At the same moment, two things start in parallel. The pod is marked not ready in its Service's EndpointSlice, and that news spreads to kube-proxy on every node and to the ingress controller. And the kubelet on the pod's node starts stopping the container.
  3. The kubelet runs the container's preStop hook, if it has one. sheet-tool's simply waits 5 seconds.
  4. The kubelet sends SIGTERM (§2.4). uvicorn stops accepting new connections, finishes the requests in progress (for up to 60 seconds, its --timeout-graceful-shutdown), and exits.
  5. If the container is still running when the grace period ends, the kubelet sends SIGKILL.

The grace period counts from step 1, so the preStop pause is part of it.

9.4The race at the end, and why preStop pauses

Step 2 hides a race. Telling every node and the ingress that a pod is leaving takes a moment, and the SIGTERM can arrive before they all know. In that moment a new request can be sent to a pod that has just stopped accepting connections, and the user gets an error. The preStop pause delays SIGTERM by 5 seconds, which is enough for the news to arrive everywhere first; requests already in progress aren't affected by the pause at all.

Recorded · a client inside the cluster calling the Service every 0.05 s while both pods were replaced

{200: 605}                                          with the 5-second preStop (603 and 592 in two more runs, all 200)
{200: 637, 'ConnectError': 4, 'ConnectTimeout': 1}  without it (7 and 9 errors in two more runs)

9.5Stopping in the middle of an upload

The other half of a clean stop is finishing what's in progress. That needs three things to line up: the app receives SIGTERM (exec-form CMD, §2.4); the app waits for running requests (uvicorn's graceful shutdown); and the grace period is longer than the preStop pause plus the longest request.

10New versions, rollbacks and maintenance

Why you need thisEvery deploy is a rolling update, and every rollback is one in reverse. Knowing how they work explains why a broken release usually hurts nobody, why "undo" in the cluster can be undone by the next deploy, and what the settings in the Deployment's strategy block do.

10.1A new version is a new ReplicaSet

Pod templateThe part of a Deployment that describes its pods: image, settings, probes. Any change to it is a new version.RevisionA numbered version of a Deployment, kept as an old ReplicaSet with zero pods.

The part of a Deployment that describes its pods is the pod template: the image, the environment, the probes, the limits. Changing anything in it, even one setting, is a new version. The Deployment controller then creates a new ReplicaSet for the new template (§4.3) and moves pods from the old ReplicaSet to the new one. The old ReplicaSet is kept, scaled to zero, as a revision you can go back to; ten are kept by default.

10.2How fast pods are replaced: maxSurge and maxUnavailable

maxSurgeHow many pods above the desired number may exist during an update.maxUnavailableHow many pods below the desired number may be not ready during an update.

Two settings in the Deployment's strategy control a rolling update:

  • maxSurge: how many extra pods may exist during the update. With 1, Kubernetes may run 3 pods for a Deployment of 2.
  • maxUnavailable: how many pods may be missing (not ready) during the update. With 0, there are always at least 2 ready pods.

sheet-tool uses maxSurge: 1 and maxUnavailable: 0: start one new pod, wait until it's ready, remove one old pod, repeat. It's the safest choice for a small Deployment: capacity never drops. Both can't be 0, because then nothing could ever change:

Kubernetes doesn't undo a stuck rollout by itself. After progressDeadlineSeconds (600 seconds by default) it marks the Deployment as failed, which deploy tools can react to, but the old pods simply keep running until someone fixes the release.

10.4Going back

kubectl rollout undo makes the previous revision current again: its ReplicaSet scales up and the broken one scales down. It works at once, but it changes only the cluster, not the files the cluster was deployed from:

Recorded · the warning that comes with rollout undo

Warning: resource deployments/sheet-tool was previously managed with 'kubectl apply'. Rolling back will not update the kubectl.kubernetes.io/last-applied-configuration annotation, which may cause unexpected behavior on future 'kubectl apply' operations. …
deployment.apps/sheet-tool rolled back

In plain words: the files in Git still name the broken tag, so the next deploy from Git brings it back. Treat rollout undo as the emergency button, and make the real fix the way the team deploys: put the previous tag back in the files, usually by reverting a commit (§14.2).

10.5Planned interruptions and the PodDisruptionBudget

DrainMoving every pod off a node before maintenance.PodDisruptionBudget (PDB)A rule such as "keep at least 1 pod of this app" that drains must respect.

Nodes need maintenance: security updates, new machine types, scaling the cluster down. Before that, the team drains the node: its pods are stopped, with the sequence from §9.3, and recreated elsewhere. If both of an app's pods happen to be on that node, both could go at once. A PodDisruptionBudget prevents it: sheet-tool's says minAvailable: 1, so a drain waits until another pod is ready before taking the second. It only applies to planned interruptions like drains; a node that crashes doesn't ask permission (§3.6).

11Settings and secrets

Why you need thisThe same image runs in staging and production, with different settings and different keys. This section shows where those come from, what "Secret" does and doesn't protect, and the one surprise everyone meets: changing a setting doesn't change running pods.

11.1One image, many environments

Lesson 3 set a rule: nothing that differs between environments goes into the image, and nothing secret ever does. The app reads its settings from environment variables when it starts. sheet-tool reads six: S3_BUCKET, S3_KEY, AWS_REGION, OPENROUTER_BASE_URL, MAX_UPLOAD_MB and LOG_LEVEL, plus one secret, OPENROUTER_API_KEY. Then the image that passed the tests in staging can be promoted to production unchanged: only the values around it change.

11.2ConfigMaps and Secrets

ConfigMapAn object holding settings as key-value text.SecretThe same, for sensitive values: kept apart, with separate access rules. Its values are base64-encoded, not encrypted.base64A way to write any bytes as plain letters. Anyone can decode it.

In Kubernetes, settings live in two kinds of objects. A ConfigMap holds ordinary settings, and a Secret holds sensitive ones. The Deployment turns every key of both into environment variables with envFrom (§18), so the app just reads os.environ, exactly as on your Mac.

The name "Secret" promises more than the object does. Its values are stored base64-encoded, which is a way of writing bytes as letters, not a way of hiding them:

Recorded · reading the lab's Secret

kubectl get secret sheet-tool-secrets -n sheet-tool -o jsonpath='{.data.OPENROUTER_API_KEY}'
ZmFrZS1vcGVucm91dGVyLWtleQ==
… | base64 -d
fake-openrouter-key

What actually protects a Secret is around it: access rules that let fewer people read Secrets than ConfigMaps (§12.1), and encryption at rest, a cluster setting that encrypts Secrets in etcd, which managed clusters such as EKS can turn on. Two habits follow: never write a Secret's real value in a file in Git, and treat anyone who can read Secrets in a namespace as someone who has the keys.

11.3A changed setting needs a restart

Environment variables are copied into a process once, when it starts. Changing a ConfigMap or a Secret therefore changes nothing in pods that are already running:

The running pods kept the old value until kubectl rollout restart replaced them, through the same rolling update as a new version (§10).

Deploy tools usually handle this for you. Kustomize can generate ConfigMaps with a fingerprint of their content in the name, and Helm charts often put a fingerprint in the pod template, so any change to a setting changes the pod template and starts a rollout. If your team's setup doesn't, remember the restart.

11.4Where real secrets live

Secrets ManagerAWS's service for storing secrets, with access controlled by IAM and rotation.External Secrets OperatorA program in the cluster that copies values from a secret store into Kubernetes Secrets and keeps them current.

In the lab, sheet-tool's Secret is a file with a fake value. In production the real OpenRouter key is kept in a secret store, usually AWS Secrets Manager, and a program in the cluster copies it into a Kubernetes Secret. A common one is the External Secrets Operator, configured with an object like this:

apiVersion: external-secrets.io/v1

  secretStoreRef:
    kind: ClusterSecretStore

    name: sheet-tool-secrets           # the Secret the Deployment reads

"Read sheet-tool/openrouter-api-key from Secrets Manager and keep the Secret sheet-tool-secrets up to date with it." The Deployment reads that Secret as before, and nothing secret is in Git. Note that the refreshed value still only reaches the app on its next restart (§11.3).

12Who the pod is: identity and permissions

Why you need thissheet-tool reads and writes a file in S3. On your Mac it uses keys from a file; in the cluster it must not have keys at all. This section explains how a pod proves who it is, to Kubernetes and to AWS, and the smallest permission it needs.

12.1People, ServiceAccounts and RBAC

ServiceAccountAn identity for programs running in pods, as opposed to people.RBACRole-based access control: Roles list allowed actions, RoleBindings give a Role to a person, group or ServiceAccount.

A cluster has two kinds of identities. People sign in, usually through the company's identity provider, and use kubectl. Programs running in pods use a ServiceAccount, an identity object that lives in a namespace. Every pod runs as one; sheet-tool's is called sheet-tool.

What each identity may do in the cluster is set by RBAC (role-based access control). A Role lists actions on kinds of objects, such as "read pods and their logs in this namespace", and a RoleBinding gives a Role to a person, a group or a ServiceAccount. Kubernetes ships a few ready-made roles; the one called view allows reading almost everything in a namespace except Secrets, which is usually what a developer needs to debug their app. That's a good thing to ask for (§20.3).

sheet-tool never calls the Kubernetes API, so its ServiceAccount needs no Kubernetes permissions at all. Its Deployment even sets automountServiceAccountToken: false, so the pod doesn't receive the token it would need to try. Its ServiceAccount exists for a different reason: AWS.

12.2AWS without keys

IAM roleAn AWS identity with permissions but no long-lived keys. Whoever is allowed to assume it gets temporary credentials.IRSA, Pod IdentityTwo EKS features that let the pods of one ServiceAccount assume one IAM role.

On your Mac, the AWS SDK found MinIO's keys in environment variables. In production, putting long-lived AWS keys into a Secret would mean keys to rotate and keys that can leak. EKS has two features that remove them, and both connect a ServiceAccount to an IAM role, an AWS identity that has permissions but no permanent keys:

  • IRSA (IAM roles for service accounts): the ServiceAccount carries an annotation naming the role. EKS gives each pod a signed token that says "I run as ServiceAccount sheet-tool in namespace sheet-tool", and the SDK trades that token with AWS for temporary credentials.
  • EKS Pod Identity: the newer way. The team links the role to the ServiceAccount in AWS, with no annotation, and an agent on each node hands the SDK temporary credentials.

Either way, sheet-tool's code doesn't change: boto3.client("s3") looks for credentials in a fixed order (environment variables first, then the token or agent that IRSA or Pod Identity set up) and uses what it finds. In the lab it finds MinIO's keys; on EKS it finds the role. That's why the production files have no AWS keys at all (§14.1).

12.3The smallest permission for one file

The role should allow exactly what the app does and nothing more, a principle called least privilege. sheet-tool reads and writes one object, so its IAM policy needs three actions:

{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": "arn:aws:s3:::example-sheet-tool-production/settings.yaml" },
    { "Effect": "Allow", "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::example-sheet-tool-production" }
  ]
}

ListBucket looks unnecessary, but without it S3 answers "access denied" instead of "no such file" when settings.yaml doesn't exist yet. S3 does this on purpose, so that someone without permission can't find out which files exist. sheet-tool's "nothing saved yet, use the defaults" path depends on getting "no such file", so it needs the permission. (This policy needs AWS to test; it wasn't run for this chapter.)

13Container security

Why you need thisMany clusters refuse to start a container that doesn't meet a security standard, and the error appears at deploy time, in a cluster you can't easily look into. This section explains each rule, so your image meets them before it gets there.

13.1Why the defaults are dangerous

By default, a container runs as whatever user the image says, which is root for most base images, with a set of Linux privileges, and with a writable filesystem. If an attacker finds a flaw in your app, they get all of that. Root inside a container isn't root on the node, but it's much closer: a bug in the kernel or a mistake in the setup can let it out, and a writable filesystem lets the attacker install tools. Each rule below takes away one of those footholds. None of them limits what a normal web app needs to do.

13.2The securityContext, field by field

CapabilityOne piece of root's power, such as binding to ports below 1024 (NET_BIND_SERVICE) or changing network settings (NET_ADMIN).setuidA file flag that makes a program run as its owner, often root, whoever starts it.seccompA kernel filter that limits which system calls a process may make.

A Deployment sets these rules in two securityContext blocks, one for the whole pod and one per container. sheet-tool's, together:

13.3Pod Security Standards: the cluster enforces them

Pod Security StandardsThree levels of rules for pods: privileged (none), baseline, restricted.AdmissionThe API server's checks on an object before it's stored. A refused object is never created.

Kubernetes defines three Pod Security Standards: privileged (no rules), baseline (blocks the known ways out of a container, such as sharing the node's network or files) and restricted (baseline plus runAsNonRoot, no privilege escalation, all capabilities dropped and the seccomp filter from §13.2; it doesn't require a read-only filesystem). A namespace chooses a level with a label, and the API server checks every new pod against it before storing it. This check is called admission, and a pod that fails it is never created:

Admission checks pods, and with a Deployment the pods are created later, by the ReplicaSet. So a Deployment that breaks the rules is still created. kubectl prints a warning, but the Deployment then sits at 0/1 with no pods, and the refusal itself is in the ReplicaSet's events:

13.4Why the image's user must be a number

Admission only reads the pod's settings. A second check happens on the node, when the kubelet is about to start the container: with runAsNonRoot: true and no runAsUser, it reads the image's USER to prove the container won't be root. As §2.3 explained, it can only check a number:

With readOnlyRootFilesystem: true, an app can write only to folders mounted for it. sheet-tool writes in two places that aren't in its own code: the upload parser buffers uploads over 1 MB to a temporary file, and openpyxl writes a temporary file every time it saves a workbook. Why you need thisYour team won't run kubectl apply by hand in production. This section explains how one set of files serves several environments, how a commit becomes running pods, which pieces the platform team runs around your app, and the storage decision in front of sheet-tool.

14.2From a push to running pods

GitOpsKeeping the desired state of a cluster in a Git repository, with a program in the cluster that applies whatever is there.
  1. You push to GitLab. CI builds the image and pushes it to the registry, tagged with the commit (Lesson 6).
  2. A deploy step puts that tag into the environment's files. Two setups are common:
    • CI deploys: a pipeline job runs kubectl apply -k or helm upgrade against the cluster.
    • GitOps: CI only commits the new tag to a repository of deployment files. Argo CD or Flux, running inside the cluster, notices and applies it. This is desired state (§3) one level up: Git holds the wish, and a controller keeps the cluster matching it.
  3. Staging first; production after a check, often a manual button in the pipeline.
  4. The Deployment rolls the new version out (§10) and stops if it never becomes ready.

A rollback is the same path with the previous tag, usually a reverted commit. With GitOps that's the only kind that lasts: a manual kubectl rollout undo is overwritten the next time the controller syncs (§10.4).

        if error.response["Error"]["Code"] == "NoSuchKey":
            return Settings()  # nothing saved yet
        raise
    return Settings(**(yaml.safe_load(body) or {}))

    except (BotoCoreError, ClientError) as error:

def save_settings(settings: Settings):
    body = yaml.safe_dump(settings.model_dump(), sort_keys=False).encode()
    s3.put_object(Bucket=S3_BUCKET, Key=S3_KEY, Body=body, ContentType="application/yaml")

    response = ai.post("/chat/completions", json={"model": model, "messages": [{"role": "user", "content": prompt}]})
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"].strip()

@app.post("/process")
def process(file: UploadFile):
    if not (file.filename or "").lower().endswith(".xlsx"):
        raise HTTPException(415, "Upload an .xlsx file")
    data = file.file.read(MAX_UPLOAD_BYTES + 1)
    if len(data) > MAX_UPLOAD_BYTES:
        raise HTTPException(413, f"File is larger than {MAX_UPLOAD_MB:g} MB")

    settings = settings_or_503()
    try:
        workbook = load_workbook(io.BytesIO(data))
    except Exception:
        raise HTTPException(400, "Not a valid .xlsx file")
    sheet = workbook.active
    rows = sheet.max_row - 1
    if rows > settings.max_rows:
        raise HTTPException(413, f"{rows} rows; the limit is {settings.max_rows}")

    started = time.monotonic()
    answer_column = sheet.max_column + 1
    sheet.cell(row=1, column=answer_column, value="AI answer")
    try:
        for row in range(2, sheet.max_row + 1):
            text = sheet.cell(row=row, column=1).value
            if text is not None:
                prompt = settings.prompt.replace("{text}", str(text))
                sheet.cell(row=row, column=answer_column, value=ask_ai(settings.model, prompt))
    except httpx.HTTPError as error:
        log.error("AI call failed: %r", error)
        raise HTTPException(502, "The AI service failed; try again later")

    output = io.BytesIO()
    workbook.save(output)
    # Log sizes and timings, never file contents or keys.
    log.info("processed rows=%d bytes_in=%d seconds=%.1f", rows, len(data), time.monotonic() - started)

    # The file name comes from the user: keep only safe characters before putting it in a header.
    safe_name = re.sub(r"[^A-Za-z0-9._-]", "_", file.filename)
    return Response(
        output.getvalue(),
        media_type="application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        headers={"Content-Disposition": f'attachment; filename="processed-{safe_name}"'},
    )

"""A fake OpenRouter for local testing: same URL path and JSON shape, no real model, no cost.

Only the Python standard library, so it runs in the plain python image.
"""
import json
import os
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

DELAY = float(os.getenv("FAKE_DELAY", "0.05"))  # seconds per answer, to imitate a real model


class Handler(BaseHTTPRequestHandler):
    def reply(self, status, body):
        data = json.dumps(body).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        self.reply(200, {"status": "ok"})

    def do_POST(self):
        if self.path != "/api/v1/chat/completions":
            return self.reply(404, {"error": "not found"})
        if not self.headers.get("Authorization", "").startswith("Bearer "):
            return self.reply(401, {"error": "missing API key"})
        request = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        prompt = request["messages"][-1]["content"]
        time.sleep(DELAY)
        answer = f"fake answer ({len(prompt.split())} words in)"
        self.reply(200, {"model": request["model"], "choices": [{"message": {"role": "assistant", "content": answer}}]})


ThreadingHTTPServer(("0.0.0.0", 8080), Handler).serve_forever()

class Settings(BaseModel):
    model: str = "openai/gpt-4o-mini"
    prompt: str = "Summarise in five words: {text}"
    max_rows: int = Field(500, ge=1, le=5000)


def load_settings(client=s3) -> Settings:
    try:
        body = client.get_object(Bucket=S3_BUCKET, Key=S3_KEY)["Body"].read()
    except ClientError as error:
        if error.response["Error"]["Code"] == "NoSuchKey":
            return Settings()  # nothing saved yet
        raise
    return Settings(**(yaml.safe_load(body) or {}))


def settings_or_503() -> Settings:
    try:
        return load_settings()
    except (BotoCoreError, ClientError) as error:
        log.error("settings storage failed: %r", error)
        raise HTTPException(503, "Settings storage is unreachable")


def save_settings(settings: Settings):
    body = yaml.safe_dump(settings.model_dump(), sort_keys=False).encode()
    s3.put_object(Bucket=S3_BUCKET, Key=S3_KEY, Body=body, ContentType="application/yaml")


def ask_ai(model: str, prompt: str) -> str:
    response = ai.post("/chat/completions", json={"model": model, "messages": [{"role": "user", "content": prompt}]})
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"].strip()

    # Refuse a too-large upload before reading it. The ingress should have its own limit too.

@app.post("/process")
def process(file: UploadFile):
    if not (file.filename or "").lower().endswith(".xlsx"):
        raise HTTPException(415, "Upload an .xlsx file")
    data = file.file.read(MAX_UPLOAD_BYTES + 1)
    if len(data) > MAX_UPLOAD_BYTES:
        raise HTTPException(413, f"File is larger than {MAX_UPLOAD_MB:g} MB")

    settings = settings_or_503()
    try:
        workbook = load_workbook(io.BytesIO(data))
    except Exception:
        raise HTTPException(400, "Not a valid .xlsx file")
    sheet = workbook.active
    rows = sheet.max_row - 1
    if rows > settings.max_rows:
        raise HTTPException(413, f"{rows} rows; the limit is {settings.max_rows}")

    started = time.monotonic()
    answer_column = sheet.max_column + 1
    sheet.cell(row=1, column=answer_column, value="AI answer")
    try:
        for row in range(2, sheet.max_row + 1):
            text = sheet.cell(row=row, column=1).value
            if text is not None:
                prompt = settings.prompt.replace("{text}", str(text))
                sheet.cell(row=row, column=answer_column, value=ask_ai(settings.model, prompt))
    except httpx.HTTPError as error:
        log.error("AI call failed: %r", error)
        raise HTTPException(502, "The AI service failed; try again later")

    output = io.BytesIO()
    workbook.save(output)
    # Log sizes and timings, never file contents or keys.
    log.info("processed rows=%d bytes_in=%d seconds=%.1f", rows, len(data), time.monotonic() - started)

    # The file name comes from the user: keep only safe characters before putting it in a header.
    safe_name = re.sub(r"[^A-Za-z0-9._-]", "_", file.filename)
    return Response(
        output.getvalue(),
        media_type="application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        headers={"Content-Disposition": f'attachment; filename="processed-{safe_name}"'},
    )


@app.get("/settings")
def get_settings() -> Settings:
    return settings_or_503()


@app.put("/settings")
def put_settings(settings: Settings) -> Settings:
    try:
        save_settings(settings)
    except (BotoCoreError, ClientError) as error:
        log.error("settings storage failed: %r", error)
        raise HTTPException(503, "Settings storage is unreachable")
    log.info("settings saved model=%s max_rows=%d", settings.model, settings.max_rows)

@app.get("/health/live")
def live():
    # "The process is running and answering." Checks nothing else, so a broken S3 never causes restarts.
    return {"status": "ok"}


@app.get("/health/ready")
def ready():
    # "I can do my job right now." The app can't work without its settings, so check that S3 answers.

        load_settings(client=s3_check)
    except Exception as error:
        log.warning("not ready: %r", error)
        raise HTTPException(503, "Settings storage is unreachable")

20.3Questions, both ways

Questions they may ask you, with sheet-tool's answers

"Is it stateless? Can we run three copies, or scale it automatically?"

Yes. Each upload is handled within one request, and the only lasting data is settings.yaml in S3. Any pod can serve any user, so no sticky sessions. Scaling on CPU works, since processing is CPU-bound (§8.4).

"Does it need a persistent volume?"

No. Settings are in S3, and /tmp only holds temporary files during a request, so an emptyDir is enough. A volume would make several replicas harder, because an ordinary EBS-backed volume attaches to one node at a time.

"What happens when S3 is down? When OpenRouter is down?"

S3 down: readiness fails, the pods get no traffic, and they come back by themselves; no restarts (§6.2). OpenRouter down: the pods stay ready, and /process answers 502 "The AI service failed; try again later" after its timeout. Probes never call OpenRouter (§6.3).

"Why 90 seconds of grace? The default is 30."

So an upload in progress can finish during a deploy: up to 60 seconds of uvicorn's graceful shutdown, plus the 5-second preStop pause, plus margin. With 10 seconds, uploads were cut off (§9.5). If real requests are shorter, it can come down.

"Does it need root, extra capabilities or host access?"

No. It runs as user 10001 with every capability dropped, a read-only root filesystem and the default seccomp profile, and it was tested in a namespace set to restricted (§13).

"How do we know a deploy worked?"

kubectl rollout status finishes only when every new pod is ready, which means it can reach S3 (§10.3). After that, GET /health/ready through the real hostname and one small upload in staging.

      21Chapter summary

      1. A cluster does four jobs one machine can't: placement, recovery, updates and discovery. Kubernetes does them with a control plane and nodes (§1).
      2. A container is an isolated, limited process. Its files vanish with it, its user is a number, it's stopped with SIGTERM and then SIGKILL, and an exit code of 128 + n means signal n killed it (§2).
      3. You describe desired state in objects; the API server stores them; controllers keep comparing spec with reality and act on the difference, whatever caused it (§3).
      4. The scheduler picks a node for each pod by its requests; the kubelet on that node starts the containers and runs the probes (§3.4).
      5. Objects find each other by labels and selectors. A Deployment owns one ReplicaSet per version, and each ReplicaSet owns its pods (§4).
      6. Pods have their own addresses, which change. A Service gives them a fixed address and a DNS name, and sends connections only to ready pods listed in its EndpointSlice (§5).
      7. From outside, a load balancer and an Ingress or Gateway bring requests in and end HTTPS. 502, 503 and 504 are made by proxies on the way; 413 can be the app's or the ingress's (§5.6).
      8. Readiness failing means no traffic; liveness failing means a restart. Liveness checks only the process; readiness checks what the app can't work without; neither calls paid APIs (§6).
      9. Every outside call needs a timeout, and a request must finish before the shortest timeout on its path. Long processing in one request may need a different design (§7).
      10. Requests decide placement; limits are enforced by the kernel: CPU is slowed, memory over the limit is OOMKilled. Set memory from the largest accepted input times concurrency, measured with memory.peak (§8).
      11. A pod is stopped by: marked terminating, removed from routing and, in parallel, preStop, then SIGTERM, then SIGKILL at the end of the grace period. A short preStop pause closes the race; the grace period must cover the longest request (§9).
      12. A new version is a new ReplicaSet. maxSurge and maxUnavailable set the pace, and readiness stops a broken release from replacing anything. rollout undo is an emergency button; the lasting fix goes through Git (§10).
      13. Settings come from ConfigMaps and Secrets as environment variables, read at start, so changes need a restart. A Secret is only base64; its protection is access rules and encryption at rest (§11).
      14. Pods run as a ServiceAccount. On EKS, IRSA or Pod Identity link it to an IAM role, so the app needs no AWS keys; give the role the least it needs (§12).
      15. The restricted Pod Security level requires non-root, no privilege escalation, no capabilities and the seccomp filter, and refuses pods at admission. The image's USER must be a number; a read-only root needs a mounted /tmp (§13).
      16. One set of files serves every environment through Kustomize or Helm, and new versions arrive through CI or GitOps (§14). You hand over an image and a sheet of facts (§20).
