Kubernetes, the big picture

You may never set up a Kubernetes cluster, but you'll likely read Kubernetes files: in your team's repositories, in open-source projects, in deployment reviews. Almost every idea in them is something you've already learned under another name. This lesson maps them, and lets you run a real Kubernetes file on your Mac with Podman.

Reading about 35 minLab about 25 minUses hello-ai:2.0 from Lesson 4Outputs from the test Mac, autumn 2026

By the end you should be able to

  • explain what Kubernetes does that a single podman run doesn't
  • map Pods, Deployments, Services, ConfigMaps, Secrets and probes to what you know from Lessons 1–5
  • read a Deployment file and say what it will do
  • run Kubernetes YAML locally with podman kube play, and know where Podman differs
  • recognise the everyday kubectl commands and what EKS adds on AWS

01Why Kubernetes exists

Everything so far ran on one machine. Production usually means many machines and many containers, and someone has to answer questions like these, all day, automatically:

  • Which machine should this container run on, given the CPU and memory it needs?
  • A container crashed, or a whole machine died. What replaces it, and where?
  • We have a new image. How do we replace 10 running copies without downtime, and undo it if it's broken?
  • How do the other services find this one, when its copies keep moving between machines?

Kubernetes answers them. The key idea is desired state. You don't say "start 3 containers"; you write "there should always be 3 copies of this, using this image". Kubernetes' controllers keep comparing that with reality and fix any difference. If a copy dies, reality is 2, desired is 3, so a controller starts one. You change the image in the file, and a controller rolls it out.

ECS Express Mode and Cloudflare Containers (Lesson 6) do the same work for you, with fewer choices. Kubernetes gives you every choice, and every responsibility that comes with it.

03Reading a Deployment

Kubernetes objects are written in YAML. Several can share a file, separated by ---. Each starts with the same three keys: apiVersion and kind (what sort of object) and metadata (its name and labels). Here's hello-ai as a real cluster would run it:

hello-ai-k8s.yaml4 objects
apiVersion: v1 kind: ConfigMap metadata: name: hello-ai-config data: MODEL_NAME: keyword-sentiment-v1

Settings, stored in the cluster under the name hello-ai-config.

apiVersion: v1 kind: Secret metadata: name: hello-ai-secrets type: Opaque stringData: API_KEY: not-a-real-key

A secret. Written into the file here to keep the example complete; in real repositories the value comes from a secret manager and never sits in Git.

apiVersion: apps/v1 kind: Deployment metadata: name: hello-ai spec: replicas: 2

"Keep 2 copies running."

selector: matchLabels: app: hello-ai template: metadata: labels: app: hello-ai

Labels are how Kubernetes connects things. Every Pod made from the template gets the label app: hello-ai; the Deployment counts Pods with that label, and the Service below sends traffic to them.

spec: containers: - name: api image: 123456789012.dkr.ecr.eu-west-1.amazonaws.com/hello-ai:a1b2c3d4 ports: - containerPort: 8000

The Pod's container: the commit-tagged image from Lesson 6, listening on 8000.

envFrom: - configMapRef: name: hello-ai-config env: - name: API_KEY valueFrom: secretKeyRef: name: hello-ai-secrets key: API_KEY

All ConfigMap entries become environment variables, and one secret is added as API_KEY. Your app just reads os.getenv, as in Lesson 3.

resources: requests: cpu: 250m memory: 256Mi limits: cpu: "1" memory: 512Mi

Requests are for placement: the scheduler only uses a node with 0.25 CPU (250m) and 256 MiB free. Limits are enforced like --cpus and --memory: over 512 MiB means OOMKilled (Lesson 5). A CPU limit means the OMP_NUM_THREADS advice applies.

livenessProbe: httpGet: path: /health port: 8000 periodSeconds: 10 readinessProbe: httpGet: path: /health port: 8000 periodSeconds: 5

Liveness failing means restart the container. Readiness failing means stop sending it traffic. For hello-model you'd use /health/live and /health/ready (Lesson 5); a startupProbe gives slow-loading models extra time.

apiVersion: v1 kind: Service metadata: name: hello-ai spec: selector: app: hello-ai ports: - port: 80 targetPort: 8000

Inside the cluster, http://hello-ai (port 80) reaches any ready Pod labelled app: hello-ai on port 8000. The same idea as db in Compose.

04Try it with Podman

podman kube play reads Kubernetes YAML and creates the matching Podman pods, containers, secrets and volumes. It's not a cluster, but it's a quick way to test a file. The local version of the file differs in three lines: the local image, a hostPort so your Mac can reach it, and the liveness probe (explained in step 3).

Step 1: play it

podman kube play hello-ai-podman.yaml
podman pod ps
podman ps --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'
curl localhost:8080/health

Output

hello-ai-pod   Running   containers=2
9f5017880561-infra   Up 7 seconds   0.0.0.0:8080->8000/tcp   ← holds the pod's shared network namespace
hello-ai-pod-api     Up 7 seconds   0.0.0.0:8080->8000/tcp   ← your container
{"status":"ok","model":"keyword-sentiment-v1",…}

Two containers, as Lesson 1 described pods: a tiny "infra" container owns the network namespace, and your container joins it. That's why both show the same port.

Step 2: settings and limits arrived

podman exec hello-ai-pod-api sh -c 'echo MODEL_NAME=$MODEL_NAME; [ -n "$API_KEY" ] && echo API_KEY is set'
podman inspect hello-ai-pod-api --format 'memory={{.HostConfig.Memory}} cpu={{.HostConfig.CpuQuota}}/{{.HostConfig.CpuPeriod}}'

Output

MODEL_NAME=keyword-sentiment-v1          ← from the ConfigMap
API_KEY is set                           ← from the Secret, stored as a podman secret
memory=536870912 cpu=100000/100000       ← 512 MiB and 1 CPU, from limits

Step 3: the probe surprise

With the real-cluster file's httpGet liveness probe, this happened after about half a minute:

Output

hello-ai-pod-api   Stopping (unhealthy)
health=unhealthy streak=3 restarts=2
/bin/sh: 1: curl: not found
  1. Podman turns an httpGet probe into a health check that runs curl inside the container.
  2. Your slim image has no curl, so every check failed.
  3. A failing liveness probe means "restart it", so Podman restarted the container, twice by then.

A real cluster makes httpGet requests from outside the container, so it doesn't need curl and this file works there unchanged. For local testing, the Podman file uses an exec probe that runs Python, like your Lesson 3 HEALTHCHECK:

          livenessProbe:
            exec:
              command: ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2)"]
            periodSeconds: 10

Result: Up 11 seconds (healthy), 0 restarts.

Step 4: what Podman ignores

In the YAMLKubernetespodman kube play on your Mac
replicas: 22 Pods1 pod, without a warning

Step 5: clean up, and generate YAML from containers

podman kube down hello-ai-podman.yaml

This removes the pod, its containers and the secret it created. Podman can also go the other way: podman kube generate POD writes Kubernetes YAML from running containers, a useful starting point. But look at what it produced for this pod:

podman kube generate hello-ai-pod (excerpt)

  containers:
  - env:
    - name: API_KEY
      value: not-a-real-key          ← the secret, written out as plain text
    - name: MODEL_NAME
      value: keyword-sentiment-v1

Generated files contain secret values as plain text. Never commit them without replacing those lines.

05How it looks on a real cluster

On a real cluster you use kubectl. These were not run for the course, which had no cluster, so this is for recognising them, not a transcript:

kubectl apply -f hello-ai-k8s.yamlSend the desired state to the cluster. Run it again after edits; it applies the differences.
kubectl get podsList Pods with status and restart counts. The first thing to run when something's wrong.
kubectl describe pod NAMEDetails plus events: failed probes, OOMKilled, image pull errors
kubectl logs NAME (-f)Like podman logs
kubectl exec -it NAME -- shLike podman exec
kubectl port-forward svc/hello-ai 8080:80Reach a Service from your laptop, like a temporary -p
kubectl rollout status deployment/hello-aiWatch a rollout progress
kubectl rollout undo deployment/hello-aiGo back to the previous version

What happens when you change the image tag

  1. You edit image: to the new commit tag and run kubectl apply.
  2. The Deployment starts a new Pod with the new image, next to the old ones.
  3. It waits until the new Pod's readiness probe passes, and only then sends it traffic and removes an old Pod.
  4. It repeats until every Pod is new.

If the new version never becomes ready, the rollout stops at step 3 and the old Pods keep serving. That's why a good readiness endpoint (Lesson 5) protects you from bad deploys.

06Kubernetes on AWS: EKS

Amazon EKS runs the control plane for you, charged per cluster per hour. You still decide where Pods run and how traffic, permissions and secrets are connected:

NeedCommon EKS answer
Machines for PodsEC2 managed node groups, or Fargate for Pods (no GPUs on Fargate)
GPU models (Lesson 5)A node group of GPU instances, such as g5 or g6
Traffic from the internetThe AWS Load Balancer Controller turns an Ingress into an Application Load Balancer
AWS permissions for PodsEKS Pod Identity: roles for Pods, no keys, the same idea as GitLab's OIDC login in Lesson 6
Secrets from Secrets ManagerAn add-on (External Secrets Operator or the Secrets Store CSI driver) that syncs them into the cluster
ImagesECR, exactly as in Lesson 6

ECS Express Mode or EKS? For one or a few services, Express Mode is far less to run. EKS makes sense when the company already runs Kubernetes, when you have many services and teams, or when you need its ecosystem: Helm charts, operators and GPU scheduling. Cloudflare has no Kubernetes offering; its Containers product is its managed answer.

Teams rarely write raw YAML for every environment. Look for Helm (templated YAML packages, with a values.yaml of settings) or Kustomize (a base plus per-environment patches). Underneath, it's the same objects you just read.

07Reading your team's files: a checklist

When you open a Deployment, Helm chart or Kustomize folder at work, find these, in this order:

  1. Image: which registry and tag? A commit tag, or a moving tag like latest?
  2. Resources: requests and limits. Do they match what the app really uses? Is OMP_NUM_THREADS set for model services?
  3. Probes: separate liveness and readiness? Does liveness avoid depending on the model or database?
  4. Settings and secrets: where do the values come from? Nothing secret should be written in the repository.
  5. Replicas and scaling: a fixed number, or a HorizontalPodAutoscaler?
  6. Traffic: which Service and Ingress point at it, and on what hostname?
  7. Security: runAsNonRoot, the user ID, a read-only root filesystem (Lesson 3).

09Check yourself

Try answering each question out loud before opening it.

Q1What does "desired state" mean, and what happens when a Pod of a 3-replica Deployment crashes?Show

You declare what should exist ("3 copies of this Pod"), not the steps to get there. Controllers keep comparing that with reality. After the crash reality is 2, so a controller creates a new Pod, possibly on another node.

Q2How does a Service know which Pods to send traffic to?Show

By labels. Its selector (app: hello-ai) matches Pods carrying that label, and only ready ones get traffic. The Deployment's template gives every Pod the label.

Q3What's the difference between requests and limits?Show

Requests are reserved and used to choose a node; limits are the maximum, enforced at run time. Exceeding the memory limit gets the container OOMKilled; hitting the CPU limit slows it down.

Q4A model service's liveness and readiness probes both call /health/ready, and the model takes 3 minutes to load. What goes wrong?Show

Liveness fails during loading, so Kubernetes restarts the container before the model finishes: a restart loop. Liveness should call /health/live, and a startupProbe can give extra start-up time.

Q5Under podman kube play, your container keeps restarting as unhealthy, but the app works when you curl it. Why, and does the same file fail on a real cluster?Show

Podman runs httpGet probes with curl inside the container, and slim images don't have it. A real cluster makes the request from outside, so the file works there. Locally, use an exec probe.

Q6A new image version never becomes ready during a rollout. What do users see?Show

Nothing unusual. The rollout stalls because new Pods never pass readiness, and the old Pods keep serving traffic. kubectl rollout undo returns the Deployment to the previous version.

Q7A colleague wants to commit the output of podman kube generate to the repository. What do you check first?Show

Secret values: generated YAML writes them out as plain value: entries. Replace them with references to a Secret that's managed outside Git.

Q8Your team runs two small services on AWS and no one knows Kubernetes. EKS or ECS Express Mode?Show

ECS Express Mode. It gives you load balancing, HTTPS, scaling and rollbacks with far less to operate. EKS pays off with many services, an existing Kubernetes platform, or a need for its ecosystem.
