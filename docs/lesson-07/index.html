Your app on Kubernetes

In many companies, a devops or platform team runs the apps that developers build on a Kubernetes cluster. This lesson prepares you for that from both sides. First you make the image ready for deployment: a checklist, with a test on your Mac for each item. Then you run the app on a real Kubernetes cluster on your Mac and see everything your team will build around it, so you can answer their questions and know which ones to ask.

By the end you should be able to

  • build an image that a strict cluster accepts, and that survives restarts, new versions and large uploads
  • measure the numbers your team will ask for (memory, CPU, request time) instead of guessing
  • read every Kubernetes object your team will create for the app
  • run the app on a real cluster with kind and kubectl, break it on purpose, and recognise each failure
  • give your team a one-page description of the app, and ask them the right questions

01Who does what

This section shows where your work ends and your team's begins. That's also where most of their questions will come from.

Your devops team runs the cluster: the machines, the network, how users reach apps, where secrets are kept, and what each app may do in AWS. You're responsible for the image, and for the facts about your app that they can't see from outside it:

YouYour devops team
The app, its Containerfile, and the image CI builds from them (Lesson 6)The cluster, its machines, and a namespace for your app
Health endpoints, a clean shutdown, limits on what users can sendThe Kubernetes files that run the image (often packaged as a Helm chart)

You hand over two things: an image in a registry, and a short list of facts about the app. Section 10 is that list, filled in for this lesson's app. Everything before it is how you find the facts and make sure they're true.

02The practice app

This lesson uses sheet-tool, a small app of a kind many teams build:

  • a web page where a user uploads an .xlsx file;
  • the app reads it with openpyxl and sends column A, row by row, to a model on OpenRouter;
  • it writes the answers into a new column and sends the file back as a download, in the same request;
  • it keeps one YAML file (its settings: model, prompt, row limit) in an S3 bucket.
AddressWhat it does
GET /The upload page
POST /process.xlsx in, processed .xlsx out as a download
GET /settings, PUT /settingsRead or change settings.yaml in S3
GET /health/live"The process is running" (section 3)
GET /health/ready"I can do my job right now": S3 answers (section 3)

Two stand-ins replace what the cloud and the internet provide, so nothing costs money and no real key is needed: a MinIO server pretends to be S3, and a fake OpenRouter (a 40-line Python file) answers with the same URL path and JSON shape as the real one.

"""sheet-tool: upload an .xlsx file, get it back with one column written by an AI model.

Settings live in one YAML file in S3. Everything else comes from environment variables.
"""
import io
import logging
import os
import re
import time

import boto3
import httpx
import yaml
from botocore.config import Config
from botocore.exceptions import BotoCoreError, ClientError
from fastapi import FastAPI, HTTPException, Request, UploadFile
from fastapi.responses import HTMLResponse, JSONResponse, Response
from openpyxl import load_workbook
from pydantic import BaseModel, Field

# Configuration: only from environment variables, never from files baked into the image.
S3_BUCKET = os.environ["S3_BUCKET"]
S3_KEY = os.getenv("S3_KEY", "settings.yaml")
OPENROUTER_BASE_URL = os.getenv("OPENROUTER_BASE_URL", "https://openrouter.ai/api/v1")
OPENROUTER_API_KEY = os.environ["OPENROUTER_API_KEY"]
MAX_UPLOAD_MB = float(os.getenv("MAX_UPLOAD_MB", "10"))
MAX_UPLOAD_BYTES = int(MAX_UPLOAD_MB * 1024 * 1024)

logging.basicConfig(level=os.getenv("LOG_LEVEL", "INFO"), format="%(levelname)s %(name)s %(message)s")
log = logging.getLogger("sheet-tool")


class SkipHealthChecks(logging.Filter):
    """Kubernetes calls the health endpoints every few seconds; don't log each call."""

    def filter(self, record):
        return "/health/" not in record.getMessage()


logging.getLogger("uvicorn.access").addFilter(SkipHealthChecks())
logging.getLogger("httpx").setLevel(logging.WARNING)  # one line per AI call is too much

# boto3 finds the endpoint, region and credentials itself (AWS_* variables, or the pod's IAM role).
# Short timeouts: a hung S3 call should fail fast, not hold a request for minutes.
s3 = boto3.client("s3", config=Config(connect_timeout=2, read_timeout=5, retries={"max_attempts": 3}))
s3_check = boto3.client("s3", config=Config(connect_timeout=1, read_timeout=2, retries={"max_attempts": 1}))

# httpx also reads HTTPS_PROXY and NO_PROXY, in case the cluster's outbound traffic goes through a proxy.
ai = httpx.Client(
    base_url=OPENROUTER_BASE_URL,
    headers={"Authorization": f"Bearer {OPENROUTER_API_KEY}"},
    timeout=httpx.Timeout(60, connect=5),
)


class Settings(BaseModel):
    model: str = "openai/gpt-4o-mini"
    prompt: str = "Summarise in five words: {text}"
    max_rows: int = Field(500, ge=1, le=5000)


def load_settings(client=s3) -> Settings:
    try:
        body = client.get_object(Bucket=S3_BUCKET, Key=S3_KEY)["Body"].read()
    except ClientError as error:
        if error.response["Error"]["Code"] == "NoSuchKey":
            return Settings()  # nothing saved yet
        raise
    return Settings(**(yaml.safe_load(body) or {}))


def settings_or_503() -> Settings:
    try:
        return load_settings()
    except (BotoCoreError, ClientError) as error:
        log.error("settings storage failed: %r", error)
        raise HTTPException(503, "Settings storage is unreachable")


def save_settings(settings: Settings):
    body = yaml.safe_dump(settings.model_dump(), sort_keys=False).encode()
    s3.put_object(Bucket=S3_BUCKET, Key=S3_KEY, Body=body, ContentType="application/yaml")


def ask_ai(model: str, prompt: str) -> str:
    response = ai.post("/chat/completions", json={"model": model, "messages": [{"role": "user", "content": prompt}]})
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"].strip()


app = FastAPI(title="sheet-tool")


@app.middleware("http")
async def limit_upload_size(request: Request, call_next):
    # Refuse a too-large upload before reading it. The ingress should have its own limit too.
    length = request.headers.get("content-length")
    if length and int(length) > MAX_UPLOAD_BYTES:
        return JSONResponse({"detail": f"File is larger than {MAX_UPLOAD_MB:g} MB"}, status_code=413)
    return await call_next(request)


PAGE = """<!doctype html>
<title>sheet-tool</title>
<h1>sheet-tool</h1>
<p>Upload an .xlsx file (up to {limit} MB). Column A is sent to the AI model; the answers come back in a new column.</p>
<form action="process" method="post" enctype="multipart/form-data">
  <input type="file" name="file" accept=".xlsx" required>
  <button>Process and download</button>
</form>
"""


@app.get("/", response_class=HTMLResponse)
def page():
    return PAGE.format(limit=f"{MAX_UPLOAD_MB:g}")


@app.post("/process")
def process(file: UploadFile):
    if not (file.filename or "").lower().endswith(".xlsx"):
        raise HTTPException(415, "Upload an .xlsx file")
    data = file.file.read(MAX_UPLOAD_BYTES + 1)
    if len(data) > MAX_UPLOAD_BYTES:
        raise HTTPException(413, f"File is larger than {MAX_UPLOAD_MB:g} MB")

    settings = settings_or_503()
    try:
        workbook = load_workbook(io.BytesIO(data))
    except Exception:
        raise HTTPException(400, "Not a valid .xlsx file")
    sheet = workbook.active
    rows = sheet.max_row - 1
    if rows > settings.max_rows:
        raise HTTPException(413, f"{rows} rows; the limit is {settings.max_rows}")

    started = time.monotonic()
    answer_column = sheet.max_column + 1
    sheet.cell(row=1, column=answer_column, value="AI answer")
    try:
        for row in range(2, sheet.max_row + 1):
            text = sheet.cell(row=row, column=1).value
            if text is not None:
                prompt = settings.prompt.replace("{text}", str(text))
                sheet.cell(row=row, column=answer_column, value=ask_ai(settings.model, prompt))
    except httpx.HTTPError as error:
        log.error("AI call failed: %r", error)
        raise HTTPException(502, "The AI service failed; try again later")

    output = io.BytesIO()
    workbook.save(output)
    # Log sizes and timings, never file contents or keys.
    log.info("processed rows=%d bytes_in=%d seconds=%.1f", rows, len(data), time.monotonic() - started)

    # The file name comes from the user: keep only safe characters before putting it in a header.
    safe_name = re.sub(r"[^A-Za-z0-9._-]", "_", file.filename)
    return Response(
        output.getvalue(),
        media_type="application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        headers={"Content-Disposition": f'attachment; filename="processed-{safe_name}"'},
    )


@app.get("/settings")
def get_settings() -> Settings:
    return settings_or_503()


@app.put("/settings")
def put_settings(settings: Settings) -> Settings:
    try:
        save_settings(settings)
    except (BotoCoreError, ClientError) as error:
        log.error("settings storage failed: %r", error)
        raise HTTPException(503, "Settings storage is unreachable")
    log.info("settings saved model=%s max_rows=%d", settings.model, settings.max_rows)
    return settings


@app.get("/health/live")
def live():
    # "The process is running and answering." Checks nothing else, so a broken S3 never causes restarts.
    return {"status": "ok"}


@app.get("/health/ready")
def ready():
    # "I can do my job right now." The app can't work without its settings, so check that S3 answers.
    try:
        load_settings(client=s3_check)
    except Exception as error:
        log.warning("not ready: %r", error)
        raise HTTPException(503, "Settings storage is unreachable")
    return {"status": "ready"}

"""Count answers from the Service for N seconds: python count_requests.py 40

Run it inside the cluster (see the lesson), so requests go through the Service like real traffic.
"""
import collections
import sys
import time

import httpx

end = time.time() + float(sys.argv[1])
counts = collections.Counter()
with httpx.Client(timeout=5) as client:
    while time.time() < end:
        try:
            counts[client.get("http://sheet-tool.sheet-tool/", headers={"Connection": "close"}).status_code] += 1
        except httpx.HTTPError as error:
            counts[type(error).__name__] += 1
        time.sleep(0.05)
print(dict(counts))

"""A fake OpenRouter for local testing: same URL path and JSON shape, no real model, no cost.

Only the Python standard library, so it runs in the plain python image.
"""
import json
import os
import time
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

DELAY = float(os.getenv("FAKE_DELAY", "0.05"))  # seconds per answer, to imitate a real model


class Handler(BaseHTTPRequestHandler):
    def reply(self, status, body):
        data = json.dumps(body).encode()
        self.send_response(status)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def do_GET(self):
        self.reply(200, {"status": "ok"})

    def do_POST(self):
        if self.path != "/api/v1/chat/completions":
            return self.reply(404, {"error": "not found"})
        if not self.headers.get("Authorization", "").startswith("Bearer "):
            return self.reply(401, {"error": "missing API key"})
        request = json.loads(self.rfile.read(int(self.headers["Content-Length"])))
        prompt = request["messages"][-1]["content"]
        time.sleep(DELAY)
        answer = f"fake answer ({len(prompt.split())} words in)"
        self.reply(200, {"model": request["model"], "choices": [{"message": {"role": "assistant", "content": answer}}]})


ThreadingHTTPServer(("0.0.0.0", 8080), Handler).serve_forever()

class SkipHealthChecks(logging.Filter):
    """Kubernetes calls the health endpoints every few seconds; don't log each call."""

    def filter(self, record):
        return "/health/" not in record.getMessage()


logging.getLogger("uvicorn.access").addFilter(SkipHealthChecks())
logging.getLogger("httpx").setLevel(logging.WARNING)  # one line per AI call is too much

# boto3 finds the endpoint, region and credentials itself (AWS_* variables, or the pod's IAM role).
# Short timeouts: a hung S3 call should fail fast, not hold a request for minutes.
s3 = boto3.client("s3", config=Config(connect_timeout=2, read_timeout=5, retries={"max_attempts": 3}))
s3_check = boto3.client("s3", config=Config(connect_timeout=1, read_timeout=2, retries={"max_attempts": 1}))

ai = httpx.Client(
    base_url=OPENROUTER_BASE_URL,
    headers={"Authorization": f"Bearer {OPENROUTER_API_KEY}"},
    timeout=httpx.Timeout(60, connect=5),
)


class Settings(BaseModel):
    model: str = "openai/gpt-4o-mini"
    prompt: str = "Summarise in five words: {text}"
    max_rows: int = Field(500, ge=1, le=5000)


def load_settings(client=s3) -> Settings:
    try:
        body = client.get_object(Bucket=S3_BUCKET, Key=S3_KEY)["Body"].read()
    except ClientError as error:
        if error.response["Error"]["Code"] == "NoSuchKey":
            return Settings()  # nothing saved yet
        raise
    return Settings(**(yaml.safe_load(body) or {}))


def settings_or_503() -> Settings:
    try:
        return load_settings()
    except (BotoCoreError, ClientError) as error:
        log.error("settings storage failed: %r", error)
        raise HTTPException(503, "Settings storage is unreachable")


def save_settings(settings: Settings):
    body = yaml.safe_dump(settings.model_dump(), sort_keys=False).encode()
    s3.put_object(Bucket=S3_BUCKET, Key=S3_KEY, Body=body, ContentType="application/yaml")


def ask_ai(model: str, prompt: str) -> str:
    response = ai.post("/chat/completions", json={"model": model, "messages": [{"role": "user", "content": prompt}]})
    response.raise_for_status()
    return response.json()["choices"][0]["message"]["content"].strip()

@app.post("/process")
def process(file: UploadFile):
    if not (file.filename or "").lower().endswith(".xlsx"):
        raise HTTPException(415, "Upload an .xlsx file")
    data = file.file.read(MAX_UPLOAD_BYTES + 1)
    if len(data) > MAX_UPLOAD_BYTES:
        raise HTTPException(413, f"File is larger than {MAX_UPLOAD_MB:g} MB")

    settings = settings_or_503()
    try:
        workbook = load_workbook(io.BytesIO(data))
    except Exception:
        raise HTTPException(400, "Not a valid .xlsx file")
    sheet = workbook.active
    rows = sheet.max_row - 1
    if rows > settings.max_rows:
        raise HTTPException(413, f"{rows} rows; the limit is {settings.max_rows}")

    started = time.monotonic()
    answer_column = sheet.max_column + 1
    sheet.cell(row=1, column=answer_column, value="AI answer")
    try:
        for row in range(2, sheet.max_row + 1):
            text = sheet.cell(row=row, column=1).value
            if text is not None:
                prompt = settings.prompt.replace("{text}", str(text))
                sheet.cell(row=row, column=answer_column, value=ask_ai(settings.model, prompt))
    except httpx.HTTPError as error:
        log.error("AI call failed: %r", error)
        raise HTTPException(502, "The AI service failed; try again later")

    output = io.BytesIO()
    workbook.save(output)
    # Log sizes and timings, never file contents or keys.
    log.info("processed rows=%d bytes_in=%d seconds=%.1f", rows, len(data), time.monotonic() - started)

    # The file name comes from the user: keep only safe characters before putting it in a header.
    safe_name = re.sub(r"[^A-Za-z0-9._-]", "_", file.filename)
    return Response(
        output.getvalue(),
        media_type="application/vnd.openxmlformats-officedocument.spreadsheetml.sheet",
        headers={"Content-Disposition": f'attachment; filename="processed-{safe_name}"'},
    )

3.2 Write only to /tmp

Many clusters make the container's filesystem read-only (readOnlyRootFilesystem: true), so an attacker who gets in can't change the app or add tools. The app may then write only to folders mounted for it. sheet-tool writes in two places you won't find in its code: the upload parser buffers uploads bigger than 1 MB to a temporary file, and openpyxl writes a temporary file every time it saves a workbook. Both go to /tmp, so /tmp is the one folder the cluster will mount (section 6).

Testing this on your Mac has a trap. podman run --read-only quietly mounts a writable /tmp for you; Kubernetes doesn't:

podman run --rm --read-only localhost/sheet-tool:1.0 touch /tmp/x && echo writable
podman run --rm --read-only --read-only-tmpfs=false localhost/sheet-tool:1.0 touch /tmp/x

Output

writable
touch: cannot touch '/tmp/x': Read-only file system

So test with --read-only-tmpfs=false plus --tmpfs /tmp, which is what the cluster will give you. Section 8 shows what happens in the cluster without a /tmp: even a 5 KB file fails.

3.3 Two health endpoints

Kubernetes calls two addresses in your app every few seconds (Lesson 5 introduced them):

  • Liveness (/health/live): "is the process stuck?" If it fails, Kubernetes restarts the container.
  • Readiness (/health/ready): "can it do its job right now?" If it fails, Kubernetes sends it no traffic, but leaves it running.
@app.get("/health/live")
def live():
    return {"status": "ok"}                # checks nothing else

@app.get("/health/ready")
def ready():
    try:
        load_settings(client=s3_check)     # can it read settings.yaml from S3?
    except Exception as error:
        raise HTTPException(503, "Settings storage is unreachable")
    return {"status": "ready"}

Never call OpenRouter in a probe. Probes run every 5–10 seconds on every pod: each call would cost money and count against rate limits, and an OpenRouter outage would take down your upload page too.

S3 in readiness. When S3 is down, every pod becomes unready at the same moment, so the Service has no pods and users get errors even on the upload page (section 8 shows it). 3.5 Limit what users can send

An uploaded file is untrusted, and it turns into memory (section 4). sheet-tool checks, in this order:

  • Size, before reading the body: over MAX_UPLOAD_MB (10) gives 413.
  • Type: not .xlsx gives 415; not a valid workbook gives 400.
  • Rows: over max_rows from the settings gives 413, before any AI call is made.
  • XML tricks: defusedxml is installed, and openpyxl uses it on its own to refuse files built to explode in memory.
  • The file name is reduced to safe characters before it goes into the Content-Disposition header of the download.
head -c 11000000 /dev/urandom > too-big.xlsx
curl -s -w ' %{http_code}\n' -F file=@too-big.xlsx localhost:8000/process

Whatever sits in front of your app has its own size limit, and it may be smaller than yours. The once-common ingress-nginx defaults to 1 MB, so a 2 MB upload gets a 413 from it and never reaches your app. Put your limit in the handoff (section 10).

3.6 Timeouts and logs

  • Every outside call has a timeout. S3: 2 seconds to connect and 5 to read. OpenRouter: 5 to connect and 60 to answer. Without one, a hung connection holds a request (and its memory) until the user gives up.
  • Outbound proxy. httpx reads HTTPS_PROXY and NO_PROXY by itself, so if your company sends outbound traffic through a proxy, it's one environment variable, not a code change.
  • Logs go to stdout, one line per event, never with file contents or keys. Health checks aren't logged, because the cluster calls them every few seconds per pod.

04Measure what your team will ask

"How much memory and CPU does it need?" is usually the first question. The answer becomes the Deployment's requests and limits (section 6). Too low, and the pod is killed in production; too high, and you pay for idle machines, or the pod doesn't fit anywhere. So measure.

Memory: the biggest file decides

Make a file just under the 10 MB limit, with random text that barely compresses, the worst case for memory. Then restart the app so its memory count starts fresh, upload, and read the peak:

podman run --rm -v ./dev:/work:ro localhost/sheet-tool:1.0 python /work/make_sample.py 232000 --random > big.xlsx
podman compose up -d --force-recreate app
sleep 5
curl -s -w ' %{http_code}\n' -F file=@big.xlsx localhost:8000/process
podman exec sheet-tool-app-1 cat /sys/fs/cgroup/memory.peak | awk '{printf "%d MiB\n", $1/1048576}'

Output

wrote 232000 rows, 9.9 MB
{"detail":"231999 rows; the limit is 500"} 413
394 MiB

The upload was refused for its row count (the app assumes a header row, which this random file doesn't have), but only after openpyxl had loaded it, and loading is the expensive part. memory.peak is a file the kernel keeps for every container (cgroup v2): the most memory it has used since it started. The same measurement for other cases:

What the app was doingPeak memory
Idle, just started66 MiB
One 6.4 MB upload288 MiB
One 9.9 MB upload (the limit)394 MiB
Two 9.9 MB uploads at the same time714 MiB

So sheet-tool asks for 512 MiB (one large upload plus some room) and is allowed up to 1 GiB (two at once). Mi and Gi are the binary units Kubernetes uses: 1 MiB = 1,048,576 bytes. Section 8 shows what happens with a 256 MiB limit: OOMKilled.

CPU: one core at most

One limit-size upload took 4.1 seconds; two at once took 8 seconds each. Python runs one thread of Python code at a time, so the app never uses more than one core. A CPU limit of 1 costs it nothing, and it asks for 250m (a quarter of a core), because most of its time is spent waiting for the model.

Time per request: the number that may change your design

With the fake model (0.05 seconds per answer), 20 rows took 1.1 to 1.4 seconds. sheet-tool asks the model one row at a time, so the real time is roughly rows × seconds per model answer. Measure it with your own app, a realistic file and a few rows against the real API (each call costs money).

Every layer between the user and your pod has a timeout: the browser, the load balancer (an AWS Application Load Balancer gives up after 60 seconds of silence unless your team changes it) and the ingress. If a realistic file takes more than a minute or two, a single request isn't the right design. Tell your team early, because the alternative changes the app: start a job, let the browser check on it, and download the result later. The result then has to live in shared storage such as S3, because with two pods the download may reach the other one.

06The files your team writes

These are the files your team will write for your app, often as a Helm chart (section 9), with the same content. Reading them lets you check that they match your app, and answer questions about each line. The project has them in k8s/:

├── lab/           your Mac: the local image, the stand-ins, a fake Secret
├── production/    EKS: the ECR image, real S3, the Secret from Secrets Manager, an Ingress (not run)

Every object starts with apiVersion and kind (what sort of object) and metadata (its name and labels). Here's the Deployment, the biggest one:

k8s/base/deployment.yamlDeployment
apiVersion: apps/v1 kind: Deployment metadata: name: sheet-tool spec: replicas: 2

"Keep 2 copies running." One can be replaced while the other serves. Two copies work because the app keeps nothing between requests: upload and download happen in one request, so any pod can answer anyone.

strategy: rollingUpdate: maxUnavailable: 0 maxSurge: 1

For a new version: start one new pod, wait until it's ready, then remove an old one. Never fewer than 2 ready pods.

selector: matchLabels: app: sheet-tool template: metadata: labels: app: sheet-tool

Labels connect things. Every pod made from this template gets app: sheet-tool; the Deployment counts pods with that label, and the Service sends requests to them.

spec: serviceAccountName: sheet-tool automountServiceAccountToken: false terminationGracePeriodSeconds: 90

Run as the ServiceAccount that has the S3 permission. Don't give the pod a key to the Kubernetes API, which it never uses. On stop, wait up to 90 seconds before killing it (3.4).

securityContext: runAsNonRoot: true runAsUser: 10001 runAsGroup: 10001 seccompProfile: type: RuntimeDefault

Refuse to start as root, and run as user 10001. seccomp is a list of allowed system calls; RuntimeDefault blocks the rarely needed, risky ones.

containers: - name: app image: sheet-tool ports: - name: http containerPort: 8000

The image name is a placeholder that each environment replaces (section 9). The port gets a name, http, so the probes and the Service can refer to it.

envFrom: - configMapRef: name: sheet-tool-config - secretRef: name: sheet-tool-secrets

Every entry of the ConfigMap and of the Secret becomes an environment variable. The app just reads os.environ.

securityContext: allowPrivilegeEscalation: false readOnlyRootFilesystem: true capabilities: drop: ["ALL"]

No way to gain more rights than it starts with, a read-only filesystem (3.2), and no Linux capabilities (the pieces of root's power, such as changing file owners). Together with runAsNonRoot and seccomp, this is what a cluster set to restricted demands (section 8).

resources: requests: cpu: 250m memory: 512Mi limits: cpu: "1" memory: 1Gi

The numbers from section 4. Requests are reserved, and decide which node has room for the pod. Limits are the ceiling: above 1 GiB the container is killed (OOMKilled); at 1 CPU it's slowed down.

readinessProbe: httpGet: path: /health/ready port: http periodSeconds: 5 timeoutSeconds: 3 failureThreshold: 3 livenessProbe: httpGet: path: /health/live port: http periodSeconds: 10 timeoutSeconds: 3 failureThreshold: 3

The endpoints from 3.3. Readiness is asked every 5 seconds, liveness every 10, and three failures in a row count. sheet-tool starts in about a second; an app that loads a model for minutes would add a startupProbe (Lesson 5).

lifecycle: preStop: sleep: seconds: 5

When a pod is told to stop, two things happen at once: it's removed from the Service, and it receives SIGTERM. For a moment, new requests can still arrive at a pod that no longer accepts them. Pausing 5 seconds before SIGTERM lets the removal finish first. Measured on the test Mac during rollouts: 5 to 9 failed requests per rollout without the pause, none with it (three runs each, section 8).

volumeMounts: - name: tmp mountPath: /tmp volumes: - name: tmp emptyDir: sizeLimit: 100Mi

The one writable folder (3.2). An emptyDir is an empty folder created with the pod and deleted with it: scratch space, not storage.

The other objects are short:

k8s/base/ and k8s/lab/4 objects
kind: Service metadata: name: sheet-tool spec: selector: app: sheet-tool ports: - name: http port: 80 targetPort: http

Inside the cluster, http://sheet-tool reaches a ready pod labelled app: sheet-tool, on its http port. From another namespace the name is sheet-tool.sheet-tool (name, then namespace).

kind: ConfigMap metadata: name: sheet-tool-config data: S3_BUCKET: sheet-tool-settings S3_KEY: settings.yaml AWS_REGION: eu-west-1 OPENROUTER_BASE_URL: https://openrouter.ai/api/v1 MAX_UPLOAD_MB: "10"

Settings that aren't secret. Values are always text, hence the quotes around "10".

kind: Secret metadata: name: sheet-tool-secrets stringData: OPENROUTER_API_KEY: fake-openrouter-key AWS_ACCESS_KEY_ID: local-admin AWS_SECRET_ACCESS_KEY: fake-local-password

Lab only, with fake values. In production this Secret is filled from AWS Secrets Manager and has no AWS keys at all (section 9).

kind: PodDisruptionBudget spec: minAvailable: 1

When your team drains a node for maintenance, Kubernetes keeps at least one pod running.

09How your team deploys it

This section covers the parts of the conversation about environments, pipelines and rollbacks, and the pieces your team runs outside your app's files.

The same files, different values

Staging and production run the same image with different settings (the same idea as one compose.yaml with an env file per environment). In Kubernetes, two tools do this:

  • Kustomize, built into kubectl (the -k you used): a base folder plus one folder per environment that lists only what's different.
  • Helm: the files become templates with blanks, plus a values.yaml per environment that fills them in. A packaged set is called a chart. Not used in this lesson, but it produces the same objects.

From a push to running pods

  1. You push to GitLab. CI builds the image and pushes it to ECR, tagged with the commit (Lesson 6).
  2. A deploy step puts that tag into the production files. Two common setups:
    • CI deploys: a job runs kubectl apply -k or helm upgrade against the cluster.
    • GitOps: CI only changes the tag in a Git repository of deployment files. Argo CD or Flux, running inside the cluster, notices and applies it.
  3. Staging first; production after a check, often a manual button in the pipeline.
  4. The Deployment rolls out the new pods as in section 8.6, and stops if they never become ready.

Rolling back means deploying the previous tag the same way, for example by reverting the commit that changed it. kubectl rollout undo is for emergencies, and the next deploy from Git overwrites it (8.6).

Questions they may ask you

?"Is it stateless? Can we run 3 copies, or scale it automatically?"Answer

Yes. Each upload is handled entirely within one request, and the only lasting data is settings.yaml in S3. Any pod can serve any user, so no sticky sessions. Automatic scaling on CPU works, since processing is CPU-bound.

?"Does it need a persistent volume?"Answer

No. The settings are in S3, and /tmp only holds temporary files during a request, so an emptyDir is enough. A volume would also make several replicas harder, because a normal EBS-backed volume attaches to one node at a time.

?"What happens when S3 is down? And when OpenRouter is down?"Answer

S3 down: readiness fails, the pods get no traffic, and they come back by themselves when S3 returns. They aren't restarted (8.5). OpenRouter down: pods stay ready, and /process answers 502 "The AI service failed; try again later" after its timeout. Probes never call OpenRouter.

?"Why 90 seconds of termination grace? The default is 30."Answer

So an upload in progress can finish during a deploy: up to 60 seconds of uvicorn's graceful shutdown, plus the 5-second preStop pause, plus some margin. With 10 seconds, uploads were cut off (8.7). If real requests are shorter, this can come down.

?"Does it need root, extra capabilities, or host access?"Answer

No. It runs as user 10001 with all capabilities dropped, a read-only root filesystem and the default seccomp profile, and it was tested in a namespace set to restricted.

?"How do we know a deploy worked?"Answer

kubectl rollout status finishes only when all new pods are ready, which means they can reach S3. A quick extra check after deploy: GET /health/ready through the real hostname, then one small upload in staging.

12Check yourself

Try answering each question out loud before opening it.

Q1Your image has USER app. Why might a cluster refuse it, even though app isn't root?Show

With runAsNonRoot: true and no runAsUser in the Deployment, Kubernetes must prove from the image that the user isn't root. It can't look a name up, so it refuses with "image has non-numeric user (app), cannot verify user is non-root". USER 10001 fixes it.

Q2The app works with podman run --read-only, but in the cluster every upload fails with "No usable temporary directory found". Why?Show

Podman's --read-only mounts a writable /tmp by itself; Kubernetes' readOnlyRootFilesystem doesn't. The Deployment needs an emptyDir mounted at /tmp. To test this on your Mac, add --read-only-tmpfs=false --tmpfs /tmp.

Q3What should sheet-tool's liveness and readiness check, and why should neither call OpenRouter?Show

Liveness: only that the process answers, so an outage elsewhere never causes restarts. Readiness: that it can read its settings from S3, because it can't work without them. OpenRouter isn't checked because probes run every few seconds on every pod: that costs money, uses up rate limits, and an OpenRouter outage would take the whole app down instead of failing only the AI calls.

Q4Your team reports pods restarting with OOMKilled when users upload big files. What do you do?Show

Measure the peak memory with the largest file you accept (section 4), and with two at once. Then raise the memory limit to match, or lower the upload limit, or both. Requests should cover the common case, limits the worst case you allow.

Q5During every deploy a few requests fail with "connection refused", then everything is fine. What's missing?Show

A preStop pause. Removing a pod from the Service and sending it SIGTERM happen at the same time, so a few new requests reach a pod that has stopped accepting them. A 5-second preStop sleep took the failures from 5–9 per rollout to none.

Q6Long uploads are cut off whenever a pod is replaced. Which settings do you check?Show

That the app receives SIGTERM (exec-form CMD) and waits for running requests (uvicorn's --timeout-graceful-shutdown), and that terminationGracePeriodSeconds is longer than the longest request plus the preStop pause.

Q7A release goes out with a tag that doesn't exist. What do users see, and how do you get back properly?Show

Nothing: the new pod is stuck in ErrImagePull, and with maxUnavailable: 0 the old pods keep serving. kubectl rollout undo fixes the cluster right away, but the proper fix is deploying the previous tag from Git, otherwise the next deploy brings the bad tag back.

Q8Why can sheet-tool run 2 or more copies without sticky sessions, and what would change if upload and download were separate requests?Show

Each upload is processed and returned within one request, so no pod holds anything a later request needs. With separate requests, the download might reach a different pod than the upload, so the result would have to be stored somewhere shared, such as S3, with a job ID to find it.

Q9Your team suggests keeping the YAML file in MinIO. What do you ask?Show

Whether an S3 bucket would do, since you're on AWS and MinIO's free edition is no longer maintained; and if it's MinIO, which build, who runs and backs it up, and how the app gets credentials. The app itself only needs AWS_ENDPOINT_URL_S3 and credentials to change.
