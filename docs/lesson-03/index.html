Docker Fundamentals · Lesson 3 · Production-ready images

Making an image production-ready

Your hello-ai image works. This lesson turns it into one you could hand to a platform team: it runs without root, keeps secrets out, tells the platform when it's healthy, and builds the same way next month.

Reading about 35 minLab about 35 minStarts from your Lesson 2 ContainerfileOutputs from the test Mac, autumn 2026

By the end you should be able to

  • run your app as a normal user and explain what that protects against
  • get settings and secrets into a container without putting them in the image
  • add a health check that Podman can see, and know Podman's format catch
  • make sure your app's log output actually reaches podman logs
  • pin the base image so rebuilds are repeatable
  • choose where a real model's weights should live

01What's missing from the Lesson 2 image

Here is the Containerfile you wrote in Lesson 2. It's correct: good instruction order, exec-form CMD, and a .containerignore that keeps .env out.

FROM docker.io/library/python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

It's fine for learning, but it has gaps that matter once real users, real secrets and real servers are involved. Each section of this lesson fixes one:

02Don't run as root

Step 1: see who your app runs as

podman run --rm hello-ai:0.3 id

Output

uid=0(root) gid=0(root) groups=0(root)

No USER instruction means every container runs as root, the all-powerful user. Your app can modify its own code, install software and read every file in the container.

Step 2: understand why that's a risk

Containers are about limiting damage when something goes wrong. Suppose an attacker finds a way to run commands through your app, for example through a vulnerable library, or a model file that runs code when it's loaded (more on that in section 8). They get exactly the power of the user your app runs as:

  • As root, they can change your code to steal every request, install tools, and use root as a starting point to attack the container runtime itself.
  • As a normal user, they can't change the code, can't install anything, and have much less to work with.

It can also matter on your own Mac. Lesson 1 said Podman is rootless by default, where root in a container maps to an ordinary user outside. A Podman machine can also be set to rootful mode, and then root in a container is real root in the VM. The test Mac's machine is set up that way:

podman machine inspect --format '{{.Rootful}}'
podman run -d --name who hello-ai:0.3
podman top who user,huser     # user inside the container, user on the host (the VM)
podman rm -f who

Output on the test Mac

true
USER        HUSER
root        root

On a default, rootless machine the first line is false, and the HUSER column shows an ordinary user of the VM instead of root. That output is not shown here, because the test Mac runs in rootful mode.

You can't know where your image will end up: Docker on Linux servers is also rootful by default, and many Kubernetes clusters are set to refuse containers that run as root. So the image itself should not need root.

Step 3: add a user and switch to it

Two lines. The second one goes below pip install; step 5 shows why:

RUN useradd --create-home --uid 1000 app
USER app
  • useradd creates a normal user called app, with user ID 1000 and a home folder /home/app. A fixed number matters because file permissions and Kubernetes settings work with numbers, not names.
  • USER app is a config setting: every later RUN step, and the running container, use this user.
  • The files that COPY puts into the image belong to root, and everyone may read them. The app can read its code but can't change it, which is what you want.

Step 4: check the result

With those two lines added (you'll build this as hello-ai:1.0 in the lab):

podman run --rm hello-ai:1.0 id
podman run --rm hello-ai:1.0 touch /app/main.py
podman run --rm hello-ai:1.0 touch /tmp/scratch.txt

Output

uid=1000(app) gid=1000(app) groups=1000(app)
touch: cannot touch '/app/main.py': Permission denied   ← code is protected
                                                         ← /tmp still works

The API still answers normally, and podman top now shows app and 1000 instead of root.

Step 5: where the USER line goes

The position of USER app matters for RUN lines. It does not matter for COPY lines. Both were tested with the hello-ai files on the test Mac.

COPY ignores USER. It is natural to expect that files copied after USER app belong to app. Here USER app is moved above COPY . .:

RUN pip install --no-cache-dir -r requirements.txt
USER app
COPY . .

ls -l /app, then touch /app/main.py, in that image

-rw-r--r--. 1 root root  560 Sep 27 20:24 README.md
-rw-r--r--. 1 root root 1059 Oct  4 18:43 main.py
-rw-r--r--. 1 root root   33 Sep 27 20:21 requirements.txt
touch: cannot touch '/app/main.py': Permission denied

The third and fourth columns are the owner and the group. Both are still root, exactly as with the two lines in the usual order.

To give copied files to another user, COPY has its own option, --chown (short for "change owner"):

COPY --chown=app:app . .
USER app

The same commands, then touch /app/new.txt

-rw-r--r--. 1 app app  560 Sep 27 20:24 README.md
-rw-r--r--. 1 app app 1059 Oct  4 18:43 main.py
-rw-r--r--. 1 app app   33 Sep 27 20:21 requirements.txt
                                                         ← touch /app/main.py printed nothing: allowed
touch: cannot touch '/app/new.txt': Permission denied   ← the folder /app is still root's

Now app owns the files and can change main.py. Don't use --chown for your code: an app that can't change its own code is the protection this section is about.

RUN follows USER. Here USER app is moved above the pip install line. The build finished, with this in its output:

Output of podman build

Defaulting to user installation because normal site-packages is not writeable
  WARNING: The script uvicorn is installed in '/home/app/.local/bin' which is not on PATH.

pip ran as app, was not allowed to write to the system's folder for Python packages, and put them in /home/app/.local instead. PATH is the list of folders where the system looks for programs, and that folder is not on it. So the container failed to start:

Output of podman run, shortened

Error: … crun: executable file `uvicorn` not found in $PATH: No such file or directory

So keep USER app below every RUN line that needs root: installing packages, creating the user, creating folders.

If your app writes files

Some apps need a writable folder, for a cache or downloaded model files. Create it and hand it to the user before switching: RUN mkdir /app/cache && chown app:app /app/cache. For data that must survive restarts, use a volume instead (Lesson 4).

03Settings and secrets at run time

The goal is one image that runs everywhere: on your laptop, in staging, in production. What differs between them (the model name, the log level, the API key) is supplied when the container starts. That way the image never contains a secret, and you test exactly the image you ship.

Wrong way 1: ENV in the Containerfile

ENV API_KEY=sk-baked-into-the-image

Anyone who pulls the image can read it with one command:

podman image inspect IMAGE --format '{{range .Config.Env}}{{println .}}{{end}}'

Output

API_KEY=sk-baked-into-the-image

Wrong way 2: a build argument

ARG looks safer, because the value is only passed during the build with --build-arg HF_TOKEN=…. But the builder records it in the image history:

podman history --no-trunc --format '{{.CreatedBy}}' IMAGE

Output

|1 HF_TOKEN=hf_secret_build_token /bin/sh -c echo "pretend to download a model…"

Build arguments are fine for non-secret options, such as a version number. Never use them for tokens.

Right way A: environment variables at run time

Your app reads settings with os.getenv("API_KEY"), and you supply them with -e or, for several at once, from a file with --env-file:

podman run -d -p 8000:8000 -e MODEL_NAME=sentiment-v2 hello-ai:1.0   # one setting
podman run -d -p 8000:8000 --env-file .env hello-ai:1.0             # or every line of a file

This is the standard approach, and it's how most platforms deliver configuration. Its weakness: the values are stored in the container's settings, so anyone who can run Podman commands on that machine can read them.

podman inspect CONTAINER shows

API_KEY=not-a-real-key-just-for-the-lesson

Right way B: Podman secrets

For real secrets, Podman can store the value separately and hand it to the container at start:

printf 'sk-your-real-key' | podman secret create api_key -
podman run -d --secret api_key hello-ai:1.0                                # as a file: /run/secrets/api_key
podman run -d --secret api_key,type=env,target=API_KEY hello-ai:1.0        # as the API_KEY variable
  • As a file, the secret appears at /run/secrets/api_key, readable by any user in the container. Your app reads the file instead of a variable.
  • As a variable, your app doesn't need to change.
  • Either way, podman inspect shows only the secret's name. A search of the inspect output for the value found it 0 times.

Production platforms work the same way: Kubernetes Secrets and cloud secret managers (AWS Secrets Manager, Google Secret Manager) deliver values as variables or files when the container starts.

MethodInside the image?Shown by podman inspect?Use it for
ENV in ContainerfileYesYesHarmless defaults, like LOG_LEVEL=info
ARG / --build-argYes, in history—Non-secret build options
-e / --env-fileNoYesSettings; secrets on your laptop
podman secretNoName onlySecrets

04Health checks

"Up" in podman ps only means the main process exists. It doesn't mean your app works: the model may have failed to load, or the server may be stuck. A health check is a small command the platform runs regularly inside the container. Exit code 0 means healthy; anything else means unhealthy.

Step 1: add a HEALTHCHECK

HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://127.0.0.1:8000/health', timeout=2)"]
  • The command calls your /health endpoint from inside the container. The slim image has no curl, so it uses Python. urlopen raises an error, and Python exits with 1, if the request fails.
  • --interval=30s: run every 30 seconds. --timeout=3s: a check that takes longer counts as a failure.
  • --start-period=10s: failures in the first 10 seconds don't count, so the app has time to start. A real model can need much longer.
  • --retries=3: three failures in a row mark the container unhealthy, so one slow moment doesn't.

Step 2: the Podman catch

Build it the normal way, and Podman quietly drops the health check:

Output of podman build

level=warning msg="HEALTHCHECK is not supported for OCI image format and will be ignored. Must use `docker` format"

Podman builds images in the standard OCI format, and the OCI spec has no field for health checks; Docker's older format does. Build with --format docker and it's kept:

podman build --format docker -t hello-ai:1.0 .

The image still runs everywhere; Docker, Kubernetes and registries all accept this format.

Step 3: watch it

podman ps, over time

Up 1 second (starting)       ← no check has run yet
Up 14 seconds (healthy)      ← with a 10 s interval, after the first check

With a 30-second interval the first check runs after about 30 seconds. To check immediately, run podman healthcheck run NAME: exit code 0 means healthy, and podman ps updates straight away. With the check pointed at a wrong port, the status turned (unhealthy) after three failures.

You can also add a check when starting any image, without changing it: podman run --health-cmd "…" --health-interval 30s ….

Kubernetes

Kubernetes ignores HEALTHCHECK. It calls your app's /health endpoint directly, with a liveness probe ("is the process stuck? restart it") and a readiness probe ("can it take traffic yet?"). For AI services, readiness matters: return an error from /health until the model has loaded, and no requests are sent before then. The part that works everywhere is a good /health endpoint: fast, cheap, and with no calls to paid APIs.

05Logs that show up

Containers log to their output: whatever the main process prints appears in podman logs, and platforms collect it from there. Python has a surprise here.

This container prints "model loaded", then keeps running. Its logs, 3 seconds later:

podman run -d --name buf docker.io/library/python:3.12-slim \
  python -c "import time; print('model loaded'); time.sleep(20)"
podman logs buf

Output

                     ← nothing
  1. When Python writes to a terminal, it sends each line out immediately.
  2. In a container, output goes to a pipe, not a terminal. Python then saves output up in a buffer, a few kilobytes at a time, to be efficient.
  3. "model loaded" waits in that buffer. It appears when the buffer fills or the program exits, and it's lost if the process is killed.

One environment variable turns buffering off. The same test with it set:

podman run -d --name buf2 -e PYTHONUNBUFFERED=1 docker.io/library/python:3.12-slim \
  python -c "import time; print('model loaded'); time.sleep(20)"
podman logs buf2

Output

model loaded

Put ENV PYTHONUNBUFFERED=1 in every Python image. You didn't notice the problem in Lesson 2 because uvicorn's own log lines go through Python's logging module, which writes out each line. Your own print() calls, and some libraries, don't.

06Pin the base image

Lesson 1: a tag like python:3.12-slim is a movable label. It's rebuilt regularly, so rebuilding your image next month can silently pick up a different Python patch version or different system libraries. A digest is the opposite of a tag: it is the SHA-256 fingerprint of one exact file on the registry, and it never changes. Pinning means writing a digest into FROM, so every build starts from the same base:

FROM docker.io/library/python:3.12-slim@sha256:f77ac9e44ae96ef2c90b8053ea08c31f8be030f824196b0ae4db6d462c84e51f

The tag stays in the line so people can read it; the digest decides what's pulled.

The only hard part is knowing which digest to write there, because your Mac shows two for the same image. The steps below explain why there are two, and how to pick the right one.

Step 1: the tag points to a list, not to an image

You would expect python:3.12-slim to be one image. It is eight, one for each processor type, because a program built for one processor type doesn't run on another (the exec format error from Lesson 1).

So Docker Hub stores one more thing next to those eight images: a small text file that lists them. Its proper name is the image index. Shortened, it says:

The list behind python:3.12-slim

for linux/amd64   use the image  sha256:44ff437b…
for linux/arm64   use the image  sha256:950206c3…
for linux/386     use the image  sha256:846bc0ce…
…five more lines, one per processor type

The name python:3.12-slim points to this file, not to an image. When you pull:

  1. Podman downloads the small list file first.
  2. It finds the line for its own processor type. On your Mac that is linux/arm64.
  3. It downloads the image named on that line, 950206c3….

Step 2: that's why your Mac shows two digests

The list is a file, so it has a fingerprint. Each image has one too. After a pull, your Mac remembers both:

podman image inspect docker.io/library/python:3.12-slim --format '{{range .RepoDigests}}{{println .}}{{end}}'

Output

docker.io/library/python@sha256:950206c37262dd86…   ← the image your Mac downloaded
docker.io/library/python@sha256:f77ac9e44ae96ef2…   ← the list

Podman doesn't label the two lines, and their order means nothing. A second command prints only the image:

podman image inspect docker.io/library/python:3.12-slim --format '{{.Digest}}'

Output

sha256:950206c37262dd86…

So the rule is: the list is the RepoDigests line that is not equal to .Digest.

To be sure, the list file itself was downloaded from Docker Hub. It is 10,373 bytes, and its SHA-256 is f77ac9e44ae96ef2…, exactly the second line above. The digest really is the fingerprint of the list.

Step 3: pin the list, not the image

  • Pin the list (f77ac9…): every machine reads the same list and takes the image for its own processor. Builds with it for both linux/arm64 and linux/amd64 each got the right image.
  • Pin the arm64 image (950206…): there is no list to choose from any more. Every machine gets the arm64 image, including an amd64 server, where it fails with exec format error.

Because the list is fixed, the eight images named in it are fixed too. You still get the same base on every build, on any processor type.

Step 4: the routine, in three commands

1. Get today's version of the base. Your local copy may be weeks old. Pulling first means you pin the version with the latest security fixes.

podman pull docker.io/library/python:3.12-slim

2. Print the digest of the list. This command does the comparison from step 2 for you. jq is a tool that picks values out of JSON; the setup step installs it.

podman image inspect docker.io/library/python:3.12-slim | jq -r '.[0] | .Digest as $d | .RepoDigests[] | select(endswith($d) | not)'

Output

docker.io/library/python@sha256:f77ac9e44ae96ef2c90b8053ea08c31f8be030f824196b0ae4db6d462c84e51f
  • .Digest as $d remembers the image's digest. .RepoDigests[] goes through the two lines. select(endswith($d) | not) keeps the line that does not end with it.
  • Write the image's name with its tag, exactly as shown. Looked up by its ID instead, the same image showed the list in .Digest, and the comparison picked the wrong line.
  • If the command prints nothing, the base image exists for one processor type only. Then there is no list, and .Digest is all you can pin.

3. Write it into the FROM line. Copy the part from sha256: to the end, and put it after the tag with an @ and no space:

FROM docker.io/library/python:3.12-slim@sha256:f77ac9e44ae96ef2c90b8053ea08c31f8be030f824196b0ae4db6d462c84e51f

Step 5: check that you picked the list

podman manifest inspect asks the registry what a name or digest points to, and prints it. It downloads no image. With jq, one line per processor type:

podman manifest inspect docker.io/library/python@sha256:f77ac9e44ae96ef2c90b8053ea08c31f8be030f824196b0ae4db6d462c84e51f \
  | jq -r '.manifests[] | select(.platform.os != "unknown") | "\(.platform.os)/\(.platform.architecture)  \(.digest)"'

Output

linux/amd64    sha256:44ff437bba87…
linux/arm      sha256:6f6b9f27d56b…
linux/arm      sha256:679673bc59af…
linux/arm64    sha256:950206c37262…   ← the image your Mac downloaded
linux/386      sha256:846bc0cee2cb…
linux/ppc64le  sha256:32e353a26495…
linux/riscv64  sha256:a32947180e15…
linux/s390x    sha256:97761e2944eb…

Several lines means it is the list. Your server's processor type should be among them: most Linux servers are linux/amd64, and AWS Graviton machines are linux/arm64. The select(…) part hides entries marked unknown; those are build records that Docker Hub stores next to each image, not images you can run.

Run the same command on the other digest, 950206…, and it fails, because that one is a single image:

Output

Error: … Treating single images as manifest lists is not implemented

Does your machine's processor type matter?

Not for pinning. A machine with a different processor downloads a different image, but it reads the same list, so the routine prints the same digest there.

arm64 machine (your Mac)amd64 machine
The image it downloads950206…44ff437b…
The list, which you pinf77ac9…f77ac9…

The right-hand column was checked on the test Mac by downloading the amd64 image for a moment: its two RepoDigests were 44ff437b… and the same f77ac9….

The processor type matters for a different question: which processor your finished image is built for. That is the --platform option in Lesson 6, and it doesn't change which digest you pin.

Real example

The digests in this lesson are from late September, when the tag pointed to Python 3.12.14. On 6 October the same tag pointed to a new list, 05cda977…, with Python 3.12.15. So your Mac will print different digests from the ones shown here: use yours. A Containerfile pinned to f77ac9… still gets 3.12.14 today, and that is the point of pinning.

The trade-off: a pinned base no longer picks up security patches by itself. To update, repeat the routine in step 4 and replace the digest in the FROM line. Teams often leave this to a bot such as Renovate, which opens a merge request when a new version of the base is published.

08Where the model goes

hello-ai's "model" is a few lines of Python. A real one is a file of weights, from hundreds of megabytes to many gigabytes, and you have to decide where it lives. There are three common answers:

OptionHowGoodCostly
1. Inside the imageCOPY the files in, or download them in a RUN stepSelf-contained: the image is the release. Starts fast, works offline, and exactly what you tested.Huge images, slow pulls on every deploy, and a model update needs a rebuild
2. Downloaded at startThe app fetches weights from Hugging Face or cloud storage when it startsSmall image; model and code can be updated separatelySlow cold starts, needs network and credentials, and "latest" can change under you: pin the model version
3. Mounted storageWeights sit on a volume or shared disk, mounted into the containerFast starts, one copy shared by many containersThe storage must be set up and kept in sync separately (volumes are in Lesson 4)

Small models (up to a few hundred MB) are often simplest baked in. Large models usually use option 2 or 3. Whatever your team does, check which one it is. It explains why their images look the way they do.

Three practical tips

  • Only load model files you trust, and prefer .safetensors. Older formats (.bin, .pt, .pkl) use Python's pickle, which can run code while loading. This is one of the "attacker runs commands through your app" routes from section 2.
  • With a non-root user, point caches somewhere writable. Hugging Face libraries cache downloads in the home folder by default. Set HF_HOME to a folder the app user owns, or to a mounted volume.
  • Check which PyTorch you install. On Linux x86-64 servers, a plain pip install torch brings several gigabytes of NVIDIA GPU libraries. A service that runs on CPU only can use PyTorch's CPU build instead (--index-url https://download.pytorch.org/whl/cpu) and be far smaller.

podman rm -f api

The key arrives (true), and it's visible in podman inspect. Now use a secret:

printf 'not-a-real-key-either' | podman secret create api_key -
podman run -d --name api -p 8000:8000 --secret api_key,type=env,target=API_KEY hello-ai:1.0
curl localhost:8000/health
podman inspect api | grep -c not-a-real-key-either

Still true, and the count is 0.

A complete example with your own variable. A small script needs a key called MY_API_KEY, and the key is 12345. Save this as show_key.py in ~/practice/hello-ai:

import os

key = os.getenv("MY_API_KEY")
if key is None:
    print("MY_API_KEY is not set")
else:
    print("MY_API_KEY =", key)

os.getenv reads an environment variable and gives back None when it doesn't exist. The script prints the key only because 12345 is a made-up value; never print a real key. Now put the script into an image. A separate tag keeps hello-ai:1.0 as it is:

podman build --format docker -t hello-ai:keydemo .

First run the script without passing anything. The command after the image name replaces the image's CMD for this one run:

podman run --rm hello-ai:keydemo python show_key.py

Output

MY_API_KEY is not set

Way 1: an environment variable. Give it directly with -e, or put the same line into .env and pass the file. >> adds the line to the end of the file:

podman run --rm -e MY_API_KEY=12345 hello-ai:keydemo python show_key.py
echo 'MY_API_KEY=12345' >> .env
podman run --rm --env-file .env hello-ai:keydemo python show_key.py

Output of the two runs, on the test Mac

MY_API_KEY = 12345
MY_API_KEY = 12345

Way 2: a Podman secret. The first line stores 12345 in Podman under the name my_api_key. In the second, type=env means "hand it over as an environment variable", and target=MY_API_KEY is the name the script will see:

printf '12345' | podman secret create my_api_key -
podman run --rm --secret my_api_key,type=env,target=MY_API_KEY hello-ai:keydemo python show_key.py

Output of the run, on the test Mac

MY_API_KEY = 12345

The script is the same in all three runs, and it can't tell how the key arrived. What differs is where 12345 is kept outside the container: with way 1 it is in the container's settings, where podman inspect shows it; with way 2 it is not. Remove the example when you're done:

podman secret rm my_api_key
podman rmi hello-ai:keydemo

You can also delete show_key.py and the MY_API_KEY line in .env.

Clean up

podman rm -f api
podman secret rm api_key
podman images --filter dangling=true
podman image prune

podman images --filter dangling=true lists the unnamed <none> images left over from rebuilds, and podman image prune removes them after asking. You have a few from Lessons 2 and 3. Keep hello-ai:1.0: Lesson 4 uses it.

10Check yourself

Try answering each question out loud before opening it.

Q1Your image has no USER line. What does an attacker who finds a command-execution bug in your app get, and what changes with USER app?Show

Without USER they're root in the container: they can change your code, install tools and read everything, and on a rootful host that's root outside too. As app, they can't modify the code or install anything, and have much less to work with.

Q2A colleague passes a Hugging Face token with --build-arg HF_TOKEN=…, "so it's never saved in the image". Is that right?Show

No. The value is recorded in the image history; podman history --no-trunc shows it. Tokens should be supplied at run time, or with a build secret mount, never as build arguments.

Q3What's the difference between --env-file .env and --secret api_key,type=env,target=API_KEY, if the app sees the same variable either way?Show

Where the value is stored. With --env-file it's saved in the container's settings, and podman inspect shows it. With a Podman secret, only the secret's name is in the settings; the value is stored separately.

Q4You added a HEALTHCHECK, but podman ps never shows (healthy) or (starting). What's the first thing to check?Show

Whether the image was built with --format docker. In the default OCI format, Podman drops HEALTHCHECK with a warning in the build output.

Q5Your app prints "model loaded" at startup, but podman logs is empty, even though the API answers. What's going on?Show

Python is buffering its output because it's writing to a pipe, not a terminal. Set PYTHONUNBUFFERED=1 in the image.

Q6You pinned FROM to the digest that podman image inspect --format '{{.Digest}}' printed on your Mac. The CI server, which is amd64, now fails. Why?Show

That digest identifies only the arm64 variant, so the amd64 server was forced to use arm64 files. Pin the multi-platform index digest instead: the RepoDigests entry that isn't equal to .Digest.

Q7Your team's model image is 9 GB, and every deploy spends minutes pulling it. The weights are baked in. What are the other two options, and what do they cost?Show

Download the weights when the container starts (small image, but slow cold starts and a network dependency; pin the model version), or mount them from shared storage (fast starts and one shared copy, but the storage has to be managed separately).
