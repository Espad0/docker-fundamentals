From your Mac to AWS and Cloudflare

Until now every image lived on your Mac. This lesson takes hello-ai the rest of the way: into a registry, built for the right CPU, built automatically by GitLab CI, and running on AWS ECS Express Mode or Cloudflare Containers.

Reading about 45 minLab 30 min locally, plus optional real deploysUses hello-ai from Lesson 4Outputs from the test Mac, autumn 2026

By the end you should be able to

  • push and pull images to a registry, and tag them so you always know what's running
  • build linux/amd64 or multi-architecture images on your Apple-silicon Mac
  • read and adapt a GitLab CI pipeline that builds with Buildah and logs in to AWS without stored keys
  • deploy a container to AWS with ECS Express Mode, including settings and secrets
  • deploy the same image to Cloudflare Containers behind a Worker
  • choose between the two for a given app
What was tested

Everything that runs locally was tested on the test Mac: the registry, amd64 and multi-architecture builds, the GitLab build job (simulated with the same Buildah image), and the Cloudflare configuration (type-checked and dry-run deployed). The AWS and Cloudflare account steps are written from their current documentation, checked on 28 September 2026, and were not run against real accounts. They also create resources that cost money.

01From your Mac to production

In a team, nobody deploys images built on their laptop. You push code, and a pipeline builds, tests and publishes the image. That way every image is built the same way, from code everyone can see.

Why two registries? GitLab's built-in registry is free and needs no setup, so every commit's image goes there. Cloudflare can only pull from its own registry, Docker Hub, Amazon ECR or Google Artifact Registry, not GitLab's. So release images from main are copied to Amazon ECR, which both AWS and Cloudflare can use.

02Registries and tags

Step 1: run a registry on your Mac

A registry is just a server speaking the OCI distribution API (Lesson 1). The official one runs as a container, which makes it perfect for practice:

podman run -d --name registry -p 5050:5000 docker.io/library/registry:3

Step 2: name, push, and look

An image's name says where it lives (Lesson 1: registry, namespace, repository, tag). To push, give the image a name that starts with the registry's address:

podman tag hello-ai:2.0 localhost:5050/hello-ai:a1b2c3d4
podman push --tls-verify=false localhost:5050/hello-ai:a1b2c3d4
curl localhost:5050/v2/_catalog
curl localhost:5050/v2/hello-ai/tags/list

Output

{"repositories":["hello-ai"]}
{"name":"hello-ai","tags":["a1b2c3d4"]}

podman tag doesn't copy anything; it adds a second name to the same image. --tls-verify=false is only for this local practice registry, which has no HTTPS certificate. Real registries always use HTTPS.

Step 4: tag with the commit, not latest

The pipeline in section 4 names every image after the Git commit it was built from, such as hello-ai:a1b2c3d4. Then "what's running in production?" has an exact answer: that commit. Rolling back means deploying the previous tag. latest can't tell you either (Lesson 1). On ECR you can make tags immutable, so a tag can never be overwritten with a different image.

03Build for the server's CPU

Your Mac builds linux/arm64 images. Cloudflare Containers require linux/amd64, and ECS Express Mode also runs amd64 unless you choose ARM64 (Graviton) explicitly. An arm64 image on an amd64 server fails with exec format error (Lesson 1). Two ways to handle it:

Option A: build amd64 only

podman build --format docker --platform linux/amd64 -t hello-ai:2.0-amd64 .
podman image inspect hello-ai:2.0-amd64 --format '{{.Architecture}}'

Your Mac runs the amd64 build steps through emulation, which is slower. The hello-ai build took 46 seconds. It can even run the result: the amd64 image answered /health after about 12 seconds (emulated start-up is slow), with uname -m reporting x86_64 and Podman warning that the platform doesn't match. Use this to check an image, not to measure its speed.

Option B: one tag, both architectures

podman build --format docker --platform linux/amd64,linux/arm64 --manifest hello-ai:multi .
podman manifest inspect hello-ai:multi
podman manifest push --all --tls-verify=false hello-ai:multi docker://localhost:5050/hello-ai:1.0

podman manifest inspect (shortened)

application/vnd.oci.image.index.v1+json
  linux/amd64  sha256:66ed617c7b47…
  linux/arm64  sha256:b1876388efa4…

This is the same kind of multi-platform index as python:3.12-slim (Lesson 3, section 6): each machine pulls its own variant. It took 54 seconds. --all matters: without it, only the index is pushed, not the images it lists.

Which to use: build amd64 in CI for both targets. Add arm64 if you want to run on AWS Graviton, which is usually cheaper, or run the same tag on your Mac.

04The GitLab pipeline

GitLab reads .gitlab-ci.yml from the root of your repository. Each push starts a pipeline: jobs grouped into stages, and each job runs in a container you choose. Here's the full file, then the important parts:

Show the full .gitlab-ci.yml
# Build hello-ai on every push, publish it to Amazon ECR from the default
# branch, and deploy it to AWS or Cloudflare when someone presses "play".
stages: [test, build, release, deploy]

variables:
  IMAGE_TAG: $CI_COMMIT_SHORT_SHA   # every image is named after the commit it came from
  # Set these as CI/CD variables in GitLab (Settings > CI/CD > Variables):
  #   AWS_REGION, AWS_ROLE_ARN, ECR_REGISTRY, ECS_SERVICE_ARN,
  #   CLOUDFLARE_API_TOKEN (masked), CLOUDFLARE_ACCOUNT_ID

test:
  stage: test
  image: docker.io/library/python:3.12-slim
  script:
    - pip install --no-cache-dir -r requirements.txt
    - python -c "import main; print('app imports fine')"

build:
  stage: build
  image: quay.io/buildah/stable
  variables:
    STORAGE_DRIVER: vfs       # works inside a CI container without special storage
    BUILDAH_FORMAT: docker    # keeps HEALTHCHECK (Lesson 3)
  script:
    - echo "$CI_REGISTRY_PASSWORD" | buildah login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
    - buildah build --platform linux/amd64 -t "$CI_REGISTRY_IMAGE:$IMAGE_TAG" .
    - buildah push "$CI_REGISTRY_IMAGE:$IMAGE_TAG"

# Log in to AWS with a short-lived token instead of stored keys (OIDC).
.aws-login:
  id_tokens:
    GITLAB_OIDC_TOKEN:
      aud: https://gitlab.com   # your GitLab address, as registered in AWS IAM
  before_script:
    - command -v aws >/dev/null || dnf install -y -q awscli2
    - >
      aws_sts_output=$(aws sts assume-role-with-web-identity
      --role-arn "$AWS_ROLE_ARN"
      --role-session-name "gitlab-$CI_PROJECT_ID-$CI_PIPELINE_ID"
      --web-identity-token "$GITLAB_OIDC_TOKEN"
      --duration-seconds 3600
      --query 'Credentials.[AccessKeyId,SecretAccessKey,SessionToken]'
      --output text)
    - export $(printf "AWS_ACCESS_KEY_ID=%s AWS_SECRET_ACCESS_KEY=%s AWS_SESSION_TOKEN=%s" $aws_sts_output)

push-to-ecr:
  stage: release
  extends: .aws-login
  image: quay.io/buildah/stable
  variables:
    STORAGE_DRIVER: vfs
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH && $AWS_ROLE_ARN   # only once AWS is set up
  script:
    - echo "$CI_REGISTRY_PASSWORD" | buildah login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY"
    - aws ecr get-login-password --region "$AWS_REGION" | buildah login -u AWS --password-stdin "$ECR_REGISTRY"
    - buildah pull "$CI_REGISTRY_IMAGE:$IMAGE_TAG"
    - buildah tag "$CI_REGISTRY_IMAGE:$IMAGE_TAG" "$ECR_REGISTRY/hello-ai:$IMAGE_TAG"
    - buildah push "$ECR_REGISTRY/hello-ai:$IMAGE_TAG"

deploy-aws:
  stage: deploy
  extends: .aws-login
  image:
    name: public.ecr.aws/aws-cli/aws-cli:latest
    entrypoint: [""]
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH && $ECS_SERVICE_ARN
      when: manual              # a person decides when production changes
  script:
    - >
      aws ecs update-express-gateway-service
      --region "$AWS_REGION"
      --service-arn "$ECS_SERVICE_ARN"
      --primary-container "{\"image\":\"$ECR_REGISTRY/hello-ai:$IMAGE_TAG\",\"containerPort\":8000}"

deploy-cloudflare:
  stage: deploy
  image: docker.io/library/node:22-slim
  rules:
    - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH && $CLOUDFLARE_API_TOKEN
      when: manual
  script:
    - cd cloudflare
    - npm ci
    - sed -i "s|/hello-ai:[^\"]*\"|/hello-ai:$IMAGE_TAG\"|" wrangler.jsonc   # point at this commit's image
    - npx wrangler deploy
.gitlab-ci.yml, the important parts4 stages

Stages run in order; a failure stops the pipeline. CI_COMMIT_SHORT_SHA is one of GitLab's predefined variables: the commit's short ID, used as the tag.

build: image: quay.io/buildah/stable variables: STORAGE_DRIVER: vfs BUILDAH_FORMAT: docker

The build job runs in the official Buildah image. Buildah is the engine inside podman build, so CI builds exactly like your Mac, with no Docker needed. GitLab's documentation recommends it. BUILDAH_FORMAT: docker keeps your HEALTHCHECK (Lesson 3).

script: - echo "$CI_REGISTRY_PASSWORD" | buildah login -u "$CI_REGISTRY_USER" --password-stdin "$CI_REGISTRY" - buildah build --platform linux/amd64 -t "$CI_REGISTRY_IMAGE:$IMAGE_TAG" . - buildah push "$CI_REGISTRY_IMAGE:$IMAGE_TAG"

GitLab supplies a short-lived registry password and your project's image name. Build for amd64, push to GitLab's registry.

.aws-login: id_tokens: GITLAB_OIDC_TOKEN: aud: https://gitlab.com

A reusable piece (the leading dot means "not a job"). GitLab issues a signed token that says which project and branch this job runs for. AWS trusts it (section 5), so no AWS keys are stored in GitLab. If your company runs its own GitLab, use its address.

before_script: - …aws sts assume-role-with-web-identity --role-arn "$AWS_ROLE_ARN" --web-identity-token "$GITLAB_OIDC_TOKEN" … - export $(printf "AWS_ACCESS_KEY_ID=%s …" $aws_sts_output)

Swap the token for temporary AWS credentials valid for one hour. This is GitLab's documented pattern.

push-to-ecr: extends: .aws-login rules: - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH && $AWS_ROLE_ARN

Only on main, and only once AWS_ROLE_ARN has been set up, so the pipeline works before AWS is configured. It copies the tested image from GitLab's registry to ECR.

deploy-aws: … rules: - if: … && $ECS_SERVICE_ARN when: manual

when: manual adds a ▶ button in GitLab: production only changes when a person clicks it. The script runs aws ecs update-express-gateway-service with the new image.

deploy-cloudflare: image: docker.io/library/node:22-slim script: - cd cloudflare - npm ci - sed -i "s|/hello-ai:[^\"]*\"|/hello-ai:$IMAGE_TAG\"|" wrangler.jsonc - npx wrangler deploy

Points the Cloudflare configuration at this commit's image, then deploys. Needs CLOUDFLARE_API_TOKEN and CLOUDFLARE_ACCOUNT_ID as CI/CD variables.

Runners

Buildah was run with --privileged. On GitLab.com's hosted runners that works. On a company's own runners, Buildah may need the runner to allow it. If the build job fails with permission or "unshare" errors, ask whoever manages your runners.

Set these under Settings → CI/CD → Variables: AWS_REGION, AWS_ROLE_ARN, ECR_REGISTRY, ECS_SERVICE_ARN, CLOUDFLARE_ACCOUNT_ID, and CLOUDFLARE_API_TOKEN (marked masked so it never appears in logs).

05One-time AWS setup

Done once per account, usually by whoever manages AWS. Replace 123456789012 with your account ID, eu-west-1 with your region, and mygroup/hello-ai with your GitLab project path.

1. A repository for the images

aws ecr create-repository --repository-name hello-ai --image-tag-mutability IMMUTABLE --region eu-west-1

2. Let AWS trust GitLab's tokens

aws iam create-open-id-connect-provider --url https://gitlab.com --client-id-list https://gitlab.com

The client ID must equal the aud in .gitlab-ci.yml.

3. A role that only your project's main branch can use

Save as gitlab-trust.json. The condition is the security boundary: other projects, and other branches of yours, can't use this role.

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": { "Federated": "arn:aws:iam::123456789012:oidc-provider/gitlab.com" },
    "Action": "sts:AssumeRoleWithWebIdentity",
    "Condition": {
      "StringEquals": {
        "gitlab.com:sub": "project_path:mygroup/hello-ai:ref_type:branch:ref:main"
      }
    }
  }]
}
aws iam create-role --role-name gitlab-ci-hello-ai --assume-role-policy-document file://gitlab-trust.json
aws iam attach-role-policy --role-name gitlab-ci-hello-ai \
  --policy-arn arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryPowerUser

That covers pushing to ECR. The deploy-aws job also needs permission to update your Express service. Ask your AWS admin to add a policy scoped to that one service; if something is missing, AWS's error message names the exact permission.

4. The two roles ECS Express Mode needs

From AWS's getting-started guide: an execution role (lets ECS pull your image and write logs) and an infrastructure role (lets ECS create the load balancer and networking):

aws iam create-role --role-name ecsTaskExecutionRole --assume-role-policy-document \
  '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ecs-tasks.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
aws iam attach-role-policy --role-name ecsTaskExecutionRole \
  --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSTaskExecutionRolePolicy

aws iam create-role --role-name ecsInfrastructureRoleForExpressServices --assume-role-policy-document \
  '{"Version":"2012-10-17","Statement":[{"Effect":"Allow","Principal":{"Service":"ecs.amazonaws.com"},"Action":"sts:AssumeRole"}]}'
aws iam attach-role-policy --role-name ecsInfrastructureRoleForExpressServices \
  --policy-arn arn:aws:iam::aws:policy/service-role/AmazonECSInfrastructureRoleforExpressGatewayServices

New roles take about a minute to become usable. If the next command says it can't assume a role, wait and retry.

06Deploy to AWS with ECS Express Mode

AWS used to recommend App Runner for "just run my container". App Runner stopped accepting new customers on 30 April 2026. Its replacement is Amazon ECS Express Mode, launched in November 2025. With one command it creates a Fargate service, a load balancer with HTTPS, a URL, autoscaling, logging and alarms. It costs nothing extra; you pay for what it creates. The load balancer costs money even when idle.

Step 1: store the secret

aws secretsmanager create-secret --name hello-ai/api-key --secret-string 'your-real-key' --region eu-west-1

The execution role must be allowed to read it (secretsmanager:GetSecretValue on this secret). The standard execution policy doesn't include that, so add it. ECS then passes the value in as an environment variable, the AWS version of Lesson 3's Podman secret.

Step 2: create the service

aws ecs create-express-gateway-service \
  --region eu-west-1 \
  --service-name hello-ai \
  --execution-role-arn arn:aws:iam::123456789012:role/ecsTaskExecutionRole \
  --infrastructure-role-arn arn:aws:iam::123456789012:role/ecsInfrastructureRoleForExpressServices \
  --primary-container '{
    "image": "123456789012.dkr.ecr.eu-west-1.amazonaws.com/hello-ai:a1b2c3d4",
    "containerPort": 8000,
    "environment": [{"name": "MODEL_NAME", "value": "keyword-sentiment-v1"}],
    "secrets": [{"name": "API_KEY", "valueFrom": "arn:aws:secretsmanager:eu-west-1:123456789012:secret:hello-ai/api-key-AbCdEf"}]
  }' \
  --health-check-path /health \
  --cpu 512 --memory 1024 \
  --monitor-resources
SettingWhy it's there
"containerPort": 8000The default is 80. Without this, the load balancer knocks on a port nobody listens on.
--health-check-path /healthThe default is /ping, which hello-ai doesn't have, so every task would be marked unhealthy. For hello-model, use /health/ready (Lesson 5).
environment and secretsLesson 3's run-time settings. The secret's value never appears in the service definition, only its ARN.
--cpu 512 --memory 10240.5 vCPU and 1 GB, in AWS's units. For hello-model, set memory from your Lesson 5 measurements, and add OMP_NUM_THREADS to match the CPU.

When the status reaches ACTIVE, the app is at https://<service-name>.ecs.<region>.on.aws/. Logs go to CloudWatch. To inspect or remove it later:

aws ecs describe-express-gateway-service --service-arn SERVICE_ARN
aws ecs monitor-express-gateway-service --service-arn SERVICE_ARN
aws ecs delete-express-gateway-service --service-arn SERVICE_ARN

Updates come from the pipeline's deploy-aws job. Express Mode rolls out the new version gradually and rolls back automatically if error rates rise.

Your database

Lesson 4's Postgres becomes Amazon RDS for PostgreSQL in production. Pass its address as DATABASE_URL, with the password in Secrets Manager. hello-ai works without a database too: /health reports "database":"not configured".

07Deploy to Cloudflare Containers

Cloudflare Containers is generally available on the Workers Paid plan. It works differently from AWS: your container sits behind a Worker, Cloudflare's small serverless function. The Worker receives every request and forwards it to a container instance, which starts on demand and goes to sleep when idle.

Instance typevCPUMemoryDisk
lite1/16256 MiB2 GB
basic1/41 GiB4 GB
standard-11/24 GiB8 GB
standard-216 GiB12 GB
standard-328 GiB16 GB
standard-4412 GiB20 GB
  • Images must be linux/amd64, and an image can't be bigger than the instance's disk.
  • Disk is temporary: when an instance sleeps, it wakes with a fresh disk from the image. Keep data in a database or R2, and bake models into the image (Lesson 5, section 8).
  • Only HTTP reaches the container, through the Worker.
Podman

By default, wrangler deploy builds your image with the Docker command-line tool, and Cloudflare's docs say Docker must be running. Building with Podman is a known problem (Podman doesn't accept a flag wrangler passes, reported as workers-sdk issue #9755). The way around it, and the better practice anyway: point wrangler at an image already in a registry. Then no local build happens at deploy time. ECR from section 5 is one of the supported registries.

Step 1: create the project from Cloudflare's template

npm create cloudflare@latest cloudflare -- --template=cloudflare/templates/containers-template --no-deploy --git=false

Run it in ~/practice/hello-ai. It creates a cloudflare folder with a Worker, a sample container and wrangler.jsonc. Replace two files with the versions below. The sample container isn't needed, because we use our image.

Add cloudflare/ to .containerignore straight away. The folder contains node_modules, and COPY . . would otherwise put it into your image.

Step 2: the Worker

import { Container, getContainer } from "@cloudflare/containers";
import { env } from "cloudflare:workers";

// One class describes the container: which port it listens on, when it may
// sleep, and which settings it receives (like `-e` in podman run).
export class HelloAi extends Container<Env> {
	defaultPort = 8000;
	sleepAfter = "10m";
	envVars = {
		MODEL_NAME: env.MODEL_NAME,
		API_KEY: env.API_KEY, // a Worker secret: npx wrangler secret put API_KEY
	};
}

// The Worker receives every request and forwards it to the container.
export default {
	async fetch(request: Request, env: Env): Promise<Response> {
		return getContainer(env.HELLO_AI).fetch(request);
	},
};
  • class HelloAi extends Container describes the container: port 8000, sleep after 10 idle minutes, and the environment variables it gets, like -e in podman run.
  • getContainer(env.HELLO_AI) returns one shared instance. Cloudflare's template also shows spreading requests over several instances with getRandom.

Step 3: the configuration

{
	"$schema": "node_modules/wrangler/config-schema.json",
	"name": "hello-ai",
	"main": "src/index.ts",
	"compatibility_date": "2025-10-08",
	"compatibility_flags": ["nodejs_compat"],
	"observability": { "enabled": true },
	"vars": { "MODEL_NAME": "keyword-sentiment-v1" },
	"containers": [
		{
			"class_name": "HelloAi",
			// A prebuilt linux/amd64 image in Amazon ECR (built by GitLab CI)
			"image": "123456789012.dkr.ecr.eu-west-1.amazonaws.com/hello-ai:1.0",
			"instance_type": "basic",
			"max_instances": 3
		}
	],
	"durable_objects": {
		"bindings": [{ "class_name": "HelloAi", "name": "HELLO_AI" }]
	},
	"migrations": [{ "new_sqlite_classes": ["HelloAi"], "tag": "v1" }]
}

image is the ECR address, not a Dockerfile. durable_objects and migrations are how Cloudflare keeps track of container instances; they come from the template, renamed.

Step 4: check it without an account

cd cloudflare
printf 'API_KEY=local-dev-not-a-real-key\n' > .dev.vars
npx wrangler types
npx tsc --noEmit
npx wrangler deploy --dry-run

.dev.vars holds local stand-ins for secrets; wrangler types reads it to know API_KEY exists. The template's .gitignore already keeps .dev.vars out of Git.

Step 5: deploy for real

npx wrangler login
npx wrangler containers registries configure 123456789012.dkr.ecr.eu-west-1.amazonaws.com --aws-access-key-id=AKIA…
npx wrangler secret put API_KEY
npx wrangler deploy
npx wrangler containers list

The registry command stores read-only AWS credentials so Cloudflare can pull from ECR; give that key permission to pull only. The first deploy takes a few minutes to be ready. The app is then at https://hello-ai.<your-subdomain>.workers.dev. The first request after a sleep starts the container, so expect a few seconds' delay then.

08AWS or Cloudflare?

ECS Express ModeCloudflare Containers
When it runsAlways at least one task; scales with loadStarts on request, sleeps when idle
Cold startsNone while a task runsA few seconds after a sleep
SizesFargate sizes, far beyond 4 vCPU and 12 GiBUp to 4 vCPU, 12 GiB (standard-4)
DiskTemporary; add EFS for shared filesTemporary, reset on every sleep
DatabasesRDS in the same private networkExternal Postgres through Hyperdrive, or D1
GPUsNo (Fargate). Use EC2 GPU instances.No. Use Workers AI.
You also getLoad balancer, HTTPS, autoscaling, rollbacks, CloudWatchCloudflare's global network, Workers in front for routing and auth
Paying forRunning tasks and the load balancer, even when idleOnly while instances run, plus the Workers Paid plan

A rough rule: steady traffic, a Postgres database and larger models point to AWS. Spiky or low traffic, where scaling to zero saves money, and apps already on Cloudflare point to Cloudflare. Either way, the image is the same. That's the promise from Lesson 1, and it holds.

10Check yourself

Try answering each question out loud before opening it.

Q1Why tag images with the commit ID instead of latest or v1?Show

A commit ID identifies exactly which code is running, can't accidentally be reused for different code, and makes rollback a matter of deploying the previous tag. With immutable tags in ECR, it can't be overwritten either.

Q2Your Mac-built image deploys to Cloudflare and fails immediately. What's the first thing you check?Show

The architecture. Macs build linux/arm64; Cloudflare Containers require linux/amd64. Build with --platform linux/amd64 (as the pipeline does) or as a multi-architecture index.

Q3You pushed a multi-architecture image, but the server says there's no amd64 variant. What was probably forgotten?Show

--all on podman manifest push. Without it, only the index was pushed, not the per-platform images it points to.

Q4How does the pipeline get into AWS without an AWS key stored in GitLab? And why can't another project use the same role?Show

GitLab issues a signed OIDC token for each job (id_tokens), and assume-role-with-web-identity exchanges it for credentials valid for one hour. The role's trust policy only accepts tokens whose sub is your project's main branch.

Q5You created an ECS Express service for hello-ai with just an image. Tasks keep being replaced and the URL never works. Which two defaults bit you?Show

The container port defaults to 80 (hello-ai listens on 8000), and the health-check path defaults to /ping (hello-ai has /health). Set containerPort and --health-check-path.

Q6Why does the Cloudflare configuration point at an ECR image instead of the Containerfile?Show

With a Containerfile, wrangler deploy builds the image locally with Docker, which doesn't work with Podman. With a registry image, no build happens at deploy time, and Cloudflare runs exactly the image your pipeline built and tested.

Q7hello-model downloads its weights at start-up into its disk. It works on AWS, but on Cloudflare every first request after a quiet period is very slow. Why?Show

Cloudflare instances sleep when idle and wake with a fresh disk, so the model is downloaded again on every wake-up. Bake the model into the image for Cloudflare.

Q8Your app gets steady traffic all day, uses Postgres, and needs 16 GB of memory. AWS or Cloudflare?Show

AWS. Cloudflare's largest instance is 12 GiB, steady traffic gains nothing from scaling to zero, and RDS can sit in the same private network as the service.
