Building your first image

In Lesson 1 you used images other people built. Now you'll write the recipe yourself, and learn the handful of rules that decide whether your builds are fast, your images are clean, and your app actually answers when you call it.

Reading about 30 minLab about 30 minPractice app ~/practice/hello-aiOutputs from the test Mac, autumn 2026

By the end you should be able to

  • write a Containerfile for a Python web service and explain every line
  • say which instructions run at build time and which at run time
  • keep secrets and junk out of an image with .containerignore
  • order instructions so a code change rebuilds in under a second
  • explain why podman stop sometimes takes 10 seconds, and fix it
  • run your image so it's reachable from your Mac, and debug it when it isn't

01Build time and run time

An image goes through two separate moments, often on different machines and days apart:

  • Build time: podman build reads your Containerfile and executes it step by step. Each step that changes files is saved as a layer. The result is an image: layers plus a config, exactly like the python.tar you unpacked.
  • Run time: podman run takes the finished image and starts a container from it. Only now does the default command run.

RUN does work now; CMD leaves a note for later

A Containerfile mixes two kinds of lines:

  • RUN: do this now, while building the image, and keep whatever files it creates.
  • CMD: write down which program to start later, whenever a container is started.

Think of setting up a laptop for a colleague. You install all the software yourself; that's RUN, done once, and what remains is files on the disk. Then you stick a note on the lid saying "double-click Server to start"; that's CMD. Writing the note doesn't start anything. The server only starts when your colleague opens the laptop, and it starts again every time they do.

Example: the same command at build time and at run time

This Containerfile calls date twice, once in RUN and once in CMD:

FROM docker.io/library/python:3.12-slim
RUN date > /built-at.txt
CMD ["sh", "-c", "echo \"built at: $(cat /built-at.txt)\"; echo \"now:      $(date)\""]

Built on the test Mac, with two containers started a few seconds apart:

Output

built at: Sun Sep 27 21:28:21 UTC 2026
now:      Sun Sep 27 21:28:25 UTC 2026
---
built at: Sun Sep 27 21:28:21 UTC 2026    ← same as before
now:      Sun Sep 27 21:28:27 UTC 2026    ← changed
  • The RUN date line ran once, during the build, at 21:28:21. The only thing kept was the file it wrote, /built-at.txt, saved as a 2 kB layer. Every container from this image sees that same frozen time.
  • The date inside CMD did nothing during the build; it was stored in the image's config. It runs fresh each time a container starts, which is why "now" is different every time.

What RUN keeps and what it throws away

For each RUN line, the builder:

  1. starts a temporary container from the image built so far,
  2. runs your command inside it,
  3. waits for the command to finish,
  4. saves the files that changed as a new layer,
  5. throws the temporary container away, including any programs still running in it.

So an image contains files, never running programs. RUN pip install fastapi works because what you need afterwards is files: the installed package. RUN service postgresql start achieves nothing: the database starts, the step ends, and the running database is thrown away with the temporary container.

Example: RUN uvicorn never finishes

Look at step 3 above: the builder waits for the command to finish. pip install finishes after a few seconds. A web server is designed to never finish; it keeps running until someone stops it. Here is the practice app with the server start wrongly placed in RUN:

COPY main.py .
RUN uvicorn main:app --host 0.0.0.0 --port 8000

On the test Mac, the build output got this far and then stopped:

Output

STEP 6/6: RUN uvicorn main:app --host 0.0.0.0 --port 8000
INFO:     Started server process [2]
INFO:     Application startup complete.
INFO:     Uvicorn running on http://0.0.0.0:8000 (Press CTRL+C to quit)

After 30 seconds it was still there, and it would have waited forever:

  • The builder is waiting for step 6 to finish so it can save the layer.
  • Uvicorn is doing its job: running and waiting for requests.
  • Nobody can send it any, because this is a build step, not a container with a published port.
  • The image never gets created.

If this happens to you, stop the build with Ctrl+C. Then run podman ps -a --external, which also lists temporary build containers, to check nothing was left behind. On the test Mac, a build stopped this way kept running inside the Podman VM and had to be cleaned up there too.

The correct version splits the two jobs:

RUN pip install --no-cache-dir -r requirements.txt                   # build time: finishes, leaves files
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]   # run time: starts with each container

How to decide for any line

Ask: "Should this happen once, when the image is made, and leave files behind? Or every time a container starts, and keep running?"

TaskWhere it goesWhy
Install Python or system packagesRUNOnce; the result is files
Compile code, download files you want in the imageRUNOnce; the result is files
Start the web serverCMDMust run for the whole life of the container
Run database migrationsAt container start, not RUNThe real database only exists at run time
Read an API key or other settingsAt run time (-e)Values differ per environment and must not be in the image

02A Containerfile, line by line

Here is the complete Containerfile for the practice app, a small FastAPI service. It's seven instructions, and each one is a choice worth understanding. The tag on each line shows whether it adds a layer of files or only changes a config setting.

hello-ai/Containerfile7 instructions
FROM docker.io/library/python:3.12-slim

layersStart from this image. All of its layers become the bottom of yours. It must be the first instruction.

WORKDIR /app

configSet the current directory for the following instructions and for the running container. Creates /app if it doesn't exist.

COPY requirements.txt .

layerCopy one file from the build context into /app (. means the WORKDIR). Only the dependency list, on purpose: see section 4.

RUN pip install --no-cache-dir -r requirements.txt

layerRun a command during the build, inside a temporary container, and save the files it changed: 24 MB of packages here. --no-cache-dir stops pip leaving its download cache in the layer.

COPY . .

layerCopy the entire build context into /app: your code, and anything else in the folder that isn't excluded.

EXPOSE 8000

configDocument the port the app listens on. It doesn't open or publish anything.

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]

configThe default command, stored for run time. The square-bracket form and 0.0.0.0 both matter; sections 5 and 6 explain why.

After a build, podman history hello-ai:0.1 confirms the split: the RUN line is 23.8 MB, the two COPY lines are a few kB, and WORKDIR, EXPOSE and CMD are 0 B. The finished image is 173 MB: 149 MB of python:3.12-slim plus your 24 MB.

03The build context and .containerignore

The dot at the end of podman build -t hello-ai:0.1 . is not decoration. It's the build context: the folder whose files the build can see. COPY paths are relative to it, and nothing outside it is reachable, so COPY ../secrets.txt . fails.

COPY . . copies the whole context. Built without an ignore file, the practice app's image contained this:

$ podman run --rm hello-ai:0.1 ls -a /app
.  ..  .env  Containerfile  main.py  requirements.txt

$ podman run --rm hello-ai:0.1 cat /app/.env
API_KEY=not-a-real-key-just-for-the-lesson

The .env file with the API key is in the image. Anyone who can pull it can read the key, and as Lesson 1 showed, deleting it in a later step doesn't remove it from the earlier layer. In a real project the same line would also copy .git, your virtualenv, notebooks, caches and any model files lying around.

The fix is a .containerignore file next to the Containerfile. It lists what to leave out of the context, one pattern per line. Podman also reads .dockerignore, which uses the same syntax.

# secrets and local settings
.env
.env.*
# version control, virtualenvs, Python caches
.git
.venv
**/__pycache__
**/*.pyc
# build files the running app doesn't need
Containerfile
.containerignore

With this file in place, /app contains only main.py and requirements.txt. **/ matches at any depth, so a __pycache__ folder inside a subfolder is excluded too.

Rule

Create .containerignore before your first COPY . ., not after. It keeps secrets out, keeps images small, and keeps builds fast, because excluded files are never processed and changes to them never invalidate the cache.

04The layer cache

Every layer the builder creates is kept. On the next build, it walks the Containerfile from the top and asks, for each instruction, "have I already built exactly this, on top of exactly the same layer?"

  • For RUN, "exactly this" means the same command text.
  • For COPY and ADD, it also means the copied files have the same contents.
  • If the answer is yes, the stored layer is reused and the output says Using cache. At the first no, that step and every step after it are rebuilt, because each layer sits on top of the one before.

Here is the real output of rebuilding the practice app after editing only main.py:

STEP 2/7: WORKDIR /app
--> Using cache 8a9a2edd78f7…
STEP 3/7: COPY requirements.txt .
--> Using cache 8466a0c9008b…
STEP 4/7: RUN pip install --no-cache-dir -r requirements.txt
--> Using cache 1f91524495ec…
STEP 5/7: COPY . .
--> 5e307e1b4a4b              # main.py changed: rebuilt from here down

Order instructions from least to most frequently changed

Your code changes many times a day. Your dependency list changes occasionally. The base image changes rarely. Put them in that order, from the top, and the expensive pip install stays cached while you work. Here is the same edit to main.py with the two possible orders, timed on the test Mac:

Dependencies first recommended

  • FROM python:3.12-slim cached
  • COPY requirements.txt . cached
  • RUN pip install … cached
  • COPY . . rebuilt
0.7 srebuild after editing main.py

Code first slow

  • FROM python:3.12-slim cached
  • COPY . . rebuilt
  • RUN pip install … reinstalled
6.0 severy edit reinstalls every package

With two small packages the difference is seconds. With torch and transformers, the right-hand column means several minutes and gigabytes of downloads on every code change.

Two traps, because the cache only looks at text

  • The cache doesn't know the internet changed. RUN pip install -r requirements.txt stays cached even after new package versions are released, because the command text is the same. This is one reason to pin exact versions (fastapi==0.141.1): the image you get shouldn't depend on whether a step happened to be cached. When you want fresh packages, such as security updates, rebuild with podman build --no-cache.
  • Keep apt-get update and apt-get install in one RUN. On separate lines, the update layer gets cached with a package list that goes stale. Months later someone adds a package to the install line, the install step rebuilds against the old list, and fails with 404 Not Found. The standard pattern is below. Cleaning up in the same step keeps the list files out of the layer.
RUN apt-get update \
 && apt-get install -y --no-install-recommends ffmpeg \
 && rm -rf /var/lib/apt/lists/*

05CMD, ENTRYPOINT and the exec form

CMD can be written two ways, and they behave differently at run time:

  • Exec form, a JSON list: CMD ["uvicorn", "main:app", "--host", "0.0.0.0"]. Podman starts uvicorn directly, so uvicorn is PID 1.
  • Shell form, plain text: CMD uvicorn main:app --host 0.0.0.0. Podman runs /bin/sh -c "uvicorn …", so the shell is PID 1 and uvicorn is its child.

Remember from Lesson 1 that podman stop sends SIGTERM to PID 1 and waits 10 seconds before killing. The shell doesn't pass SIGTERM on to uvicorn, so nothing reacts. Both were measured on the test Mac:

Exec form

CMD ["uvicorn", "main:app", …]
PID 1
uvicorn main:app …
podman stop
0.4 s
Status
Exited (0), clean shutdown

Shell form

CMD uvicorn main:app …
PID 1
/bin/sh -c uvicorn …
podman stop
10.2 s
Status
Exited (137), killed

The 137 means every deployment and every restart kills your app mid-request instead of letting it finish. Always use the exec form for CMD and ENTRYPOINT. Shell form is fine for RUN, because build steps aren't stopped with signals.

Watch the quotes

The exec form is JSON, so it needs double quotes. CMD ['uvicorn', 'main:app'] isn't valid JSON, and the builder quietly treats the whole line as shell form, bringing back the 10-second stop.

ENTRYPOINT vs CMD

When both are set, ENTRYPOINT is the program and CMD supplies its default arguments. Anything you type after the image name in podman run replaces only the CMD part:

Containerfilepodman run imagepodman run image --port 9000
CMD ["uvicorn", "main:app", "--port", "8000"]uvicorn on port 8000Error: tries to run a program called --port
ENTRYPOINT ["uvicorn", "main:app"]
CMD ["--port", "8000"]		uvicorn on port 8000uvicorn on port 9000

For a web service, a single exec-form CMD is the simplest choice: it's easy to read and easy to override when debugging, for example podman run -it hello-ai:0.1 bash. Reach for ENTRYPOINT when the image is really one tool, such as a CLI that always runs with different arguments.

06Tags, ports and environment variables

Tags

-t hello-ai:0.1 names the image. Because the name has no registry in front, Podman stores it as localhost/hello-ai:0.1, which is what podman images shows. Give each build a version tag instead of relying on latest, so you always know which build is running and can go back to the previous one. Pushing to a registry comes in a later lesson.

Ports: -p publishes, EXPOSE doesn't

A container has its own network namespace, with its own network interface and its own ports. Your Mac can't reach them until you publish a port with -p host:container. -p 8000:8000 forwards port 8000 on your Mac to port 8000 in the container. On macOS the traffic passes through the Podman VM on the way, but you don't have to do anything about that. EXPOSE in the Containerfile publishes nothing: without -p, curl localhost:8000 fails with Couldn't connect to server.

Why the app must listen on 0.0.0.0

Inside the container, 127.0.0.1 means the container's own loopback interface, not your Mac. Forwarded traffic arrives on the container's network interface, so a server that listens only on 127.0.0.1 never sees it.

Many frameworks default to 127.0.0.1 because that's safe on a laptop, so this bites almost everyone once. If the app works from inside the container (podman exec) but not from outside, check the host address first.

Environment variables

Settings that differ between environments don't belong in the image. Pass them when the container starts with -e. The practice app reads MODEL_NAME, so the same image can report a different model:

podman run -d -p 8000:8000 -e MODEL_NAME=sentiment-v2 hello-ai:0.1
curl localhost:8000/health   # {"status":"ok","model":"sentiment-v2"}

This is also how API keys should reach your app: at run time, from outside the image. Lesson 3 covers doing that safely in production.

07Command reference

08Lab: containerize hello-ai

The practice app is in ~/practice/hello-ai, where the setup step put it. It is a FastAPI service with /health and /predict, a pinned requirements.txt, and a .env with a fake API key. Your job is to write the container files. Try each step before opening its solution.

1

Look at the app

cd ~/practice/hello-ai
ls -a
cat main.py requirements.txt
2

Write the Containerfile

Create ~/practice/hello-ai/Containerfile that:

  • starts from docker.io/library/python:3.12-slim
  • works in /app
  • installs the dependencies in a way that stays cached when only code changes
  • copies the code
  • documents port 8000
  • starts uvicorn on 0.0.0.0:8000, in the form that stops cleanly
Show solution
FROM docker.io/library/python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
3

Build it

podman build -t hello-ai:0.1 .

The first build takes about 10 seconds. Read the output: you'll see STEP 1/7 to STEP 7/7, pip installing packages, and a warning that pip is running as root. That warning is harmless in an image build; Lesson 3 explains why. Then look at what you made:

podman images hello-ai
podman history hello-ai:0.1
4

Run it and call it

podman run -d --name api -p 8000:8000 hello-ai:0.1
curl localhost:8000/health
curl -X POST localhost:8000/predict -H 'Content-Type: application/json' -d '{"text": "the new build is fast and it works"}'
podman logs api

You should get {"status":"ok",…} and a "positive" prediction, and the logs show both requests. Also open localhost:8000/docs in your browser: that's FastAPI's interactive API page, served from inside the container.

Find the leak, then fix it

podman run --rm hello-ai:0.1 cat /app/.env

Your fake API key is inside the image. Write a .containerignore that keeps it out, along with anything else that doesn't belong. Then build hello-ai:0.2 and run the two commands above against it.

6

Watch the cache work

Add a word to POSITIVE in main.py (for example "amazing"), then rebuild and time it:

time podman build -t hello-ai:0.3 .

Steps 2 to 4 should say Using cache, and the build should take about a second. For comparison, move COPY . . above the pip install line, edit main.py again and rebuild: pip reinstalls everything. Put the order back when you're done.

7

Time the stop signal

time podman stop api
podman ps -a --filter name=api

Well under a second, Exited (0). Now start the same image through a shell, which is exactly what a shell-form CMD does, and stop it:

podman run -d --name api-shell -p 8001:8000 hello-ai:0.1 sh -c "uvicorn main:app --host 0.0.0.0 --port 8000"
time podman stop api-shell
podman ps -a --filter name=api-shell

About 10 seconds, Exited (137).

8

Break the networking on purpose

podman run -d --name api-lo -p 8002:8000 hello-ai:0.1 uvicorn main:app --host 127.0.0.1 --port 8000
curl localhost:8002/health
podman exec api-lo python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/health').read())"

From your Mac: Connection reset by peer. From inside the container: it works. That combination always points to the listen address.

9

Clean up

podman rm -f api api-shell api-lo
podman rmi hello-ai:0.1 hello-ai:0.2

Keep hello-ai:0.3 and the project folder: Lesson 3 builds on them.

09Check yourself

Try answering each question out loud before opening it.

Q1What's the difference between RUN and CMD? What happens if you write RUN uvicorn main:app?Show

RUN executes during the build and saves the changed files as a layer. CMD only records the command that starts when a container runs. RUN uvicorn main:app starts the server during the build; it never exits, so the build hangs.

Q2A Containerfile has COPY . . before RUN pip install. You change one line in main.py. What gets rebuilt, and why?Show

The COPY . . step, because a copied file changed, and then every step after it, including the full pip install. Copy requirements.txt and install first, then copy the code.

Q3Your image contains .env, but the Containerfile never mentions it. How did it get there, and is adding RUN rm /app/.env a fix?Show

COPY . . copies the whole build context, including .env. Deleting it in a later step only hides it; the file is still in the COPY layer and anyone with the image can extract it. The fix is to exclude it in .containerignore, and to change the key if the image was ever pushed.

Q4Your API works when you call it with podman exec from inside the container, but curl from your Mac says "Connection reset by peer". What's the most likely cause?Show

The server listens on 127.0.0.1, the container's own loopback, so traffic forwarded to the container's network interface never reaches it. Start it with --host 0.0.0.0.

Q5Your Containerfile has EXPOSE 8000, but curl localhost:8000 can't connect at all. What's missing?Show

Publishing the port. EXPOSE is documentation only; you need -p 8000:8000 on podman run.

Q6podman stop always takes 10 seconds and the container ends with exit code 137. What do you look for in the Containerfile?Show

A shell-form CMD or ENTRYPOINT, including one written with single quotes. The shell is PID 1, doesn't pass SIGTERM on, and gets killed after the grace period. Switch to the exec form with double quotes.

Q7A colleague has RUN apt-get update and RUN apt-get install -y ffmpeg on separate lines. Months later they add a package to the install line and the build fails with 404 errors. Why?Show

The update layer was reused from the cache, with a months-old package list. The changed install step rebuilt against that stale list and asked for package versions the mirrors no longer have. Keep update and install in one RUN.

Q8Your image uses ENTRYPOINT ["python", "train.py"] and CMD ["--epochs", "3"]. What runs for podman run img, and for podman run img --epochs 10?Show

python train.py --epochs 3, then python train.py --epochs 10. Arguments after the image name replace CMD; ENTRYPOINT stays.
