Keeping data and connecting containers

Real AI apps are rarely one container. There's an API, a database, maybe a vector store or a cache, and data that must survive when containers are replaced. This lesson gives hello-ai a Postgres database, connects the two, and starts the whole thing with one command.

Reading about 30 minLab about 40 minStarts from your Lesson 3 imageOutputs from the test Mac, autumn 2026

By the end you should be able to

  • keep data when containers are removed, using named volumes
  • share a folder from your Mac with a container, and know when that's the right tool
  • let containers find each other by name on a network
  • describe a multi-container app in compose.yaml and start it with one command
  • make services wait until the ones they depend on are actually ready
  • tell which Compose commands keep your data and which delete it

01Containers forget

Lesson 1's key rule: when a container is removed, its writable layer goes with it. A new deployment replaces your containers, so anything they wrote is gone. For an AI app that includes things you really want to keep:

  • the database: users, conversations, predictions,
  • documents users uploaded for a RAG system, and the vector index built from them,
  • model weights you downloaded once and don't want to download on every start.

So this data has to be kept outside the container. There are two kinds of answer:

  1. Keep a folder outside the container. Podman stores the contents of one folder somewhere else and shows that folder inside the container. The app reads and writes ordinary files and notices no difference.
  2. Send the data to another service. The app sends the data over the network to a program that stores it: a database, or file storage such as Amazon S3. Podman takes no part in this, and the app's container keeps nothing.

For the first kind, Podman offers two ways:

  • Named volume: storage that Podman creates and manages. You refer to it by name. Use it for data the app owns, like a database.
  • Bind mount: a folder from your Mac, made visible inside the container. Use it when you want to see or edit the files yourself, like your code during development.

The lab gives hello-ai a database called Postgres, which runs in a second container. A database is a program whose job is to store data. Section 4 explains what Postgres is and why it gets a container of its own.

This lesson uses both kinds:

  • Postgres keeps its files in a named volume, which is the first kind. Sections 2 and 3 cover volumes and bind mounts.
  • hello-ai keeps its predictions by sending them to Postgres, which is the second kind. It has no volume of its own. Section 4, step 4 shows this running, and section 8 explains why it is the usual choice in production.

02Named volumes

What a volume is

A volume is a folder that Podman keeps outside of every container and gives a name. You can attach it to any container, and whatever is written there stays after the container is deleted.

It works like a USB stick. The container is a computer that gets wiped when it is removed. The volume is the stick you plug in to keep your files.

You will use a named volume mostly for a database on your own machine, as in this lesson's lab. In production, a volume is needed only by a container that is itself the storage, such as a database that a team runs itself. The container with your app usually has none (section 8).

Step 1: first, see the problem

Write a file in a container, with no volume:

podman run --rm docker.io/library/python:3.12-slim sh -c "mkdir /notes && echo remember-me > /notes/a.txt && ls /notes"

Output

a.txt

Now look for it in a second, brand-new container:

podman run --rm docker.io/library/python:3.12-slim sh -c "ls /notes"

Output

ls: cannot access '/notes': No such file or directory

The first container wrote the file into its own writable layer (Lesson 1). --rm deleted that container, and the layer went with it. The second container started fresh from the image, which never had /notes.

The part after the image name, sh -c "…", runs that whole line in a shell inside the container. The reference at the end of this section explains why it is needed.

Step 2: attach a volume with -v

-v NAME:PATH attaches a volume to a container. The left side is the volume's name. The right side is the folder where it appears inside the container. If no volume with that name exists yet, Podman creates an empty one.

podman run --rm -v notes:/notes docker.io/library/python:3.12-slim sh -c "echo remember-me > /notes/a.txt && ls /notes"

Output

a.txt

That container is now deleted. Start another one with the same volume:

podman run --rm -v notes:/notes docker.io/library/python:3.12-slim sh -c "cat /notes/a.txt"

Output

remember-me      ← the second container found the first one's file

The file survived because it was never inside the container. Writes to /notes went straight to the volume's folder.

The name and the path are separate things. With -v notes:/anywhere, the same file appears at /anywhere/a.txt.

Step 3: where the volume is, and the commands for it

podman volume inspect notes --format '{{.Mountpoint}}'

Output

/var/lib/containers/storage/volumes/notes/_data

That path is inside the Podman VM, not on your Mac, so you won't find it in Finder. That's the point: Podman manages it, and you work with it through commands. After step 2, a.txt was in that folder. The path shown is from the test Mac, whose Podman machine is rootful. On a default, rootless machine the path is in the VM user's home folder instead, under .local/share/containers.

podman volume lsList volumes
podman volume create NAMECreate an empty volume. Optional, because -v does it for you
podman volume inspect NAMEDetails, including where it's stored
podman volume rm NAMEDelete a volume and all its data
podman volume pruneDelete every volume no container uses, after asking

Step 4: watch out for nameless volumes

An image can declare that a folder should always be a volume. The official Postgres image does:

podman image inspect docker.io/library/postgres:17 --format '{{.Config.Volumes}}'

Output

map[/var/lib/postgresql/data:{}]

If you run such an image without mounting a named volume there, Podman creates an anonymous volume with a long random name, one per container. podman rm leaves it behind. On the test Mac, two of them were left over from test databases. podman rm -v removes a container together with its anonymous volumes, but the real fix is to always give data you care about a name: -v pgdata:/var/lib/postgresql/data.

A container gets Permission denied when it writes to a volume

Who may write to a volume

This part is about who is allowed to write into a volume's folder. It rests on two facts:

  • Every folder has an owner, and normally only the owner may create files in it.
  • A production image does not run as root. In Lesson 3 (section 2) the image gets a user called app, which Linux knows as user number 1000. That number is called the uid.

The commands below use --user 1000:1000. It makes a container run as user 1000 without needing a special image, which is what the USER app line does inside your image.

A non-root user can't write into a folder root owns.

podman run --rm --user 1000:1000 docker.io/library/python:3.12-slim sh -c 'ls -ld /opt; touch /opt/x'

Output

drwxr-xr-x. 2 root root 6 Sep 18 00:00 /opt
touch: cannot touch '/opt/x': Permission denied

root root is the folder's owner and group. In rwx r-x r-x, the first three letters are what the owner may do, and only they contain w (write). User 1000 is not the owner, so the write is refused.

A new volume starts as root's folder, and Podman hands it over.

podman run --rm --user 1000:1000 -v data:/data docker.io/library/python:3.12-slim sh -c 'ls -ld /data; touch /data/x && echo "write ok"'

Output

drwxr-xr-x. 2 1000 1000 6 Oct  3 23:25 /data
write ok

The owner is 1000, so the write works. On the test Mac, the volume's folder in the VM belonged to root before this command and to 1000 after it. Podman changes the owner of a new volume to the container's user, as long as the volume is still empty. Docker doesn't do this.

When the volume stays root's, the write fails. On a Docker server the new volume would still belong to root. The test Mac has no Docker, so the same situation was produced in Podman by letting a root container use a new volume first:

podman run --rm -v rootdata:/data docker.io/library/python:3.12-slim sh -c 'touch /data/made-by-root; ls -ld /data'

Output

drwxr-xr-x. 2 root root 26 Oct  3 23:25 /data

Then user 1000 tries the same volume:

podman run --rm --user 1000:1000 -v rootdata:/data docker.io/library/python:3.12-slim sh -c 'ls -ld /data; touch /data/x'

Output

drwxr-xr-x. 2 root root 26 Oct  3 23:25 /data
touch: cannot touch '/data/x': Permission denied

This is the error you would get on a Docker server, there on the very first run.

The fix: create the folder in the image. To make your image work on both, create the folder in the Containerfile and give it to the user:

Containerfile3 lines
RUN useradd --create-home --uid 1000 app

Create an ordinary user named app, with user number 1000 and a home folder /home/app. The base image has no such user. Lesson 3, section 2 covers this line.

RUN mkdir /data && chown app:app /data

Create the folder inside the image and make app its owner. chown means "change owner".

USER app

Switch to that user. Every instruction after this line, and the container itself when it starts, runs as app instead of root.

In an image built this way, ls -ld /data shows app app.

This helps on Docker because of one Docker rule: when a new, empty volume is attached at a path that already exists in the image, Docker copies that folder's owner into the volume. The volume then starts out owned by app, and the write works. If the image has no /data, there is nothing to copy, and the volume belongs to root. This rule was not tested for the course, because the test Mac has Podman only. It is Docker's known behaviour.

Two details of the middle line matter:

  • It must come before USER app. Each RUN runs as the current user, and only root may create a folder at the top level. With the line after USER app, the build failed with mkdir: cannot create directory '/data': Permission denied.
  • mkdir alone is not enough. Without the chown, the folder in the image belongs to root, and app got Permission denied when writing to it.

The same volume in another container

A volume keeps its files and its owner. Removing a container changes nothing inside the volume, so what the next container can do depends only on which user it runs as. First, user 1000 writes a file:

podman run --rm --user 1000:1000 -v shared:/data docker.io/library/python:3.12-slim sh -c 'echo hello > /data/a.txt; ls -ld /data'

Output

drwxr-xr-x. 2 1000 1000 19 Oct  3 23:33 /data

A new container with the same user: everything works. This is the normal case when you deploy a new version of your app. The new container runs as the same user number, so it can read and write the old data.

podman run --rm --user 1000:1000 -v shared:/data docker.io/library/python:3.12-slim sh -c 'cat /data/a.txt; touch /data/b.txt && echo "write ok"'

Output

hello
write ok

A new container with a different user: read only.

podman run --rm --user 2000:2000 -v shared:/data docker.io/library/python:3.12-slim sh -c 'ls -ld /data; cat /data/a.txt; touch /data/c.txt'

Output

drwxr-xr-x. 2 1000 1000 32 Oct  3 23:33 /data
hello
touch: cannot touch '/data/c.txt': Permission denied

The folder still belongs to 1000, because Podman does not hand over a volume that already has files in it. User 2000 can read the file but cannot write.

A new container running as root: everything works.

podman run --rm -v shared:/data docker.io/library/python:3.12-slim sh -c 'touch /data/by-root.txt && echo "write ok"; ls -ld /data'

Output

write ok
drwxr-xr-x. 2 1000 1000 51 Oct  3 23:33 /data

Root may write anywhere. The folder stays owned by 1000, but the new file by-root.txt belongs to root.

Handing over a volume that already has data. Podman has an option for that: add :U after the path. It changes the owner of the folder and of every file in it to the current container's user:

podman run --rm --user 2000:2000 -v shared:/data:U docker.io/library/python:3.12-slim sh -c 'ls -ld /data; touch /data/c.txt && echo "write ok"'

Output

drwxr-xr-x. 2 2000 2000 51 Oct  3 23:33 /data
write ok

After this, user 1000 is the one who can no longer write. :U is Podman-only; Docker does not have it.

Bind mounts: relaxed on a Mac, strict on Linux

On the test Mac, any user in the container could write to the shared folder, including app (uid 1000), and the files always showed up on the Mac as the Mac user's own. On a Linux server there's no VM in between. The numeric user ID is checked directly, so uid 1000 in the container can only write where uid 1000 on the server may write. Keep that in mind when a setup that works on your Mac fails with Permission denied on a server.

What sh -c "…" does, and why the quotes matter

Everything after the image name is the command the container runs instead of the image's default (for this image, python3). In sh -c "ls /notes", that command has three parts:

shThe shell program inside the container, the same kind of program as zsh on your Mac
-c"The command is the next argument" (c for command)
"ls /notes"The command line, passed as one piece of text

For a single program, you don't need it. Podman can start ls directly, and the result is the same:

podman run --rm -v notes:/notes docker.io/library/python:3.12-slim ls /notes

Output

a.txt

You need it for shell features. &&, >, | and $(…) are not programs. A shell has to interpret them. Without sh -c, the shell that does it is zsh on your Mac, before Podman starts.

Without sh -c:

podman run --rm docker.io/library/python:3.12-slim echo inside && hostname

Output

inside
your-mac.local      ← hostname ran on your Mac

zsh split the line at &&, so only echo inside ran in the container. With sh -c:

podman run --rm docker.io/library/python:3.12-slim sh -c "echo inside && hostname"

Output

inside
9cfcf488f0ac                   ← the container's ID: both commands ran inside

Step 1 needed sh -c for the same reason. Without it, the > is handled by your Mac:

podman run --rm docker.io/library/python:3.12-slim echo hi > /notes/a.txt

Output

zsh: no such file or directory: /notes/a.txt

zsh tried to create /notes/a.txt on your Mac, where no /notes folder exists. Podman never started.

The quotes matter. -c takes exactly one argument as the command. Without quotes, only ls is the command, and /notes is not passed to it:

podman run --rm -v notes:/notes docker.io/library/python:3.12-slim sh -c ls /notes

Output

bin
boot
dev
…                ← the container's top-level folders, not a.txt

The kind of quote matters too. With double quotes, your Mac fills in $… first:

podman run --rm docker.io/library/python:3.12-slim sh -c "echo $HOME"

Output

/Users/you    ← your Mac's home folder

With single quotes, the text reaches the container untouched:

podman run --rm docker.io/library/python:3.12-slim sh -c 'echo $HOME'

Output

/root            ← the container's home folder

Now a longer one. Each run of this command starts a new container, adds the current time to a file in the volume, and counts the file's lines:

podman run --rm -v notes:/notes docker.io/library/python:3.12-slim \
  sh -c 'date >> /notes/log.txt; echo "run: $(wc -l < /notes/log.txt) line(s)"'

Output of running it twice

run: 1 line(s)
run: 2 line(s)      ← the second container found the first one's line
the part after the image name4 pieces
sh -c '…'

Single quotes, so your Mac leaves $(…) alone and the container's shell runs it.

date >> /notes/log.txt

Add the current time as a new line at the end of the file. >> adds to a file; > would replace it.

;

Then run the next command, whether or not the first one worked. && runs it only if the first one worked.

$(wc -l < /notes/log.txt)

Count the lines in the file and put the number into the text that echo prints.

You have met sh -c before. In Lesson 3, the shell form CMD uvicorn main:app … is run as /bin/sh -c "uvicorn main:app …". That is why the shell became PID 1 there, and the container took 10 seconds to stop.

03Bind mounts: a folder from your Mac

A bind mount makes a folder from your Mac visible inside a container. It is a tool for your own machine, because it needs a folder on the computer that runs the container. Its main use is in step 3: you edit code on the Mac while the app runs in a container.

Step 1: share a folder

With a folder called shared containing from-mac.txt:

podman run --rm -v ./shared:/shared docker.io/library/python:3.12-slim \
  sh -c 'cat /shared/from-mac.txt; echo "written by the container" > /shared/from-container.txt'
ls -l shared/

Output

hello from the Mac                       ← the container reads your file
-rw-r--r--  1 you  wheel  19  from-mac.txt
-rw-r--r--  1 you  wheel  26  from-container.txt   ← and its file appears on your Mac

The syntax is the same as for volumes, but the left side is a path. A path starting with ./ or / means a bind mount; a plain name means a volume. On a Mac, this works because Podman shares your home folder into its VM; that's why your files are reachable at all.

Step 2: read-only mounts

Add :ro and the container can read but not change anything. Use it for configuration and model files:

podman run --rm -v ./shared:/shared:ro docker.io/library/python:3.12-slim touch /shared/nope

Output

touch: cannot touch '/shared/nope': Read-only file system

Step 3: live code reload during development

The problem. An image holds a copy of your code, made by COPY . . at build time. When you edit main.py on your Mac, a running container still has the old copy. To see each small change you would have to build the image, remove the container and start a new one.

The idea. Don't use the copy in the image. Share your project folder at /app, so the container reads the files that are on your Mac, and tell the server to restart when a file changes. An edit then shows up in a few seconds, with no build.

1. Go to the project folder. The folder matters, because ./ in the next command means "the folder I am in now":

cd ~/practice/hello-ai

2. Start the container with your folder shared.

podman run -d --name dev -p 8000:8000 -v ./:/app:ro hello-ai:1.0 \
  uvicorn main:app --host 0.0.0.0 --port 8000 --reload
what is new in this command2 pieces
-v ./:/app:ro

Share the current folder at /app, read-only. The shared folder covers what the image had at /app, so the container now sees the files on your Mac and not the image's copy.

uvicorn main:app … --reload

A command after the image name runs in place of the image's default command. This one is the default command plus --reload, which makes uvicorn watch the files in /app and restart the app when one changes.

3. Ask the app for its model name.

curl localhost:8000/health

Output

{"status":"ok","model":"keyword-sentiment-v1","api_key_configured":false}

4. Edit the code on your Mac. Open main.py in your editor, change keyword-sentiment-v1 to keyword-sentiment-v2, and save. Don't build anything.

5. Ask again.

curl localhost:8000/health

Output

{"status":"ok","model":"keyword-sentiment-v2","api_key_configured":false}

The answer changed a few seconds after the save. The logs show why:

podman logs dev

Output, the last lines

WARNING:  StatReload detected changes in 'main.py'. Reloading...
…
INFO:     Started server process [6]
INFO:     Waiting for application startup.
INFO:     Application startup complete.

uvicorn saw that main.py had changed and started the app again with the new code.

6. Check that the image did not change. Its own copy of the file still has the old line:

podman run --rm hello-ai:1.0 grep keyword-sentiment main.py

Output

MODEL_NAME = os.getenv("MODEL_NAME", "keyword-sentiment-v1")

So the dev container was reading the file on your Mac the whole time. A container started without -v runs the image's copy, and its /health still answers keyword-sentiment-v1.

Two things that go wrong.

  • The logs say Could not import module "main". The command was run in another folder, so that folder was shared at /app, and it has no main.py. The image's own main.py does not help, because the shared folder covers it. Remove the container with podman rm -f dev and start it again from the project folder.
  • A new package is not found. Only your code is shared. Packages were put into the image by pip install at build time. After import yaml was added to main.py, the reload failed with ModuleNotFoundError: No module named 'yaml'. A change to requirements.txt still needs a build.

7. Clean up. Change main.py back to keyword-sentiment-v1, so that your outputs match the rest of this lesson, and remove the container:

podman rm -f dev

Live reload is for development only. In production you run the built image, so what runs is exactly what you tested.

04Networks: containers finding each other

Why you need this. In the lab, hello-ai saves every prediction in a Postgres database. That makes two containers: one runs your code and one runs Postgres. Your code has to be told where the database is. This section shows what to write there, and how to read the two errors you get when it is wrong.

What Postgres is, and why it has its own container

Postgres (full name PostgreSQL) is a database: a program whose whole job is to store data and to answer questions about it. It is free and very widely used. It keeps data in tables. hello-ai's table is called predictions, and every prediction is one row in it, with the text, the label, the score and the time. You ask for rows in a language called SQL, for example "the ten newest rows". Step 4 runs three SQL statements.

hello-ai could write its predictions to a file in a volume instead. A database is used because it also handles what a file handles badly: several programs writing at the same moment, finding a few rows among millions, and a crash in the middle of a write.

Postgres is not a Python package that your code imports. It is a separate program that runs all the time and waits for connections. Each of the two images starts one program:

podman image inspect docker.io/library/postgres:17 --format '{{.Config.Cmd}}'
podman image inspect hello-ai:1.0 --format '{{.Config.Cmd}}'

Output

[postgres]
[uvicorn main:app --host 0.0.0.0 --port 8000]

Nothing forces the two programs into separate containers. You could install Postgres into your own image. Almost nobody does, for these reasons:

  • A container is built around one main process (Lesson 1). Podman starts it, and the container stops when it stops. A second program inside would not be watched: if it crashed, the container would still look fine.
  • The two are replaced at different times. Every update of your code replaces the hello-ai container. The database keeps running through that, with its data.
  • Only the database needs a volume. Postgres keeps its files in a named volume (section 2). hello-ai needs none, because it sends its data to Postgres.
  • You don't have to build it. The postgres:17 image is ready-made. In production the database is often not a container at all but a service such as Amazon RDS, and then only the address in hello-ai's settings changes.

Two words first: address and port

  • An IP address is the number of one machine on a network, for example 10.88.0.51.
  • A port is the number of one program on that machine. Postgres waits for connections on port 5432, and hello-ai on port 8000.

You have used both already. In curl localhost:8000/health, localhost is a name that means "this same machine", and 8000 is the port.

Step 1: every container has its own address

podman run --rm docker.io/library/postgres:17 hostname -i

Output of running it twice

10.88.0.51
10.88.0.52

hostname -i prints the address of the machine it runs on. Each run starts a new container, and each container gets its own address, as if it were a separate machine. Your numbers will differ.

So inside a container, localhost means that container itself. It does not mean your Mac, and it does not mean another container. To see this, start a database:

podman run -d --name db -e POSTGRES_USER=hello -e POSTGRES_PASSWORD=hello-dev-password \
  -e POSTGRES_DB=hello docker.io/library/postgres:17

The three -e settings tell Postgres which user, password and database to create. Now start a second container, and ask from there whether a database answers at localhost:

podman run --rm docker.io/library/postgres:17 \
  pg_isready -h localhost

Output

localhost:5432 - no response

pg_isready is a small program in the Postgres image. It asks one question: is a database accepting connections at this host? -h names the host. The answer is no, because there is no database inside that second container. The same question asked inside the db container gets a yes:

podman exec db pg_isready -h localhost

Output

localhost:5432 - accepting connections

This is why a setting such as localhost:5432 stops working when an app moves into a container. It worked while the app and the database ran on one machine.

Step 2: use the container's name, on a network you created

The second container could use the database's address. But a new container gets a new address, and containers are replaced often, for example at every update. An address written into your settings would soon be wrong. A name stays the same. Something then has to turn the name into the current address, and that lookup is called DNS.

First, see it fail. Ask for the database by its container name:

podman run --rm docker.io/library/postgres:17 \
  pg_isready -h db

Output

db:5432 - no response

A container started without --network joins Podman's default network, and that network has no name lookup. Podman looks names up only on a network you created.

You choose a container's network when you start it, with --network. So remove the database, create a network, and start the database again on it:

podman rm -f -v db
podman network create hello-net
podman run -d --name db --network hello-net -e POSTGRES_USER=hello \
  -e POSTGRES_PASSWORD=hello-dev-password -e POSTGRES_DB=hello docker.io/library/postgres:17

The -v on podman rm also removes the nameless volume that Postgres was given (section 2, step 4). Ask again, this time from a container on the same network:

podman run --rm --network hello-net docker.io/library/postgres:17 \
  pg_isready -h db

Output

db:5432 - accepting connections

If it says no response, the database is still starting. Wait a few seconds and run it again. You can also watch the lookup on its own. getent hosts asks for the address that belongs to a name:

podman run --rm --network hello-net docker.io/library/postgres:17 \
  getent hosts db

Output

10.89.1.2       db.dns.podman

Now the address that hello-ai is given in the lab is easy to read. It is called a connection string:

postgresql://Protocol hello:hello-dev-passwordUser : password@ dbHost: 5432Port/ helloDatabase

The host is db, the container's name, which the network turns into an address. 5432 is the port that Postgres waits on. The user, the password and the database are the ones from the -e settings above.

When a connection fails, the error tells you which part went wrong:

The error saysWhat failedUsual cause
Name or service not knownTurning the name into an addressThe two containers are not on the same network that you created, or the name is misspelt
Connection refusedThe address was found, but no program waits on that portA wrong port, localhost used as the host, or a database that has not finished starting (section 6)

You will meet both in the lab. Day to day you rarely type podman network create: Compose, in the next section, creates the network for you, and you write the service's name as the host.

Step 3: only publish what users need

-p (Lesson 2) is a separate thing from the network. It opens a way in from outside: from your Mac, and on a server, from the internet. Containers on the same network reach each other without it. The database was started without -p, so your Mac cannot reach it:

nc -z -w 2 localhost 5432 && echo reachable || echo "not reachable"

Output

not reachable

nc -z only tries to connect to a host and a port, and -w 2 makes it give up after two seconds. Here localhost is your Mac, because the command runs on your Mac.

That is the pattern to keep: containers talk to each other inside a private network, and only the entry point is published. The lab builds this layout, with hello-ai as the only published container:

Step 4: keep data by sending it to another container

Section 1 named a second kind of answer: send the data to a service that stores it. hello-ai does this in the lab: it runs without -v, and its predictions are stored by db.

Two short commands show the same thing with nothing else in the way. The first starts a container on hello-net, with no volume. It writes one row into the database, and then --rm removes it:

podman run --rm --network hello-net -e PGPASSWORD=hello-dev-password \
  docker.io/library/postgres:17 psql -h db -U hello -d hello \
  -c "CREATE TABLE messages (body text)" \
  -c "INSERT INTO messages VALUES ('written by container 1')"

Output

CREATE TABLE
INSERT 0 1

The second command starts a brand-new container, again with no volume, and asks for the row:

podman run --rm --network hello-net -e PGPASSWORD=hello-dev-password \
  docker.io/library/postgres:17 psql -h db -U hello -d hello \
  -c "SELECT * FROM messages"

Output

          body
------------------------
 written by container 1
(1 row)

The row survived because it was never stored in the first container. It travelled over the network to db. Compare section 2, step 1: there the first container kept its file inside itself, and the second container found nothing.

The parts of these commands that are new:

  • psql is Postgres's command-line client, and the postgres:17 image contains it. A command after the image name runs in place of the image's default command (Lesson 2), so these two containers run the client and never start a database server.
  • -h db is the host to connect to: the name of the database container, found through the network's DNS.
  • -U hello and -d hello are the user and the database that db was created with in step 2.
  • -e PGPASSWORD=… sets the variable that psql reads the password from.
  • -c "…" runs one SQL statement.

Without --network hello-net, the second command has nowhere to send its question:

podman run --rm -e PGPASSWORD=hello-dev-password \
  docker.io/library/postgres:17 psql -h db -U hello -d hello \
  -c "SELECT * FROM messages"

Output

psql: error: could not translate host name "db" to address: Name or service not known

This container joined the default network, where the name db means nothing, as at the start of step 2.

One thing to notice: the service still has to keep the data on a disk of its own. db is a container too, so it needs the first kind of answer, a volume. Started as in step 2, without -v, it gets an anonymous one (section 2, step 4). The Compose file in the next section gives it a named volume, pgdata. With a service such as Amazon S3, the storage runs on the provider's machines, and that disk is the provider's job.

Clean up. The lab starts both again from nothing:

podman rm -f -v db
podman network rm hello-net

05Compose: the whole app in one file

Running hello-ai and its database by hand takes a network, two long podman run commands, a volume, and the right order. You do that once in the lab. Compose lets you describe all of that once, in a file called compose.yaml, and start everything with podman compose up. podman compose doesn't do the work itself. It hands it to a Compose program on your Mac. The setup step installs Docker Compose (the test Mac has v5.5.1), which prints a line saying so each time:

Output

>>>> Executing external compose provider "/usr/local/bin/docker-compose". <<<<

Here's the file for hello-ai and Postgres, line by line:

hello-ai/compose.yaml2 services
services:

Each entry under services becomes one container. The entry's name is also the name other containers use to reach it.

api: build: context: . dockerfile: Containerfile

Build this service's image from the current folder. Compose looks for a file named Dockerfile by default; without the dockerfile line, the build failed on the test Mac with lstat …/Dockerfile: no such file or directory.

ports: - "8000:8000"

Publish the API, like -p 8000:8000.

env_file: .env environment: DATABASE_URL: postgresql://hello:hello-dev-password@db:5432/hello

Settings at run time, as in Lesson 3: API_KEY from .env, plus the connection string. The host is db, the other service's name.

depends_on: db: condition: service_healthy

Start the API only after the database reports healthy. Section 6 shows why the short form isn't enough.

db: image: docker.io/library/postgres:17

This service uses a ready-made image instead of building one.

environment: POSTGRES_USER: hello POSTGRES_PASSWORD: hello-dev-password POSTGRES_DB: hello

The Postgres image reads these on first start to create the user and database. This password is fine for a local setup; production passwords come from a secret store.

volumes: - pgdata:/var/lib/postgresql/data

A named volume where Postgres keeps its files, so data survives containers being replaced.

healthcheck: test: ["CMD-SHELL", "pg_isready -U hello -d hello"] interval: 2s timeout: 3s retries: 15

pg_isready is a tool in the Postgres image that answers "is the database accepting connections?". This is what condition: service_healthy waits for.

volumes: pgdata:

Declare the named volume. Compose creates it on first up.

What podman compose up creates

Compose prefixes everything with a project name, which defaults to the folder's name. In ~/practice/hello-ai you get:

  • a network hello-ai_default, with DNS switched on, so db resolves. You didn't have to write it.
  • a volume hello-ai_pgdata,
  • containers hello-ai-api-1 and hello-ai-db-1,
  • and the built image, named after the project and service.

06Start order and health

Step 1: the short depends_on isn't enough

A common first version lists the dependency without a condition:

    depends_on:
      - db

Started on the test Mac with a fresh, empty database volume:

podman ps and podman logs, 6 seconds later

db-1    Up 6 seconds
api-1   Exited (3) 5 seconds ago
psycopg.OperationalError: connection failed: connection to server at "10.89.0.2", port 5432 failed: Connection refused
  1. Compose started the db container, then the api container right after.
  2. The short depends_on only waits for the database container to start, not for Postgres inside it to be ready. On first start, Postgres spends a few seconds creating its files.
  3. The API tried to connect during those seconds, was refused, and exited.

Step 2: wait for healthy

With the healthcheck on db and condition: service_healthy on api, Compose waits:

podman compose up -d

Container db-1   Started
Container db-1   Waiting
Container db-1   Healthy       ← pg_isready succeeded
Container api-1  Starting
Container api-1  Started

Repeated three times from an empty volume, the API came up every time.

Step 3: the app's health reflects the database too

Databases can also disappear later, during a restart or a network problem. The Lesson 4 version of /health checks the database and returns HTTP 503 when it can't reach it. With the database stopped while the API kept running:

curl localhost:8000/health

{"status":"error",…,"database":"unreachable: OperationalError"}  HTTP 503
# after podman compose start db:
{"status":"ok",…,"database":"connected"}  HTTP 200

The container health check from Lesson 3 calls /health, so the container turns (unhealthy) while the database is gone, and a platform can react.

Development overrides

Compose automatically merges a second file, compose.override.yaml, if it exists. It's the standard place for development-only settings, such as the live reload from section 3:

services:
  api:
    volumes:
      - ./:/app:ro
    command: ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000", "--reload"]

With this file next to compose.yaml, editing main.py on the test Mac reloaded the API inside Compose within a few seconds. compose.yaml stays clean and production-like; the override adds conveniences on your machine only.

08What changes in production

Compose is mainly a tool for your machine and for testing. In production on AWS or Cloudflare, each piece of compose.yaml usually becomes a managed service. Lesson 6 covers deploying.

In compose.yamlOn AWSOn Cloudflare
The api serviceAn ECS service on Fargate (or Kubernetes on EKS)A Cloudflare Container, started by a Worker
The db containerAmazon RDS for PostgreSQL: backups, patching and failover handled for youAn external Postgres, reached through Hyperdrive, or Cloudflare's own D1 database
Named volumesEBS or EFS disks, or S3 for filesR2 object storage; container disks don't persist between restarts
The networkA VPC with security groups deciding who can reach whatWorkers and bindings; containers aren't exposed directly
environment and .envTask definition settings, with secrets from Secrets ManagerWorker variables and secrets, passed to the container

Don't run your production database in a container on a single machine unless someone owns backups and recovery. For a new project, a managed database is almost always the right call.

A volume is never part of the image

Volumes are not special to Podman or to your Mac. But when you hand an image to another team, no volume travels with it. An image holds only what the build put into it. The rest comes from whoever runs the container:

WhatWhere it comes from
Your code and dependenciesThe image
The default command and userThe image
Volumes and the data in themWhoever runs it
Values of environment variables and secretsWhoever runs it
Published ports, networks, CPU and memory limitsWhoever runs it

An image can declare that a path should be a volume, as Postgres does (section 2, step 4). That is only a note, and no data comes with it. Your own image, the hello-ai:2.0 you build in the lab below, declares nothing:

podman image inspect hello-ai:2.0 --format '{{.Config.Volumes}}'

Output

map[]

Every platform has its own kind of volume

PlatformWhat a volume is called
Podman, DockerNamed volume
Composevolumes: in compose.yaml
KubernetesPersistentVolumeClaim (Lesson 7)
AWS ECSAn EFS or EBS volume in the task definition
Cloudflare ContainersNone: the disk is wiped on restart, so data goes to a service such as R2 or D1

What you tell the team that deploys your image

1. Most often, the app container needs no volume. The app keeps nothing important on its own disk and sends data to a service built for it: a managed database such as Amazon RDS, or file storage such as S3. The deploy team only passes connection settings as environment variables. This is the second kind of answer from section 1.

Your hello-ai already works this way. It stores predictions in Postgres through DATABASE_URL. On your Mac, Postgres is a container with the pgdata volume. In production the database would usually be RDS, and hello-ai would get a different DATABASE_URL. The volume is only part of your local setup.

2. When a volume is needed, it is written into the deployment config. Examples are a database you run yourself, a vector index on disk, or a cache of model weights. The volume is declared in the Compose file, the Kubernetes manifest or the Terraform code. That file lives in git and gets reviewed like code, so nobody has to remember to create a volume by hand.

3. You hand over a short contract, usually in the README. For hello-ai it looks like this:

README: what this container needs

Port:       8000
Env vars:   MODEL_NAME     optional
            API_KEY        optional, secret
            DATABASE_URL   optional; if set, predictions are saved to Postgres
Health:     GET /health    returns 503 if the database is unreachable
Storage:    none, the container is stateless
Resources:  0.25 CPU and 256 MB RAM are enough

The Storage line answers the question "do they need to create a volume?". If it said /data must persist, the deploy team would attach their platform's kind of volume at that path. Run with those limits (--cpus 0.25 --memory 256m), hello-ai used about 42 MB.

Show the new main.py
"""hello-ai: a tiny stand-in for an AI service.

The "model" is a keyword counter. If DATABASE_URL is set, every prediction
is also saved to Postgres, and GET /history returns the latest ones.
"""
import os
import re
from contextlib import asynccontextmanager

import psycopg
from fastapi import FastAPI
from fastapi.responses import JSONResponse
from pydantic import BaseModel

MODEL_NAME = os.getenv("MODEL_NAME", "keyword-sentiment-v1")
API_KEY = os.getenv("API_KEY")  # comes from outside the image at run time
DATABASE_URL = os.getenv("DATABASE_URL")  # e.g. postgresql://user:pass@db:5432/hello
POSITIVE = {"good", "great", "love", "excellent", "happy", "fast", "works"}
NEGATIVE = {"bad", "terrible", "hate", "slow", "broken", "sad", "crash"}


def db():
    return psycopg.connect(DATABASE_URL, connect_timeout=3)


@asynccontextmanager
async def lifespan(app):
    if DATABASE_URL:
        with db() as conn:
            conn.execute(
                """CREATE TABLE IF NOT EXISTS predictions (
                       id SERIAL PRIMARY KEY,
                       text TEXT NOT NULL,
                       label TEXT NOT NULL,
                       score INTEGER NOT NULL,
                       created_at TIMESTAMPTZ NOT NULL DEFAULT now())"""
            )
    yield


app = FastAPI(title="hello-ai", lifespan=lifespan)


class PredictRequest(BaseModel):
    text: str


@app.get("/health")
def health():
    body = {"status": "ok", "model": MODEL_NAME, "api_key_configured": API_KEY is not None}
    if not DATABASE_URL:
        body["database"] = "not configured"
        return body
    try:
        with db() as conn:
            conn.execute("SELECT 1")
        body["database"] = "connected"
        return body
    except psycopg.Error as e:
        body.update(status="error", database=f"unreachable: {e.__class__.__name__}")
        return JSONResponse(body, status_code=503)


@app.post("/predict")
def predict(req: PredictRequest):
    words = re.findall(r"[a-z']+", req.text.lower())
    score = sum(w in POSITIVE for w in words) - sum(w in NEGATIVE for w in words)
    label = "positive" if score > 0 else "negative" if score < 0 else "neutral"
    if DATABASE_URL:
        with db() as conn:
            conn.execute(
                "INSERT INTO predictions (text, label, score) VALUES (%s, %s, %s)",
                (req.text, label, score),
            )
    return {"label": label, "score": score, "model": MODEL_NAME}


@app.get("/history")
def history(limit: int = 10):
    if not DATABASE_URL:
        return JSONResponse({"error": "no database configured"}, status_code=404)
    with db() as conn:
        rows = conn.execute(
            "SELECT id, text, label, score, created_at FROM predictions ORDER BY id DESC LIMIT %s",
            (limit,),
        ).fetchall()
    return [
        {"id": r[0], "text": r[1], "label": r[2], "score": r[3], "created_at": r[4].isoformat()}
        for r in rows
    ]

10Check yourself

Try answering each question out loud before opening it.

Q1What's the difference between -v pgdata:/var/lib/postgresql/data and -v ./pgdata:/var/lib/postgresql/data?Show

The first is a named volume that Podman creates and manages. The second, because it starts with ./, is a bind mount of a folder called pgdata in your current directory on your machine.

Q2You ran Postgres several times without a volume. Now podman volume ls shows volumes with long random names. Where did they come from?Show

The Postgres image declares /var/lib/postgresql/data as a volume, so Podman created an anonymous volume for each container. podman rm leaves them behind; podman rm -v would have removed them. Always name volumes for data you care about.

Q3Your app saves uploaded files to /app/uploads inside its container. What happens to them at the next deployment, and what are the two kinds of fix?Show

The deployment replaces the container, so the files are deleted with it. Either keep that folder outside the container, with a volume at /app/uploads, or send the files to a storage service such as Amazon S3. In production the second is the usual choice, and the app's container needs no volume.

Q4The API logs failed to resolve host 'db', although a container named db is running. What's the likely cause?Show

The containers are on Podman's default network, which has no DNS, or on different networks. Put both on the same network you created, or run them with Compose, which creates one for you.

Q5Should the database service in compose.yaml have ports: - "5432:5432"?Show

Not for the app: the API reaches it over the Compose network by name. Publishing it only makes sense if you want to connect from your Mac with a database tool, and even then only locally. On a server it would expose the database to the network.

Q6With depends_on: [db], the API sometimes exits with Connection refused on a fresh setup. Why doesn't depends_on prevent it?Show

The short form only waits for the database container to start, not for Postgres to accept connections. Add a healthcheck to db (for example pg_isready) and use condition: service_healthy.

Q7A teammate says "I ran podman compose down and lost the database". What did they probably actually run?Show

podman compose down -v, which also deletes the volumes. Plain down removes containers and the network but keeps named volumes.

Q8Why put the live-reload settings in compose.override.yaml instead of compose.yaml?Show

So compose.yaml stays close to production: it runs the built image, exactly as tested. The override, merged automatically on your machine, adds development conveniences like mounting your code and --reload.
